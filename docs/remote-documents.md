# 원격 문서 도구와 파일 전달 검증

## CPU 실패 후속 보완

2026년 10월 6일 검증된 GitHub `main`의 `79e68e50e8993cc0afd0b824bdb59ae245301530`을 Sites 소스 레이아웃에 맞춰 동기화하고 운영 버전 **45**로 비공개 배포했다. Sites 소스는 `bbc9508a07e1f9ad9e1dd48ca95247ad703c54d0`이며 기존 접근·D1/R2 바인딩·마이그레이션·runtime 설정을 유지했다. 배포 도구의 성공, 실제 사용자 `hwp_capabilities`의 400,000단위와 편집 안내 플래그, 고정 합성 문서의 읽기·계획·수정·복구·embedded 회수·시험 문서 정리를 확인했다. 회수한 13,312바이트는 로컬 독립 재현과 해시·바이트 전체가 일치하고 재열기를 통과했다. 배포 뒤 첫 기능 조회에는 재연결 오류가 있었고 사용자가 다시 연결한 뒤 성공했다. 인증 자동 갱신 해결로 집계하지 않는다.

원격 Worker의 문서 엔진은 파일 크기와 독립적으로 모든 BodyText 구역·문단·표 셀의 보이는 UTF-16 단위를 합산하고 **400,000 초과**를 `HOSTED_WORKLOAD_LIMIT_EXCEEDED`로 거부한다. 예를 들어 😀는 2단위, ZWJ 결합 이모지 👩‍💻는 5단위다. 글리프 수나 Unicode 코드 포인트 수가 아니며 숨은 제어 슬롯은 기존 raw 집계 규칙에 따른다. 2,000,000 단위의 공통 raw 한도는 유지하고 그 한도 초과에는 기존 `RAW_TEXT_LIMIT_EXCEEDED`가 우선한다. 일반 Node/로컬 어댑터는 원격 한도에 자동 편입되지 않는다.

가져오기·읽기·검사·편집·미리보기·복구의 원본 검사는 WASM 생성 및 검사 캐시 접근 전에 적용한다. 수정은 검증된 전체 기존 값과 새 값의 UTF-16 길이로 요청 전체의 결과 길이도 확인하며, 초과 시 엔진 변경 전에 거부한다. 요청을 임의로 분할하거나 일부만 저장하지 않는다. MCP는 저장하지 않았다는 고정 안내와 반복 요청·자동 일부 저장 금지를 반환하고, 브라우저 업로드도 한도를 설명하며 같은 파일 재시도를 비활성화한다.

`hwp_capabilities`의 `max_hosted_body_text_utf16_code_units`와 `hosted_body_text_limit_checked_before_wasm`는 이 원격 한도를 명시한다. 기존 4 MiB 전송 한도와 128버전 보관 계약을 유지한다. 이미 저장된 큰 문서의 바이트·이전 버전을 삭제하지 않으며, 인증·해시·삭제 상태를 검사하는 직접 `.hwp` 다운로드와 문서 목록·버전 목록·명시적 삭제는 WASM 길이 검사에 의존하지 않는다. 큰 문서의 내용 조회·미리보기·편집·복구 및 MCP 다운로드의 재열기 검사는 새 한도에서 거부될 수 있다.

저장본의 `/view`는 실제 `GuardError`의 `HOSTED_WORKLOAD_LIMIT_EXCEEDED`에만 제한 안내 화면으로 전환한다. 소유자·해시·삭제 상태를 검사하는 저장층에서 선택 버전을 다시 읽고 이력과 일치해야 HWP 다운로드·현재/이전 버전·저장 시각·이름을 표시한다. 엔진을 재시도하지 않으며 편집 후보·미리보기·에이전트 읽기 요청 복사와 클라이언트 스크립트를 출력하지 않는다. 그 외 권한·손상·지원 제한 오류와 저장본 검증 실패는 기존 거부를 유지한다. `page=0` 또는 페이지 없는 주소만 이 안내를 제공하고 다른 페이지를 대신 보여주지 않는다. 읽기와 링크 제공은 저장·복구·삭제를 실행하지 않는다. 공통 raw 한도나 다른 오류까지 우회하는 일반 다운로드 보장과는 구분하며 MCP 다운로드 계약은 유지한다.

이 보기 보완은 합성 데이터의 로컬 compiled Worker/D1/R2에서 큰 이전/현재 저장본, 작은 저장본의 기존 흐름, 반복 조회 뒤 모든 저장 행·블롭 불변, 잘못된 소유자·버전·손상·누락·삭제 거부를 검증했다. 별도 실제 로컬 D1/R2의 첫 읽기 및 안내용 재읽기에 삭제 완료/정리 대기 경합을 주입해 HTML 반환 차단도 확인했다. 운영 버전 45 배포는 성공했고 실제 두 OAuth 계정 격리·새 화면의 로그인 브라우저 검증은 별도 미완료다.

복구 한도는 현재 버전이 아니라 선택한 복구 원본에 적용한다. 한도 초과 원본의 복구는 현재 버전·이력·요청 기록·바이트를 그대로 유지하며 거부한다. 현재 버전이 한도 초과여도 사용자가 명시적으로 선택한 한도 이내의 이전 원본은 새 버전으로 복구할 수 있다. 로컬 compiled Worker/D1/R2에서 이 두 경로와 기존 큰 버전의 직접 다운로드를 합성 데이터로 검증했다.

이 한도는 실패한 120만 자 입력을 사전 거부하고 기존 350,009단위 합성 성공 사례를 유지하기 위한 보수적인 제공 범위다. 32,000ms 실패 로그에서 설정 CPU 한도를 추론해 정한 값이 아니며 모든 허용 문서의 CPU·메모리·동시 처리 성공을 보장하지 않는다. 운영 버전 45 배포와 실제 기능 조회의 새 한도 반영은 확인했다. 이후 실제 소유자 연결에서 합성 399,999단위 가져오기·전체 조회, 400,001단위 입력·수정 거부와 기존 버전 유지, 정확한 400,000단위 본문·셀 합산 수정·회수·재열기·복구를 확인했다. 첫 400,000단위 직접 가져오기의 전달 호스트 거부는 이후 DNS·HTTPS 확인과 사용자 승인으로 정확한 origin 하나를 추가한 환경 revision 7 재배포 뒤 실제 가져오기 성공으로 보완했다. [설정 후 검사](performance-check.md#파일-전달-호스트-설정-후-직접-가져오기)를 따르며 모든 향후 호스트 지원을 뜻하지 않는다. 실제 서버의 초과 이전 버전 복구 거부·새 화면의 로그인 브라우저 조작·일반 양식 지원과 인증 자동 갱신은 미완료다. ## 제공하는 도구

### 편집 가능 범위 안내

`hwp_read`는 기존 편집 제한을 설명하는 `editability_summary`와 각 블록의 `read_only_reasons`를 추가로 반환한다. 요약은 이번 응답 조각이 아니라 **선택한 버전 전체의 지원 본문·최상위 표 셀 문단**을 집계한다. 이어 읽기에서 같은 문단의 조각을 별도 대상으로 더하지 않으며, 이 요약만으로 내용 전체를 읽었다고 판단하지 않는다. 각 응답의 `complete`·`content_complete`와 `next_cursor` 계약은 그대로다.

`replacement_candidates`, `body_replacement_candidates`, `cell_replacement_candidates`는 검사에서 편집 가능한 문단 수다. `empty_cell_fill_candidates`, `cell_text_clear_candidates`와 새 소스의 `mixed_style_same_length_candidates`는 그 후보에 포함된 기능이며 따로 더하지 않는다. 셀 하나에 여러 문단이 있으면 각 문단을 별도 대상 하나로 센다. `read_only_reason_counts`는 문단별 이유 수로, 하나의 문단에 여러 이유가 있을 수 있어 전체 읽기 전용 문단 수와 합산하지 않는다.

읽기 전용 이유는 원문 대응 미확인, 문서의 미지원 구조, 표·페이지 번호를 포함한 본문 문단, 혼합 글자 서식, 대상 길이·서식 검사 범위, 기존 줄바꿈 및 원본 텍스트·서식 보존 제한을 구분한다. 설명은 고정 코드와 한국어 문구이며 upstream 오류나 임의 메시지를 복사하지 않는다. 기존 `edit_restrictions`도 유지한다. 안내로 편집 허용 범위를 넓히지 않으며 모든 후보는 실제 요청의 대상·기존 값·전체 길이·직렬화·재열기·독립 보존 검사를 통과해야 저장할 수 있다.

보기 화면도 같은 선택 버전의 집계를 표시한다. 이미 연 스냅샷에서 길이 1의 제한된 조각과 집계를 가져오므로 이를 위해 WASM을 다시 열거나 전체 본문을 HTML에 표시하지 않는다. capabilities의 `editability_summary_available`와 `target_read_only_reasons_available`가 이 안내를 명시한다. 새 소스의 합성 검사와 운영 버전 45 반영은 확인했으며 새 화면의 실제 로그인 브라우저 검증은 아직 남아 있다.

### 혼합 글자 서식의 제한된 치환 — 소스 구현, 운영 미배포

10월 6일 후속 소스는 원격 엔진의 본문·최상위 표 셀 문단에서 기존 혼합 서식을 유지하는 제한된 치환을 구현한다. 운영 버전 45와 로컬 Python/stdio 엔진은 기존 읽기 전용 제한을 유지한다. 새 소스의 capabilities는 `mixed_style_same_length_edit_available: true`, 대상은 `mixed_style_same_length_supported: true`, 집계는 `mixed_style_same_length_candidates`로 구분한다. 운영에서 이 기능을 사용할 수 있다고 판단하기 전에 별도로 승인된 소스 배포와 실제 기능 조회·합성 왕복을 확인해야 한다.

전체 기존 값과 새 값의 계약을 유지하되 실제로 달라지는 최소 연속 구간만 교체한다. Unicode 코드 포인트 수와 **각 위치의 UTF-16 길이**가 동일하고, 변경 구간 전체가 기존 한 서식 구간 안에 있어야 한다. 예를 들어 굵은 `성명: ` 뒤의 일반 서식 `김철수`를 `홍길동`으로 바꾸거나 같은 위치의 `😀`를 `🚀`로 바꿀 수 있다. 전체 UTF-16 합계만 같아도 이모지 위치를 옮겨 중간 서식 경계가 달라지면 거부한다. 새 글자 서식을 지정하거나 여러 서식 구간을 동시에 바꾸는 기능은 아니다.

기존 단일 텍스트·서식 레코드 구조에서 보이는 서식 구간 최대 32개, raw 서식 참조 최대 64개를 확인한다. raw 시작 위치·중복·숨은 참조·제어 슬롯·surrogate 경계와 모델 서식이 일치해야 하며, 기존 미지원 구조와 대상별 검사 한도를 그대로 적용한다. 지원 후보도 요청한 수정의 직렬화·재열기·내용 비교와 독립 보존 검사를 통과해야 저장된다. 대상 tag-68의 **위치와 ID를 포함한 전체 바이트**를 원본과 같게 유지하고 비대상 내용·서식·스트림을 기존 검사로 보존한다. 기존 원격 합산 400,000 UTF-16 한도와 버전·충돌 검사는 유지한다.

길이 변경·삭제·서식 경계를 넘는 치환은 `MIXED_STYLE_EDIT_UNSUPPORTED`와 고정 한국어 안내로 저장 전에 거부한다. 기존 문서·버전 유지, 같은 요청의 재시도 비권장, 요청하지 않은 축약·부분 저장 금지를 명시한다. 후보 자격이 없는 혼합 문단은 계속 읽기 전용이다. 읽기 응답의 `style.char_runs`는 코드 포인트 기준의 반열린 `[start, end)` 구간이며 raw UTF-16 위치와 구분한다.

합성 본문·일반 셀·병합 셀에서 이름 치환·이모지 치환·무변경 및 32/33 서식 구간 경계를 검사했다. 실제 로컬 compiled Worker/D1/R2의 가져오기·무저장 계획·동일 문서 저장·정확 재시도·다운로드·원본 복구, 잘못된 혼합 수정과 유효한 인접 수정을 한 요청에 넣었을 때 메타데이터·버전·요청 기록·바이트 불변을 확인했다. 모의 다른 owner 접근 거부도 검사했다. 독립 Python/olefile는 원본/편집본 6개의 54개 스트림과 tag-68 레코드 22개의 정확한 바이트를 비교했다. 실제 OAuth·운영 CPU·일반 양식·시각 배치의 인증은 아니다. `node scripts/check-mixed-style.mjs`와 `node scripts/check-python-guard.mjs`로 재현한다.

브라우저의 **문서 이름 설정**은 에이전트 도구 추가와 별개인 메타데이터 기능이다. 직접 입력한 이름을 최대 80개 Unicode 코드 포인트로 보관하며 원래 파일 이름과 본문에서 자동 생성하지 않는다. 이름을 비우면 문서 번호를 표시한다. 소유자별 이름 변경 번호와 조건부 SQL로 오래된 화면·동시 변경을 거부하고, 정확한 응답 유실 재시도는 중복 변경하지 않는다. 같은 origin의 POST만 받으며 입력을 HTML로 실행하지 않는다. HWP 바이트·현재 버전·버전 이력·편집 요청 기록을 바꾸지 않고, 이름은 문서 메타데이터의 일부로 같은 보관·삭제 계약을 따른다. 실제 두 OAuth 계정의 격리 인증으로 확대 해석하지 않는다.

`hwp_import`에서 형식이 검증된 공개 HTTPS origin이 실행 서버의 허용 목록에 없으면 `FILE_URL_NOT_ALLOWED`를 유지하면서 `data.transfer_diagnostic`을 추가한다. `file_origin_not_allowlisted`, 해당 요청의 `candidate_file_origin`, 실행 설정의 origin 개수만 알려주고 URL 경로·query·파일 ID·이름과 전체 허용 목록은 반환하지 않는다. 이 거부는 네트워크 요청·바이트 수신·저장 전이다. 잘못된 descriptor나 URL, 설정 오류와 임의 upstream 오류에는 origin 진단을 붙이지 않는다. 별도 probe 호출은 다른 전달 주소를 받을 수 있으므로 가져오기 자체의 진단을 기준으로 한다. 후보 주소는 권한이 아니며 자동으로 호스트를 추가하지 않는다.

**연결 성공은 개인 파일 업로드 지원 완료와 다르다.** `hwp_capabilities.data.upload_status`는 한국어 설명과 함께 `disabled`, `file_host_not_configured`, `development_enabled_unverified`를 구분한다. `agent_file_import_available`은 업로드 플래그와 파일 호스트 설정이 모두 있을 때만 참이며, `production_ready`는 현재 세 상태 모두 거짓이다. `stored_document_tools_available`은 기존 저장 문서의 도구 경로가 있다는 뜻이다. 업로드 게이트를 여는 설정이나 실제 OAuth·클라이언트 인증 결과로 해석하지 않는다.

## 수정 계획의 저장 전 검사

원격 `hwp_plan`은 대상과 기존 값만 검사하지 않고 실제 편집과 같은 엔진으로 HWP 후보 바이트를 메모리 안에서 생성한다. 재열기 내용·구조와 독립 raw 레코드 보존 검사도 통과해야 `valid: true`를 반환한다. 후보 바이트·출력 해시·다운로드 링크·새 버전은 반환하지 않으며 원본과 D1/R2 저장 상태를 변경하지 않는다.

성공 결과는 `validation_scope: targets_and_in_memory_serialization`, `serialization_checked: true`, `content_verified: true`, `raw_preservation_verified: true`, `saved: false`, `file_changed: false`, `persistence: none`을 알린다. `storage_checked: false`와 `layout_verified: false`는 유지한다. 이후 저장 시 현재 버전·소유권·저장 한도와 편집 검사를 다시 확인하므로 사전 검사 성공이 미래 저장 성공이나 배치 정확성을 보장하지 않는다. 과거 버전의 검사가 통과해도 `stale_for_save`는 별도로 표시한다.

`edit_profile_supported`는 입력의 대상/제어 계약이 맞는다는 뜻이며 writer 보존 인증이 아니다. 같은 값을 다시 넣는 요청도 생성·보존 검사에서 실패할 수 있다. writer가 바꾸는 미지원 메타데이터는 계획과 편집에서 모두 `PRESERVATION_MISMATCH`로 거부하고 D1/R2를 유지한다. 확인된 셀 목록의 0 값 기본화만 아래의 정확한 바이트 보존 경로로 처리하며, raw 보존 검사 예외는 추가하지 않는다.

라이브러리의 동기 `snapshot.plan`은 빠른 대상·값 검사로 남아 `validation_scope: targets_and_values_only`, `serialization_checked: false`를 반환한다. 원격 MCP는 비동기 `snapshot.preflight`를 사용한다. Python 로컬 stdio의 계획 계약까지 강화됐다고 표현하지 않는다.

### 셀 목록의 0 값 보존

고정 엔진 0.8.6은 셀 LIST_HEADER의 offset 6–7 원래 word가 0일 때 재생성 경로에서 `0x0400`을 넣는다. 합성 HWP와 [해당 버전 writer 소스](https://github.com/edwardkim/rhwp/blob/v0.8.6/src/serializer/control.rs#L690)에서 이 동작을 확인했다. 이 word의 의미를 추정하거나 차이를 무시하지 않는다.

원격 어댑터는 같은 레코드 순서·수·레벨, 모델에 맞는 셀 좌표·병합·문단 수와 나머지 셀 헤더의 바이트 완전 일치를 확인한 경우에만 `0 → 0x0400`을 원래의 두 0 바이트로 되돌린다. 다른 변화와 반대 방향·다른 nonzero word는 복구 대상으로 해석하지 않는다. 기본 CFB 교체 함수는 기존 sector/mini-sector 수와 저장 종류가 같은 경우만 허용한다. 원격 보완 경로에는 아래의 한 mini-sector 증가 예외만 있으며, 이외 공간 변화는 `BODY_REPAIR_ALLOCATION_UNSUPPORTED`로 거부한다. 전체 모델 재열기와 독립 raw 보존 검사는 보완 뒤에도 필수다.

기본 DEFLATE 설정이 기존 할당 조건을 벗어나면 같은 raw 바이트를 level 9로 한 번만 다시 압축한다. 임의 padding이나 요청하지 않은 내용 변경으로 크기를 맞추지 않으며 압축 설정의 변경을 내용·서식 보존 검사 예외로 취급하지 않는다. 합성 8×2 표의 압축 경계 사례로 기본 설정의 실패와 대체 설정의 동일 할당·재열기·저장 전 불변·실제 로컬 workerd 저장 및 회수를 확인한다. 별도 39×2 표에서는 대체 설정의 할당 감소가 여전히 거부되며 저장 상태와 원래 다운로드 바이트를 유지한다. 처리 시간과 전체 메모리 한도 인증은 아니다.

대체 설정에도 공간이 **한 64바이트 mini-sector만 증가**하는 본문 한 개는, 이미 확보된 root mini-stream의 논리 끝 다음 공간이 64바이트 전체 0이고 기존 miniFAT 항목이 `FREESECT`일 때만 그 공간을 연결할 수 있다. root 논리 크기는 64바이트 증가하지만 파일 길이·일반 FAT·root sector chain·directory tree와 다른 스트림의 위치·바이트는 유지한다. 본문 크기 DWORD, root 크기 DWORD와 miniFAT 두 DWORD 및 지정 본문 데이터 밖의 모든 파일 바이트가 그대로인지 확인하고 CFB를 다시 파싱한다. root 크기의 64바이트 정렬과 변경하는 크기 필드의 high DWORD 0도 요구한다. 공간 부족·점유·nonzero 꼬리·손상 체인, miniFAT 확장·root/FAT 확장, 할당 감소·저장 종류 전환, 두 mini 증가 또는 여러 본문의 동시 증가는 거부한다. 기존 root 내부의 빈 구멍을 재사용하지 않는다. [CFB miniFAT 구조](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cfb/c5d235f7-b73c-4ec5-bf8d-5c08306cd023)에 맞춘 제한된 연결 변경이며 일반 allocator가 아니다.

고정 합성 3×2 표의 셀 비우기로 이 경로의 계획·저장·재시도·다운로드·재열기와 이전 버전 불변을 실제 로컬 workerd/D1/R2에서 검사한다. CFB v3/v4의 비연속 mini 연결과 다른 스트림 보존, 잘못된 꼬리·할당·메타데이터의 거부도 시험한다. 원격 계획과 메모리 편집의 `body_mini_sector_growth`는 0 또는 1이며 원격 저장 응답의 필드나 서식 정확성 인증은 아니다.

계획과 메모리 편집 결과의 `restored_cell_list_words`는 이 정확한 보완의 개수를 알린다. 원격 저장 응답에 이 개수가 포함된다는 뜻은 아니다. 합성 문서의 무저장 계획·같은 문서 저장·다운로드·재열기, 쪽 번호 보존과의 조합, unrelated 메타데이터 거부 및 CFB v3/v4 mini/regular 경계를 검사한다. 일반 CFB/HWP writer, 서식 인증, Python 로컬 stdio의 지원 확대는 아니다.

### 할당 조건 실패의 에이전트 피드백

검증된 CFB 본문 스트림에서 기존 할당 수나 mini/regular 저장 종류의 불일치가 확인되면, MCP는 `isError: true`와 첫 텍스트의 `BODY_REPAIR_ALLOCATION_UNSUPPORTED`를 유지하면서 `data.edit_diagnostic`을 추가한다. 한국어 설명, `existing_body_allocation_mismatch` 상태와 후보·보완 데이터의 바이트 수, 단위 크기·개수 및 저장 종류만 전달한다. 원본 HWP의 크기나 PC 디스크 용량이 아니라 **writer가 만든 편집 후보의 본문 할당 조건**이다. 작아진 압축 데이터도 기존 할당 개수가 달라지면 거부하므로 이를 모두 공간 부족으로 설명하지 않는다.

`saved: false`, `file_changed: false`와 함께 동일 요청의 무조건 재시도를 권하지 않고, `suggested_action: report_limit_without_altering_request`를 제공한다. 재인증이나 저장소 용량 오류로 오인하지 않으며 실패 이유를 알리고 현재 요청을 유지한다. 자동 일부 저장, 요청을 쪼개 일부만 반영하기, 요청하지 않은 변경 추가 및 임의 축약·공백·padding으로 압축 크기를 맞추기는 허용하지 않는다. 사용자가 요청 범위를 바꾸기 전에는 저장 성공을 위해 다른 내용을 고치지 않는다.

진단은 검증된 컨테이너 경로가 만든 오류 객체에만 연결한다. 임의 upstream 오류의 속성·메시지·stack을 진단으로 읽지 않으며 문서 텍스트·이름·ID·해시·스트림 경로·URL은 포함하지 않는다. 모양이 같은 오류나 누락된 스트림에는 진단을 붙이지 않는다. CFB v3/v4의 증가·감소·저장 종류 경계, 위조·오염 오류의 개인정보 비노출과 실제 로컬 workerd/D1/R2의 계획·저장 거부 후 버전·blob·다운로드 불변을 검사한다. 지원 폭을 넓히거나 할당 제한을 해결한 기능은 아니며 Python 로컬 stdio의 오류 계약은 유지한다.

### 조회 단계의 대상별 편집 제한

`hwp_read`의 각 블록은 `editable`과 `edit_restrictions`를 반환한다. 원본 글자 서식 참조가 눈에 보이는 텍스트의 서식 검사에 모두 포함되지 않으면 `RAW_CHAR_SHAPE_REFS_UNCOVERED`, 서식 레코드의 구조를 확인하지 못하면 `RAW_CHAR_SHAPE_LAYOUT_UNVERIFIED`로 읽기만 허용한다. 기존 텍스트 레코드가 정확히 한 개가 아닌 경우에는 아래 검증된 빈 셀 채우기 예외 외에 `RAW_TEXT_RECORD_LAYOUT_UNVERIFIED`를 표시한다. 사유는 고정 코드와 한국어 `message_ko`로 제공하며 문서 내용을 오류에 넣지 않는다.

이 제한은 문서 전체 읽기를 막거나 다른 지원 대상을 일괄 차단하지 않는다. 제한된 대상을 선택한 계획·편집은 후보 생성 전에 `TARGET_NOT_EDITABLE`로 거부한다. `editable: true`도 저장 보존 인증이 아니므로 실제 생성·재열기·raw 검사는 여전히 필수다. 여러 대상의 결합과 텍스트 길이에 따라 후보의 압축 크기가 달라질 수 있으며, 셀 목록 보완에 필요한 기존 할당 조건이 맞지 않으면 `BODY_REPAIR_ALLOCATION_UNSUPPORTED`로 저장하지 않는다. 실패한 여러 대상의 요청을 임의로 나누어 일부만 저장하지 않는다.

합성 HWP의 보이지 않는 끝 서식과 검증되지 않은 범위 메타데이터를 가진 빈 셀을 생성해 제한 사유·대상 거부·입력 불변을 검사한다. 실제 로컬 workerd/D1/R2에서는 MCP 조회에 사유가 전달되는지, 거부 뒤 버전·blob이 그대로인지, 다른 셀을 수정해도 비대상 끝 서식이 유지되는지 확인한다. 테스트 신원은 모의이며 실제 OAuth 격리나 시각 배치 인증이 아니다. Python 로컬 stdio에는 이 원격 조회 제한을 자동 적용하지 않는다.

### 기존 빈 셀의 텍스트 채우기

원격 조회의 `empty_cell_fill_supported: true`는 기존 최상위 표 셀의 기존 빈 문단을 채울 수 있는 좁은 원본 구조를 뜻한다. 22/24바이트 문단 헤더, 종료 문자를 포함한 원본 문자 수 1, 제어·범위 메타데이터 없음, 시작 위치 0의 단일 글자 서식과 한 줄의 레코드가 정확히 일치해야 한다. 일반 빈 본문, 혼합/숨은 서식, 제어가 있는 셀, 다른 레코드 구조는 이 예외에 포함하지 않는다. 빈 문단이나 셀을 새로 만드는 기능도 아니다.

기존 `target_id`, `expected_old: ""`, `new_text` 계약을 사용한다. 후보에 대상 문단 바로 뒤의 텍스트 레코드 한 개만 추가됐는지, UTF-16 원문이 요청한 문자열과 종료 CR에 정확히 일치하는지 먼저 독립 검사한다. 탭·줄바꿈·제어 문자 삽입은 거부한다. 검증한 대상에만 빈 CR 레코드를 보탠 **검사 전용 원본 투영**으로 기존 엄격한 전체 raw 검사를 실행한다. 이 투영을 HWP로 저장하거나 출력하지 않으며 나머지 레코드·서식·셀·문단 수·스트림 보존 조건은 완화하지 않는다. 셀 목록 0 word 보완 뒤에도 추가 텍스트를 다시 검사하고 전체 모델을 재열기한다.

계획·메모리 편집은 `empty_cell_text_insertions_verified`를 반환하며 실제 추가만 있으면 raw 검사 범위를 `narrow_raw_record_preservation_with_verified_empty_cell_insertions`로 표시한다. 원격 저장 응답에 이 개수·범위가 포함된다는 뜻은 아니다. 빈 값 유지 요청은 기존 엄격한 경로를 쓰고, 문단 생성·서식 변경으로 범위를 확대하지 않는다. 기존 텍스트의 비우기는 아래 별도 원본 구조와 정확한 제거 검사를 요구한다. `editable`은 여전히 사전 검사 대상 자격이지 모든 문자열·조합의 저장 성공 인증이 아니다.

합성 문서에서 두 빈 셀과 기존 셀의 결합 편집, 정확한 재열기·서식/비대상 보존, 잘못된 추가 위치·수·UTF-16·제어·메타데이터 거부, 쪽 번호 및 셀 목록 보완과의 조합을 검사한다. 실제 로컬 workerd/D1/R2에서는 계획 전후 불변, 기본 저장·정확한 재시도·다운로드·재열기 및 원본 버전 보존을 시험한다. 고정 `hwp_workflow_probe`도 빈 셀 채우기를 포함한다. Python 로컬 stdio 지원 확대, 시각 배치·임의 문서·실제 Cloud/Dots 인증은 아니다.

### 기존 셀의 텍스트 비우기

`cell_text_clear_supported: true`는 기존 최상위 표 셀 문단의 일반 텍스트를 빈 문자열로 바꾸는 원본 구조 자격이다. 비어 있지 않은 모델 문자열과 UTF-16 텍스트 레코드 및 마지막 CR이 정확히 일치하고, 문자 수·단일 시작 서식·줄 레코드 수·22/24바이트 헤더를 확인해야 한다. 제어·범위 메타데이터, 탭·줄바꿈·제어 문자, 숨은/혼합 서식과 다른 자식 레코드는 제외한다. 지원 플래그가 있더라도 실제 후보의 할당·보존 검사에서 실패할 수 있으며 자동 분할이나 일부 저장으로 우회하지 않는다.

같은 버전의 `target_id`와 전체 `expected_old`, `new_text: ""`를 요청한다. 원본에 있던 해당 텍스트 레코드 한 개만 후보에서 없어지고 문단·셀·서식·다른 레코드는 남았는지 독립 검사한다. 원래 글자 서식 ID는 빈 문단에서도 그대로 유지하고 재열기로 확인한다. 빈 셀 채우기와 결합할 때도 허용된 추가·제거 위치와 수를 함께 검사한 뒤, 정확한 변경만 반영한 검사 전용 원본 투영에 기존 엄격한 전체 raw 검사를 적용한다. 실제 저장 바이트에 임의 레코드를 보태거나 비대상 제어를 지우지 않는다.

계획·메모리 편집의 `cell_text_record_removals_verified`는 검증한 제거 수다. 제거가 있으면 raw 범위는 `narrow_raw_record_preservation_with_verified_cell_text_transitions`이며, 추가가 함께 있으면 그 수도 별도로 반환한다. 저장 응답에 이 개수·범위가 포함된다는 뜻은 아니다. 문단 삭제·셀 삭제·범용 제어 제거와 다르며 본문 문단 비우기까지 지원을 넓히지 않는다. 공유 WASM 어댑터의 비우기 옵션은 검증한 원격 대상에만 내부적으로 켜고, Python 로컬 stdio의 기본 차단·독립 raw 계약은 유지한다.

합성 검사에서는 일반/비기본 서식의 비우기→다시 채우기, 추가·제거·일반 교체를 요청 순서와 무관하게 결합하기, 예상 밖 텍스트 잔존·잘못된 레코드 제거·다른 메타데이터 변화 거부, 쪽 번호 및 셀 목록 보존과의 조합을 시험한다. 실제 로컬 workerd/D1/R2에서는 계획 전후 불변, 같은 문서에 채우기→비우기→다시 채우기, 정확한 재시도·다운로드·재열기와 모든 이전 버전 보존을 확인한다. 고정 원격 workflow도 새로 채운 합성 셀을 다시 비운 뒤 복구한다. 모의 신원과 실제 사용자 연결 검증은 구분하며 시각 배치·Cloud/Dots 인증을 뜻하지 않는다.

## 입력과 출력

### 브라우저에서 저장 문서 다시 열기

인증된 `GET /documents`는 같은 사용자의 저장 문서를 최대 20개씩 표시한다. 업로드·보기 화면의 **내 문서** 링크로 이동한다. 문서 내용·파일 이름·blob key·SHA-256을 조회하거나 표시하지 않고, D1의 현재 버전 포인터에 연결된 저장 시각·크기·revision만 사용한다. 삭제 영수증이 있는 문서는 완료 여부와 관계없이 제외한다. 보기 링크는 조회 당시의 명시적 현재 버전에 고정하며, 버전 시간의 최댓값으로 현재를 추정하지 않는다.

마지막 저장 시각 내림차순과 문서 ID 내림차순으로 정렬하며, `before=<저장시각>.<문서 UUID>`의 엄격한 단일 위치 인수와 선택적인 `q` 검색어를 받는다. 위치 값은 인증 토큰이 아니며 위치와 검색어를 변경해도 서버에서 인증한 owner 필터를 유지한다. 한 번에 21개 metadata row만 읽어 다음 페이지 여부를 판단한다. 같은 시각의 22개 합성 문서에서 누락·중복 없는 두 페이지를 검사했다. 동시 수정으로 순서가 바뀌는 동안 전체 목록을 하나의 불변 snapshot으로 보장하지는 않는다. 최근 상태는 첫 목록을 다시 열어 확인한다.

검색어는 앞뒤 공백을 제거한 최대 80 Unicode 코드 포인트이며 보이지 않는 제어 문자와 중복 `q`를 거부한다. 직접 설정한 표시 이름과 문서 ID의 부분 문자열을 바인딩된 SQL 인수로 검색한다. 한글과 ASCII 대소문자를 검사했으며 `%`·`_`는 와일드카드가 아닌 일반 문자다. 검색 조건을 적용한 전체 소유자 metadata에서 페이지를 고르며 다음 링크에도 검색어를 유지한다. HWP 본문과 원래 파일 이름은 검색하지 않는다. 결과가 없다는 안내와 계정의 문서가 없다는 안내를 구분하며, 현재 페이지의 행 수를 전체 검색 결과 수로 표시하지 않는다. 로컬 실제 workerd/D1/R2의 합성 22개 검색·이름/ID·특수문자·모의 두 owner 격리·삭제 진행 제외 및 조회 전후 저장 불변을 검사했다. 이름 변경이나 저장이 동시에 일어날 때 불변 검색 snapshot을 제공하지는 않는다.

GET 목록은 문서 생성·수정·삭제, R2 읽기와 엔진 실행을 하지 않는다. 비GET은 405, 익명·불완전한 신원은 401이며, Range·body·추가/중복/잘못된 위치 인수는 거부한다. private/no-store와 수동 보기 화면의 CSP를 유지하고 script·외부 자원을 추가하지 않는다. 실제 로컬 workerd/D1/R2/WASM에서 모의 두 owner의 같은 이메일 격리, 타인 버전 보기 거부, 요청 전후 저장 metadata·blob 불변, 명시적 현재 버전·삭제 진행 제외·손상 metadata 거부·재시작을 검사한다. 실제 두 OAuth 사용자 격리와 일반 개인 문서·시각 배치 인증은 별도다.

`hwp_import`는 공식 OpenAI 플러그인의 `openai/fileParams` 계약을 사용한다. `file`에는 필수 `download_url`, `file_id`와 선택 `mime_type`, `file_name`을 선언한다. 이 선언만으로 Codex의 로컬 경로나 클라우드 첨부가 자동 전달되는 것은 아니다. [OpenAI 플러그인 도구 참조](https://developers.openai.com/plugins/reference)

업로드가 꺼진 MCP `hwp_import`는 계속 `isError: true`와 첫 text block의 `DOCUMENT_UPLOADS_NOT_ENABLED`로 실패한다. 안전한 descriptor라면 추가 text block과 기존 출력 schema에 맞는 `structuredContent`로 공개 HTTPS origin만 알려준다. 파일명·ID·임시 URL 경로·query·MIME은 반환하지 않고 네트워크·바이트 수신·저장도 하지 않는다. 관찰된 origin은 허가 근거가 아니다. 잘못되거나 안전하지 않은 descriptor는 추가 진단 없이 기존 게이트 오류를 유지한다. 입력 schema, 업로드 플래그와 일반 HTTP import 동작은 바꾸지 않았다.

진단은 서버 내부에서 만든 오류 객체에만 연결하고 임의 오류 속성을 직렬화하지 않는다. MCP와 HTTP는 명시적으로 등록한 고정 오류 코드만 반환한다. 대문자로 된 임의 코드, 오류 message·stack·기타 속성은 내보내지 않으며 code getter가 실패해도 `DOCUMENT_OPERATION_FAILED`로 응답한다. 기존 알려진 오류 코드와 업로드 거부의 origin-only 진단은 유지한다. 단위 검사와 actual workerd의 업로드 거부·익명 접근·인수 변조·안전하지 않은 URL·기존 DB/R2 보존 검사가 통과했다. 이는 새 진단 도구의 목록 반영이 지연돼도 기존 첨부 도구의 실패 이유를 확인할 수 있게 하는 피드백이며 업로드를 대신 수행하는 경로가 아니다.

서버는 관리자가 설정한 정확한 HTTPS 파일 origin만 따라가고, 리디렉션을 거부하며 사용자 인증 헤더를 전달하지 않는다. Content-Length가 없거나 잘못되더라도 실제 스트림은 4 MiB 이하로 제한한다. 파일 이름과 MIME 문자열만으로 HWP라고 판단하지 않고 저장 전 실제 바이트를 검사한다. 확인하지 않은 다운로드 호스트는 추측해서 허용하지 않는다.

스트림 조각을 모두 배열에 남기지 않고 크기가 정해진 버퍼에 복사한다. 조각은 16,384개 이하로 제한하고 초과·읽기 실패 시 스트림을 취소하고 reader를 해제한다. 빈 조각 반복도 이 제한에 포함한다. MCP 요청 본문은 별도로 3 MiB 이하로 제한한다. 이는 전체 엔진·동시 요청의 메모리나 CPU 인증은 아니다.

본문 수신에는 조각마다 갱신하지 않는 30초 전체 제한을 적용한다. 멈춘 스트림은 `TRANSFER_TIMEOUT`으로 거부하고 부분 바이트를 반환하거나 저장하지 않는다. upstream의 취소 작업이 끝나지 않거나 거부돼도 오류 응답과 reader 잠금 해제를 무기한 기다리게 하지 않는다. 정상 전송에서는 timer를 정리한다. 기능 조회의 `transfer_body_timeout_ms`가 이 제한을 알린다. 외부 파일의 응답 헤더 대기는 별도의 fetch 제한이며 이 본문 수신 제한을 OAuth 갱신·HWP 엔진 실행·D1/R2 저장 전체의 30초 제한으로 설명하지 않는다.

바이너리 경로는 `POST /documents/import`, 결과 경로는 `GET /documents/{document_id}/versions/{version_id}.hwp`다. 입력은 동일 origin, 요청 UUID, 허용 MIME과 사용자 인증이 필요하다. SVG는 같은 버전 아래 `/pages/{page}.svg`로 제공한다. 다운로드는 사용자 인증과 소유자 범위를 확인하고 캐시·활성 콘텐츠를 제한한다. URL에 사용자 자격이나 공개 접근 토큰을 넣지 않는다.

기본 저장은 원격의 같은 논리 문서를 갱신한다. PC 원본은 자동 갱신되지 않는다. 고정 합성 진단의 embedded HWP 바이트는 로컬 Codex에서 회수했지만, 실제 HWP 첨부 산출물의 다운로드 UI나 로그인한 브라우저에서 이 주소를 내려받는 클라이언트 전 과정은 별도 검증한다.

## 쪽 번호 보존 전용 편집

원격 엔진은 단일 구역의 본문 루트 문단에 있는 쪽 번호 위치 제어(`pgnp`)만 보존 전용으로 허용한다. 독립 레코드 검사는 제어 ID와 16바이트 헤더, 확인된 속성 범위, 자식 레코드 부재, 16바이트 연결 슬롯의 코드·끝 코드·예약 바이트, 모델이 보고한 제어의 문단과 개수의 일치를 요구한다. 다른 미지원 요소나 미확인 형태가 있으면 기존처럼 편집을 거부한다. [한컴 HWP 5.0 규격 revision 1.3](https://cdn.hancom.com/link/docs/%ED%95%9C%EA%B8%80%EB%AC%B8%EC%84%9C%ED%8C%8C%EC%9D%BC%ED%98%95%EC%8B%9D_5.0_revision1.3.pdf)의 제어 헤더와 표 147·148을 기준으로 범위를 좁혔다.

`hwp_read`는 `unsupported`를 지우지 않고 `preserved_controls`에 `edit_mode: preserve_bytes_only`, `semantic_read_supported: false`를 알린다. 제어가 붙은 문단은 읽기 전용이다. 다른 지원 대상의 계획은 `edit_profile_supported: true`일 때 가능하지만 저장 성공을 뜻하지 않는다. 지원 블록의 끝인 `complete: true`와 전체 이해 범위의 `content_complete: false`도 함께 반환할 수 있다.

편집은 모델 재열기와 별도로 모든 제어 payload·레코드 순서·문단 연결 바이트의 보존을 검사한다. 하나라도 달라지면 결과 바이트를 반환하거나 저장하지 않는다. 개인정보 없는 합성 네 가지 형태와 손실·변조 거부, 실제 로컬 workerd/D1/R2의 업로드→읽기→계획→같은 문서 저장→다운로드→재열기와 이전 버전 불변을 시험했다. 이 시험의 신원은 모의다. 실제 개인 문서의 계획 검사와 실제 저장·시각 배치 인증을 구분한다. Python 로컬 stdio 경로는 이 예외를 켜지 않으며 기존의 미지원 요소 차단을 유지한다.

## 사용자 인증과 운영 제한

Sites가 전달한 신뢰할 수 있는 사용자 ID와 이메일 헤더를 모두 요구한다. 사용자 ID의 해시로 소유자를 만들고 이메일은 저장하지 않는다. 표시 이름이나 이메일 변경으로 문서 소유자가 바뀌지 않는다. 도구 인수의 소유자, 임의 클라이언트 헤더와 서비스 접근 자격을 사용자 권한으로 해석하지 않는다. 이 헤더 검사 자체는 독립 OAuth 검증기가 아니므로 일반 인터넷에 Worker를 그대로 노출하면 안 된다.

`node scripts/check-isolation.mjs`는 실제 로컬 workerd/D1/R2/WASM에서 모의 두 사용자를 시험한다. 같은 이메일·같은 import/edit 요청 UUID가 사용자별로 분리되고, 같은 사용자의 이메일 변경은 소유권과 정확한 재시도를 유지한다. 문서별 도구 8종과 HWP·보기·SVG 경로의 양방향 타인 접근, 타인 버전 ID 혼합과 owner 등 인수 주입을 거부한다. 각 거부 뒤 DB 메타데이터·영수증·R2 바이트 불변을 확인하며, 비공개 문자열을 포함한 엔진 오류는 MCP와 HTTP 모두에 노출되지 않는다. 이는 합성 파일·모의 신원 검사이며 실제 두 OAuth 계정, 접근 철회나 운영 로그의 검증을 대신하지 않는다.

기본 설정은 업로드 비활성화와 빈 전달 origin 목록이다. 사용자가 업로드 준비를 요청한 소유자 전용 비공개 배포에 한해 `HWP_EASY_ALLOW_UPLOADS=true`와 검증한 정확한 `HWP_EASY_FILE_ORIGINS` 목록을 설정했다. 공개·그룹·외부 방문자 접근으로 확대하지 않았고 OAuth·플러그인·MCP 주소를 재사용했다. `HWP_EASY_ORIGIN`은 확인된 배포 origin으로 고정하며 요청 Host를 신뢰하지 않는다. 일반 사용자 배포·실제 두 OAuth 사용자 격리·접근 철회·운영 로그/백업/미게시 바이트 정리는 여전히 미검증이며 민감 문서 운영의 안전성을 보증하지 않는다.

### 소유자 전용 파일 가져오기 시험

Codex Desktop의 실제 native `hwp_import` 파일 인수로 13,312바이트의 합성 HWP를 수신해 D1/R2에 저장했다. 지원 블록 10개를 모두 읽고 문단과 셀 두 곳을 편집해 같은 문서에 저장한 뒤, 원본·현재 버전의 내용과 해시를 확인했다. 비대상 내용과 이전 버전이 유지됐고 가져오기·편집의 정확한 요청 재시도는 문서·버전을 추가하지 않았다. 쓰지 않는 계획 검사의 전후 revision도 같았다. 기존 보관 시험 문서는 변경되지 않았다. 현재 버전의 보호된 HWP 다운로드 주소 반환도 확인했지만, 이번 가져오기 결과의 브라우저 수신·독립 재열기까지 새로 시험한 것은 아니다.

실제로 관찰한 전달 호스트의 공개 DNS와 유효한 TLS 호스트 인증을 확인하고 정확한 origin만 설정했다. 10월 6일에는 새로 관측된 주소를 같은 방식으로 검증한 뒤 사용자 승인으로 일반 파일 origin을 세 개에서 네 개로 보완했다. `HWP_EASY_FILE_ORIGINS`만 변경한 환경 revision 7을 기존 비공개 버전 45에 적용했고 코드·바인딩·스키마·접근 범위를 유지했다. 실제 400,000단위 합성 파일 가져오기와 400,001단위 한도 거부를 확인했다. 성공 응답은 origin을 반환하지 않아 새 주소의 실제 사용 여부와 모든 호스트 지원을 인증한 결과는 아니다. 합성 전용 설정은 별도로 열지 않았다.

관찰된 주소 자체나 인증서만으로 파일의 소유권을 인증하는 것은 아니며, 호출자가 명시적으로 전달한 파일만 가져온다. 와일드카드·리디렉션·사용자 자격 전달은 허용하지 않는다. 아직 관찰하지 않은 호스트로 전달되면 거부한다. 새 주소를 추측해 자동 허용하거나 이를 재인증 오류로 설명하지 않는다. 구체적인 세션 주소·문서 ID·배포 이력은 ignored 로컬 기록에만 둔다.

이 경로는 한글 설치 없는 HWP 5.x의 현재 지원 범위와 4 MiB 입력 한도를 그대로 적용한다. 업로드는 Codex 파일 전달 경로와 Sites 처리·D1/R2 보관으로 이어지며 PC 원본을 갱신하지 않는다. 업로드 문서와 이전 버전은 직접 삭제할 때까지 보관한다. `testdocs/`의 개인 문서를 시험 목적으로 임의 업로드하지 않았으며, 사용자 문서를 사용하려면 사용자가 선택한 파일과 작업 범위를 따른다. 서버의 포괄적인 native UI·Cloud·Dots·배치·운영 완료 플래그는 계속 거짓이다.

## 저장된 HWP의 직접 결과 반환

`hwp_download`의 기본 및 `delivery: link` 응답은 기존 보호된 브라우저 링크다. 에이전트가 파일 바이트를 회수해야 할 때 명시적으로 `delivery: embedded`를 선택하면, 인증 사용자·문서·불변 버전을 확인한 저장 HWP를 [MCP embedded resource](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/schema.mdx)의 `application/x-hwp`·base64 blob으로 반환한다. 바이너리는 별도 content block에만 두고 텍스트와 structuredContent에는 복제하지 않는다. 해당 resource URI는 식별자이며 공개 다운로드 주소나 재조회 API가 아니다.

전체 `embedded` 반환 한도는 **256 KiB**다. 더 큰 파일의 전체 반환은 `DOCUMENT_EMBEDDED_OUTPUT_LIMIT_EXCEEDED`로 거부한다. 기존 링크 또는 아래 명시적 조각 회수를 사용한다. 일부 파일이나 잘린 base64를 완성된 HWP처럼 반환하지 않는다. 조회된 바이트의 저장 해시와 엔진 재열기를 확인하고, 인코딩 뒤에도 삭제 상태와 선택 버전을 다시 확인한다. 이 마지막 확인 이후 또는 이미 받은 바이트를 회수할 수 있다는 뜻은 아니다. 읽기 작업으로 버전·blob·PC 파일을 변경하지 않는다.

`embedded_hwp_download_available`와 `max_embedded_hwp_bytes`는 서버의 경로·한도다. 실제 앱의 다운로드 버튼, 로컬 자동 저장, Cloud/Dots 호환과 서식 정확성 완료 플래그는 계속 별개다. 새 선택 인수가 클라이언트에 보이지 않으면 기존 연결의 도구 정보를 새로 고쳐야 할 수 있으며, 이를 자동으로 재인증 오류라고 설명하지 않는다.

고정 `hwp_workflow_probe`는 이 일반 저장 버전 반환 경로를 시험하고 자기 합성 결과만 resource로 돌려준다. 임시 문서는 정리하지만 이미 반환한 바이트는 읽을 수 있다. 개발용 `scripts/save-workflow-result.mjs`는 숨긴 stdin으로 이 고정 합성 응답만 받아 별도 실행에서 같은 편집을 재현하고 전체 바이트가 일치할 때 새 ignored 합성 HWP를 만든다. 일반 사용자용 CLI나 개인 문서 저장기가 아니며 임의 파일·출력 경로·덮어쓰기를 허용하지 않는다.

현재·이전 버전의 전체 바이트 일치, 타인·삭제된 문서의 거부, 출력 한도와 해시 불일치, 생성 중 삭제, 저장소 불변, 합성 결과의 로컬 재열기와 잘못된 결과의 무출력을 시험한다. actual workerd/D1/R2의 모의 신원 검사와 실제 native MCP 바이트 수신은 각각 구분해 기록한다.

### 큰 HWP의 버전 고정 조각 회수

Cloud의 작은 고정 합성 파일 왕복에는 [합성 전용 client 회수 도구](../probes/sites-runtime/scripts/save-chunk-result.mjs)와 [실행 절차](cloud-client-check.md)를 사용할 수 있다. 이 개발 helper는 알려진 합성 원본/편집본만 받아 실제 재열기와 독립 바이트 재현 뒤 새 로컬 HWP로 게시한다. 임의 개인 문서 저장이나 실제 Cloud·앱 첨부 UI 인증을 수행하는 기능은 아니다.

`hwp_download`에 `delivery: chunk`, 기존 `document_id`·`version_id`, 조회된 전체 `expected_sha256`, `offset: 0`을 지정한다. 선택 `max_bytes`는 1,024~65,536바이트이며 기본 65,536이다. 마지막 조각은 더 짧을 수 있다. 선택 버전의 전체 바이트는 기존 저장 한도인 4 MiB 이하여야 한다. 매 호출은 인증·저장 해시·전체 HWP 재열기와 반환 전 삭제 상태를 확인한다. 기대 해시가 다르면 `VERSION_CONFLICT`, 파일 끝 이후의 offset은 `INVALID_DOWNLOAD_CHUNK`다. 조각 인수는 기본 링크·전체 embedded 모드에 섞어 보내지 않는다.

텍스트/structuredContent에는 전체 크기·해시, 조각 offset·크기·해시와 `next_offset`, `transfer_complete`를 반환한다. 실제 base64는 별도 `application/octet-stream` resource에만 있다. `chunk_is_complete_hwp: false`이며 마지막 조각의 `transfer_complete: true`도 클라이언트가 앞 조각을 모두 받아 검증했다는 인증이 아니다. `.bin` resource 식별자는 공개 URL·재조회 API·HWP 첨부가 아니다.

클라이언트는 처음 선택한 문서·버전·전체 해시·크기를 고정하고 `next_offset`을 끝까지 따라간다. 현재 버전이 다른 작업으로 갱신돼도 처음의 불변 버전을 계속 사용하고 최신 버전과 섞지 않는다. [참조 재조립 라이브러리](../probes/sites-runtime/host/document-chunks.mjs)의 `createHwpChunkCollector`는 파일/네트워크 접근 없이 bounded 메모리만 사용한다. 정확한 직전 조각 재시도는 허용하지만 다른 문서·버전·크기·해시, 누락·중복 범위·순서 변경·손상/비정규 base64는 거부하며 실패 뒤 조회 위치를 진행시키지 않는다. `finalize`는 모든 바이트, 전체 SHA-256 및 필수 독립 엔진 재열기를 확인한 후에만 완성 바이트를 반환한다. 개인 원본 덮어쓰기나 로컬 자동 저장은 수행하지 않는다. 서버를 넘어간 조각의 회수·삭제는 보장할 수 없고 클라이언트의 임시 바이트 정리와 저장 권한은 별도 책임이다.

actual workerd/D1/R2의 모의 신원으로 376,832바이트 합성 HWP의 6조각 회수·재시도·전체 바이트 일치·실제 엔진 재열기와 이전 버전 회수를 시험한다. 잘못된 조각·불완전 재조립·타인/삭제 접근·생성 중 삭제 거부 및 조회 후 저장소 불변도 검사한다. `hwp_workflow_probe`의 **명시적** `diagnostic: large_chunks`만 같은 일반 도구와 라이브러리로 큰 고정 합성 문서를 서버 내부에서 회수·재열기하고 자기 생성 범위만 정리한다. 기본 무인수 검사는 기존 작은 합성 문서만 사용한다. `server_chunk_workflow_verified`와 `server_chunk_count`는 서버 내부 검사이며 **클라이언트 조각 전송/재조립 완료가 아니다**. `chunked_hwp_download_available`, `max_hwp_chunk_bytes`, `max_chunked_hwp_bytes`도 서버 기능과 한도다. 갱신된 Desktop native 도구로 작은 고정 합성 원본/편집본의 실제 조각 회수와 client helper 재조립·독립 바이트 일치를 확인했다. 도구 스키마가 갱신되지 않은 기존 대화의 일반 chunk 호출, 앱 첨부 UI·Dots 파일 왕복·시각 배치는 별도 미검증이며 포괄적인 `client_chunk_reassembly_verified`는 거짓이다.

실제 native MCP에서 확장 합성 검사가 응답 시간 초과로 끝난 사례가 있어 큰 검사를 기본 연결 검사에 묶지 않는다. 시간 초과는 재인증 요구나 서버 작업 취소·정리 완료의 근거가 아니며, 같은 무거운 진단을 자동 재시도하거나 서비스 자격으로 우회하지 않는다. 생성 범위의 정리는 정상 반환에서 확인하고, 시간 초과한 실행의 정리 상태는 확인 불가로 남긴다. 실제 클라이언트별 시간·메모리·전송 한도는 별도 실증이 필요하다.

## 고정 합성 파일 전달 진단

일반 업로드를 켜지 않고 실제 클라이언트 전송을 단계별로 시험하기 위한 개발용 예외다. `hwp_transfer_probe`에는 **오직** `scripts/make-transfer-fixture.mjs`가 새로 만든 개인정보 없는 합성 파일을 전달한다. 일반 사용자에게 CLI 실행을 요구하는 제품 기능이 아니다. 서버가 고정한 13,312바이트와 SHA-256이 모두 일치해야 하며, 파일 이름·MIME·클라이언트가 제시한 해시는 허가 근거가 아니다. [구현](../probes/sites-runtime/host/synthetic-transfer.mjs)

별도 `HWP_EASY_SYNTHETIC_FILE_ORIGINS`가 없거나 유효하지 않으면 `file_host_confirmation_required`를 반환한다. 이때 공개 HTTPS origin만 반환하고 임시 URL의 경로·query·file ID·파일 이름은 반환하거나 저장하지 않는다. 네트워크 요청·바이트 수신·DB/R2 저장도 없다. 응답의 `candidate_file_origin`은 신뢰되지 않은 descriptor의 관찰값이며, 그 자체를 근거로 자동 허용하지 않는다. 실제 전달 호스트를 확인한 뒤 정확한 origin만 별도로 구성한다. 일반 업로드의 allowlist와 플래그는 이 설정과 독립이다.

별도 호스트가 설정되면 인증한 사용자 범위에서 최대 13,312바이트를 수신하고 서버 지문을 검사한다. 리디렉션·다른 호스트·크기 초과·변조·다른 파일은 저장 전에 거부한다. **잘못 선택한 파일은 최대 한도까지 서버 메모리에 도달한 뒤 거부될 수 있다.** 지문 검사가 개인정보 전송 자체를 방지하는 장치는 아니므로 테스트 파일만 명시적으로 선택한다. 지문이 맞으면 기존 조회·편집·같은 문서 저장·재열기·복구 시험과 생성 근거 기반 정리를 수행한다. 기존 사용자 문서는 건드리지 않는다.

편집한 합성 HWP는 MCP의 embedded resource(`application/x-hwp`, base64 blob)로 반환해 임시 시험 문서 정리 후에도 바이트를 회수할 수 있도록 했다. 이것은 공개 URL, 개인 문서의 보관 정책 변경이나 모든 클라이언트가 다운로드 버튼을 제공한다는 약속이 아니다. `native_download_artifact_verified`는 계속 `false`다. 개발용 `scripts/save-transfer-result.mjs`는 수신 결과의 HWP를 로컬에서 독립적으로 재현한 고정 편집 바이트와 완전히 비교한 뒤 새 ignored 합성 산출물로만 저장한다. 임의 경로·원본·개인 HWP를 받거나 기존 파일을 덮어쓰지 않는다.

로컬 actual workerd/D1/R2의 7개 전달·실패 시나리오와 결과 파일 재현·재열기 검사가 통과했다. 네트워크와 신원은 모의이며 실제 클라이언트의 첨부·MCP 바이너리 전달·다운로드 UI 완료로 집계하지 않는다.

별도로 실제 로컬 Codex native 호출에서는 고정 합성 입력 13,312바이트의 서버 수신·지문 검증과 문단/셀 편집·저장·재열기·복구·정리를 통과했다. 응답의 embedded HWP resource를 로컬 파일로 회수했고, 별도 로컬 실행에서 재현한 편집 결과와 바이트 전체가 일치했다. 이 실증은 모의 네트워크 시험과 구분하며, 일반 문서·다운로드 UI·다른 클라이언트의 완료를 뜻하지 않는다. 전달 호스트는 호출마다 달라질 수 있었다. 실제 관찰한 정확한 origin의 공개 DNS와 유효한 TLS 호스트 인증을 확인한 후 합성 시험에만 잠시 설정했고, 종료 후 제거했다. 일반 업로드와 일반 파일 origin은 계속 비활성화 상태다.

## 고정 합성 브라우저 다운로드

`GET /diagnostics/download`는 고정 합성 결과만 내려받는 개발용 화면이고, `GET /diagnostics/synthetic-result.hwp`는 해당 바이너리를 제공한다. 두 경로 모두 Sites의 실제 사용자 ID·이메일 헤더를 요구한다. 서비스 자격만으로 신원을 대체하지 않는다. [구현](../probes/sites-runtime/host/synthetic-download.mjs)

입력 경로·문서 ID·업로드·query·Range는 받지 않고, GET 이외 방법을 거부한다. 기존 고정 fixture를 메모리에서 생성해 문단·셀 편집, 내용·레코드 보존 및 재열기를 검사한다. 결과는 정확히 13,312바이트와 SHA-256 `1d3f1472a2637a5fed2672109de946843acd07034756a4273b7fcd43ef159286`이어야 한다. 다르면 다운로드를 거부한다. D1/R2 읽기·쓰기나 외부 파일 fetch는 없고, 일반 업로드와 MCP 도구 계약도 변경하지 않는다. attachment·private no-store·nosniff·수동 콘텐츠 제한 헤더를 제공한다.

단위 검사 6개와 실제 workerd/WASM 검사는 익명·부분 신원, 잘못된 인수·방법, 변조 출력·생성 실패의 거부와 고정 바이트 재현을 통과했다. workerd 검사는 저장소 binding과 외부 네트워크 없이 실행하며 신원은 모의다. 별도로 실제 Chrome에서 사이트 로그인 → 버튼 클릭 → 로컬 HWP 다운로드를 완료했다. 수신 파일은 이전 native MCP 합성 편집 결과와 바이트 전체가 일치했다.

이것은 고정 결과의 인증된 브라우저 전송 실증이다. `/documents/{document_id}/versions/{version_id}.hwp`의 저장된 사용자 문서 다운로드, 에이전트 앱의 파일 UI, 다른 OAuth 사용자의 격리, Cloud/Dots와 시각 배치를 인증하지 않는다. 고정 workflow가 정리한 문서의 삭제를 늦추거나 일반 사용자 문서의 보관 정책을 변경하지 않는다.

## 브라우저에서 HWP 업로드

`GET /documents/upload`는 로그인한 사용자가 직접 HWP를 선택해 기존 `POST /documents/import`로 전송하는 화면이다. 업로드 설정이 꺼져 있으면 파일 선택과 전송을 제공하지 않는다. 파일을 선택하거나 화면을 여는 것만으로는 저장하지 않는다. 사용자가 업로드 버튼을 누르면 HWP 검사를 거친 원본 바이트를 새 원격 문서로 보관하고, 응답의 검증된 문서·버전 ID로 해당 보기 화면을 연다. PC 원본은 갱신하지 않으며 원격 문서는 직접 삭제할 때까지 보관한다.

클라이언트는 비어 있거나 4 MiB를 넘는 파일, `.hwp`가 아닌 이름을 전송 전에 거부한다. 서버의 인증·동일 origin·요청 UUID·본문 크기·실제 HWP 검사는 그대로 유지한다. 고정 JavaScript는 인증한 같은 origin에서만 제공하며 업로드 화면의 전송에는 `script-src 'self'`와 `connect-src 'self'`를 허용한다. 보기 화면의 복사 클라이언트는 `script-src 'self'`, `connect-src 'none'`이며 문서 SVG는 별도 수동 이미지·sandbox 응답으로 유지한다.

### 에이전트에게 저장본 전달

보기 화면의 **링크와 읽기 요청 복사**는 사용자가 누를 때만 클립보드에 선택한 저장본의 보기 링크·문서 ID·버전 ID와 읽기 전용 요청을 복사한다. 구성한 서비스 origin과 검증된 UUID로 링크를 만들며 미리보기 페이지 query, 인증 정보·본문·파일 이름을 넣지 않는다. 이전 버전에서 복사해도 현재 버전으로 바꾸지 않는다. 읽기 요청만으로 저장·복구·삭제하지 않으며 사용자가 수정 작업을 따로 요청한다.

복사가 거부되거나 지원되지 않거나 4초 안에 끝나지 않으면 요청을 펼치고 텍스트를 선택해 직접 복사하도록 안내한다. JavaScript가 없으면 직접 복사를 제공한다. 고정 `/documents/handoff-client.js`는 인증된 GET만 허용하고 query·Range를 받지 않으며 문서별 데이터가 없다. 이 클라이언트는 네트워크·원격 저장·로컬 파일·브라우저 저장소를 사용하지 않는다. 복사 기능 추가를 에이전트 요약 품질이나 일반 양식 지원 완료로 집계하지 않는다.

진행 중에는 선택·전송을 잠그고 30초 후 응답 확인을 중단한다. 연결 실패나 저장 결과 미확정 때 같은 화면의 재시도는 같은 File 바이트와 요청 UUID를 유지한다. 실제 저장 후 응답이 유실되는 경우도 한 문서만 생성함을 compiled workerd/D1/R2/WASM과 모의 DOM으로 검사한다. 화면 새로고침·다른 파일 선택 뒤의 요청 복구는 구현하지 않았으므로 그 경로까지 중복 방지를 보장하지 않는다. 자동 업로드·자동 재시도·문서 수정·삭제는 수행하지 않는다. 실제 OAuth 브라우저 조작과 일반 개인 문서·시각 배치는 별도 검증 범위다.

## 저장된 버전의 보기 화면

`GET /documents/{document_id}/versions/{version_id}/view`는 실제 D1/R2의 선택 버전을 사용자 소유권으로 조회하는 읽기 전용 화면이다. `page`는 0부터 시작하는 단일 정수 query이고, 중복·다른 query와 잘못된 값을 거부한다. 다운로드와 SVG 링크는 모두 그 불변 버전에 묶고, 현재 저장본 여부는 저장소의 명시적 `current_version`으로 표시한다. 이전 저장본을 열어도 복구나 편집을 실행하지 않는다. [구현](../probes/sites-runtime/host/document-viewer.mjs)

화면은 선택한 저장본의 상태와 저장 시각을 한국 시간으로 보여주고, 이전 저장본에서는 현재 저장본으로 이동하는 링크를 제공한다. 버전 목록은 현재 저장본을 먼저 표시하고 나머지는 저장 시각 내림차순으로 정렬한다. 같은 시각의 저장본은 ID를 함께 보여 구분하며, 시각 순서를 실제 편집·복구 순번으로 해석하지 않는다. 문서·버전 ID, 파일 크기와 전체 해시는 접힌 파일 정보에서 확인한다. 저장 이유를 기록하지 않는 현재 스키마에서 가져오기·편집·복구라는 이름을 추측하지 않는다.

HWP 다운로드는 기존 보호된 바이너리 경로를 사용한다. SVG는 기존 수동 이미지 경로를 `img`로 표시하고 문서 SVG를 HTML에 직접 삽입하지 않는다. 스크립트·외부 이미지·frame을 제한하고 응답은 private no-store다. 미리보기 실패·크기 한도 초과 때도 다운로드 링크와 별도의 경고를 유지한다. 글꼴·배치 정확성은 미검증이다.

`/diagnostics/stored-document`는 일반 업로드와 별도의 합성 시험 진입점이다. GET은 생성 없이 버튼만 보여준다. 명시적인 POST에는 동일 origin, 제한된 form 본문, 요청 UUID와 고정 생성 확인을 요구한다. 서버가 고정한 합성 편집 HWP 한 개만 저장하며, 개인 파일·바이트·경로·문서·소유자 인수를 받지 않는다. 동일 요청 재시도는 같은 문서를 반환한다. 생성한 문서는 직접 삭제할 때까지 보관하고, 실패 후 새 요청으로 맹목적으로 반복 생성하지 않는다. 일반 업로드·파일 호스트 설정·기존 자동 정리 workflow는 변경하지 않는다. [합성 생성 경로](../probes/sites-runtime/host/stored-synthetic.mjs)

시험 생성 GET에만 `Referrer-Policy: same-origin`을 사용한다. `no-referrer`에서는 기본 HTML form POST의 `Origin`이 `null`이 되어 엄격한 출처 검사를 통과하지 못한다. 외부 사이트에는 referrer를 보내지 않고, 문서 보기·바이너리·SVG의 기존 정책은 유지한다. `null`·누락·다른 origin은 계속 거부한다. [브라우저의 Origin 처리](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy#effect_on_the_origin_header)

254개 Node 회귀와 실제 workerd/D1/R2/WASM 검사를 통과했다. 새 6개 단위 검사와 저장 버전 통합 검사는 신원·CSRF·변조 인수 거부, 중복 생성 방지, 선택 버전의 읽기 불변, MCP 편집·링크와 이전 버전 보존, Worker 재시작 후 유지, 명시적 삭제 뒤 화면·HWP·SVG 접근 차단을 확인했다. 이 검사의 신원은 모의이며 실제 두 OAuth 사용자 인증이 아니다.

별도로 실제 로그인 Chrome의 명시적 버튼으로 고정 합성 HWP 한 개를 저장했다. 같은 사용자의 Codex Desktop native MCP에서 해당 저장 버전을 읽고 문단·표 셀을 수정해 같은 원격 문서에 새 버전을 저장했다. MCP가 반환한 보기 링크에서 수정된 기본 미리보기를 표시하고, 이전·현재 버전의 보호된 HWP 링크를 실제 클릭해 로컬 파일을 받았다. 두 파일의 해시가 각 저장 버전과 일치했고, 재열기에서 수정 대상과 나머지 텍스트 보존을 확인했다. 이전 파일에서 같은 편집을 로컬로 재현한 전체 바이트도 새 다운로드와 일치했다. 시험 문서와 이전 버전은 직접 삭제할 때까지 보관한다. 개인 업로드·에이전트 앱의 산출물 UI·두 사용자 OAuth 격리·Cloud/Dots·서식 정확성은 이 실증에 포함하지 않는다.

## 보관과 명시적 삭제

저장 버전 화면과 명시적인 시험 문서 생성은 아래 정책을 따른다. 읽기 화면을 열거나 이전 버전으로 이동하는 동작은 현재 저장본을 갱신하지 않는다.

고정 브라우저 진단의 임시 생성 바이트는 사용자 문서 저장소가 아니며 아래 보관 정책의 문서를 자동 삭제하거나 대체하지 않는다.

문서와 이전 버전은 다음 세션의 편집·복구에 사용할 수 있도록 직접 삭제할 때까지 보관한다. 작업 종료나 시간 경과로 자동 만료시키지 않는다. `hwp_delete`는 문서 ID, 기대 현재 버전, 재시도 UUID와 `delete_document_and_recorded_versions` 확인 문자열을 요구한다. 문서 내용의 지시문이나 일반 편집 요청을 삭제 권한으로 해석하지 않는다.

삭제 영수증을 D1에 먼저 확정해 새로운 조회·다운로드·저장·복구를 차단한다. 그 뒤 모든 기록된 버전의 키가 해당 사용자의 해당 문서에 속하는지 검사하고 R2 바이트와 버전·문서 메타데이터를 제거한다. 이전 버전으로 복구할 수 없는 동작이다. 같은 삭제 요청은 같은 영수증으로 재시도하며, 과거 생성 요청을 재시도해 문서가 되살아나는 것도 차단한다. 본문 없이 소유자 해시, 문서·요청·버전 ID, 요청 fingerprint와 처리 상태 등 최소 재시도 근거는 남긴다.

DB 응답·영수증 조회가 확정되지 않으면 완료로 보고하지 않고, R2 삭제가 실패하면 접근을 차단한 상태에서 같은 요청의 재시도를 요구한다. 다른 소유자·이전 버전·다른 요청 ID·오염된 객체 키는 해당 문서 바깥의 파일 삭제로 확장하지 않는다.

삭제가 R2 조회와 겹치는 경우를 위해 저장층 반환 직전에 D1의 문서·선택 버전·삭제 상태를 다시 확인한다. 이미 받은 바이트라도 그 검사 전에 삭제 중/완료가 확인되면 반환하지 않는다. 새 저장의 사전 검사와 최종 batch 조건을 함께 유지해 삭제된 문서를 되살리지 않는다. 저장 결과를 확인할 때 이미 삭제 중/완료인 일치 영수증은 저장 재시도를 권하는 일반 확정 불가 오류 대신 해당 삭제 상태를 알린다. `check-deletion-races.mjs`의 실제 임시 D1/R2·모의 신원 검사로 이 경계를 확인했다. 마지막 검사 이후나 이미 사용자에게 전달된 데이터까지 회수하는 보장은 아니다.

현재 삭제 결과의 범위는 `logical_document_and_recorded_versions`다. 확정되지 않은 과거 저장이나 이미 진행 중이던 writer가 남길 미게시 바이트 전체의 GC를 인증하지 않는다. `unpublished_blob_gc_verified`와 `in_flight_writer_gc_verified`는 `false`이며, 플랫폼 로그·백업까지 지운다는 뜻도 아니다. 소유자 전용 파일 가져오기를 열어도 이 한계를 운영 개인정보 삭제 완료로 소개하지 않는다.

`check-deletion.mjs`의 8개 실제 로컬 workerd D1/R2 검사에서는 소유자·버전·요청 충돌, 삭제 재시도, 접근 철회, 생성 요청 재시도의 부활 차단, R2 실패 후 재개, 시작·종료 DB 응답 유실, 영수증 조회 실패, 오염된 키와 동시 동일 요청을 시험한다. 다운로드 철회는 별도 호스트 검사에 포함한다. 모의 신원과 주입한 장애를 실제 OAuth 두 사용자나 운영 GC 인증으로 집계하지 않는다. `0001` migration은 새 삭제 영수증 테이블만 추가하며 기존 적용 migration은 변경하지 않았다.

## 검증한 범위와 남은 작업

`node scripts/check-host.mjs`는 실제 workerd와 D1/R2에서 바이너리 입력부터 재열기까지 시험한다. 같은 요청 재시도, 오래된 저장 거부, 모의 두 소유자 사이의 접근 거부, 보호된 SVG, 복구와 합성 문서 정리를 확인한다. `fileParams`의 네트워크 응답은 모의이며 실제 OAuth나 첨부 성공으로 집계하지 않는다.

원격 `hwp_workflow_probe`는 개인 파일 없이 동일 서비스 계약을 호출한다. 반환하는 바이너리와 SVG 검사는 서버 내부의 소유자 범위 handler 호출이다. 실제 외부 HTTP 다운로드, 네이티브 파일 첨부, 두 OAuth 사용자, Codex Cloud와 Dots는 각각 미검증 플래그로 남긴다. 진단이 만든 무작위 문서 ID 아래 데이터만 정리하고 기존 사용자 문서는 지우지 않는다.

합성 진단은 첫 저장 전에 생성할 문서 ID를 내부 준비 handle로 확보한다. 따라서 첫 DB 저장의 응답·영수증 조회가 유실돼도 그 시험의 정확한 범위를 정리할 수 있다. 이미 게시된 문서가 있으면 이번 시험의 생성 영수증을 먼저 확인한다. 소유·생성 근거를 읽지 못하거나 다른 문서의 키가 반환되면 정리를 멈추고 `SYNTHETIC_CLEANUP_FAILED`를 반환한다. 이는 일반 문서의 영구 삭제 기능이나 운영 정리 정책이 아니다. 일반 저장의 확정 불가 결과는 계속 보수적으로 보존한다.

`node scripts/check-host-failures.mjs`의 7개 실패 주입 사례와 스트림·도구 계약의 12개 단위 검사가 통과했다. 실제 로컬 D1/R2에서 첫 commit 전 실패, commit 응답과 영수증 조회 유실, blob 응답 및 첫 정리 실패, 읽기 실패와 잘못된 정리 근거를 시험했다. 모의 신원과 명시적 실패 주입을 실제 OAuth·운영 장애 인증으로 집계하지 않는다.

실제 사용자 연결의 고정 합성 진단, 로컬 Codex 파일 인수의 바이트 입력·embedded HWP 회수와 로그인 Chrome의 다운로드를 확인했다. 저장된 합성 문서의 브라우저 생성·native MCP 편집·미리보기·불변 버전의 외부 HTTP 다운로드도 위 제한된 범위에서 실증했다. 일반 파일, 에이전트 앱의 파일 UI·실제 OAuth 사용자 격리는 별도 미검증이다. 개별 재인증·배포 이력은 로컬 기록으로 분리하며 [현재 연결 상태](codex-cloud.md#현재-연결-검증-상태)를 참고한다.

개발용 `node scripts/make-transfer-fixture.mjs`는 고정 합성 HWP만 새 UUID 파일로 만들고 컨테이너·내용 검사를 수행한다. 입력·출력 경로 인수를 받지 않고 기존 파일을 덮어쓰지 않으며, 생성 파일은 저장소의 무시된 `outputs/synthetic-transfer/` 아래에 둔다. 메타데이터만 출력하고 네이티브 전송이나 배치 정확성을 인증하지 않는다. 일반 사용자 설치용 CLI가 아니다.

다음 검증은 에이전트 앱과 Cloud 결과 첨부 UI, 일반 사용자 파일의 입력·회수, 삭제·보관 정책, 실제 사용자 간 격리 및 권한 철회다. Dots는 MVP에서 제외한 추후 확장 항목이다. Cloud의 고정 합성 문서 native 왕복·보호된 링크 다운로드와 구분하며 [저장 계약](durable-storage.md), [클라이언트 완료 조건](codex-cloud.md), [MVP 진행 상태](mvp-status.md)를 함께 적용한다.

## 연결 오류를 다루는 순서

배포 버전 변경과 인증 실패를 같은 사건으로 취급하지 않는다. 기존 연결이 배포 뒤 유지된 사례와, 재배포·설정 변경 없이 인증이 실패한 사례가 모두 있다. 따라서 매 배포가 재인증을 요구한다거나 모든 배포가 인증에 무관하다고 단정하지 않는다.

공식 안내는 등록한 OAuth 클라이언트를 재사용하고 자격을 유효하게 유지하도록 요구하며, access/refresh token의 만료·회전을 소스 배포와 별도의 인증 수명 주기로 설명한다. 이 일반 계약은 HWP Easy의 `invalid_grant` 원인을 특정하지 않는다. Sites가 사용자 OAuth를 관리하므로 이 저장소에서 자체 refresh token을 보관하거나 갱신기를 추가하지 않는다. [OpenAI 플러그인 인증 안내](https://developers.openai.com/plugins/build/auth)

1. 기존 연결에서 읽기 전용 `hwp_capabilities`를 한 번 호출한다. 오류 코드와 완료 여부를 기록하고, 대기 상태만으로 HWP 작업 진행을 추정하지 않는다.
2. `UNAUTHORIZED` 또는 재인증 요청이면 문서 쓰기·합성 workflow 호출을 중단한다. 서비스 자격·임의 신원 헤더로 사용자 인증을 대신하거나 인증 게이트를 완화하지 않는다.
3. 읽기 전용 Sites 조회로 배포 버전, OAuth 클라이언트 ID, 플러그인 ID, MCP 주소·resource, 접근 정책 revision과 업로드 환경 revision의 변경 여부만 비교한다. 토큰·비밀·개인 문서 내용은 기록하지 않는다. Worker 로그에 원인이 없다는 사실도 모든 OAuth 계층의 정상 근거가 아니다.
4. 사용자가 기존 연결을 재인증하면 같은 클라이언트에서 기능 조회부터 재시도한다. 성공한 뒤에만 허용된 고정 합성 진단을 실행한다. Cloud와 Desktop 확인은 순서대로 수행하며, 이 순서 자체가 인증 오류의 해결책으로 입증됐다고 설명하지 않는다.
5. 재인증 직후 같은 오류가 다시 나오면 해당 클라이언트, 발생 시각, 안전한 오류 코드와 변경 여부만 남기고 사용자 또는 플랫폼의 추가 조치가 필요한 상태로 보고한다. 원인 확인 전에 토큰 만료·갱신 경쟁·앱 이름 변경·재배포 중 하나를 확정 원인으로 말하지 않는다.
