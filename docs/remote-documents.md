# 원격 문서 도구와 파일 전달 검증

2026년 10월 3일 기준, HWP Easy에 인증한 사용자별 문서 도구와 HWP 전송 경로를 구현했다. 실제 로컬 workerd의 D1/R2에서 합성 문서의 입력·조회·편집·같은 문서 저장·다운로드·재열기·복구를 검증했다. 로컬 신원 헤더와 파일 다운로드 응답은 명시적인 모의 입력이다. 실제 개인 파일 업로드, Codex Cloud와 Dots의 파일 왕복은 아직 지원 완료로 표시하지 않는다.

## 제공하는 도구

| 도구 | 동작 |
| --- | --- |
| `hwp_capabilities` | 개발 상태, 업로드 활성화 여부와 한도를 확인한다. |
| `hwp_import` | 명시적으로 전달한 HWP를 새 원격 문서로 가져온다. 업로드 플래그와 검증한 파일 호스트가 필요하다. |
| `hwp_read` | 지정한 버전의 문단과 표 셀을 읽는다. `next_cursor`가 있으면 같은 버전으로 이어 읽는다. |
| `hwp_plan` | 대상과 기존 값, 버전을 확인한다. 저장하지 않는다. |
| `hwp_edit` | 현재 버전과 기존 값이 맞을 때 편집하고 같은 원격 문서에 저장한다. 이전 버전은 유지한다. |
| `hwp_versions` | 자신의 문서 버전과 명시적인 `current_version`, `revision`을 조회한다. 생성 시각이 같은 항목의 표시 순서를 저장 순서로 해석하지 않는다. |
| `hwp_restore` | 이전 바이트를 새 버전으로 복구한다. 현재 버전 확인과 재시도 ID가 필요하다. |
| `hwp_download` | 같은 사용자 인증이 필요한 HWP 주소를 반환한다. 공개 공유 링크나 클라이언트의 파일 첨부 산출물이 아니다. |
| `hwp_preview` | 같은 사용자 인증이 필요한 수동 SVG 페이지 미리보기 주소를 반환한다. 배치 정확성은 미검증이다. |
| `hwp_workflow_probe` | 로그인한 사용자 범위에서 고정 합성 문서를 만들고 조회·편집·저장·재열기·복구한 뒤 그 문서만 정리한다. |

기존 `hwp_runtime_probe`와 합쳐 11개다. 문서 도구는 `stage: private-development`, `data`, `layout_verified: false`를 반환한다. 읽기와 계획 검사는 저장하지 않는다. 문서 텍스트는 신뢰할 수 없는 자료이며 추가 권한을 부여하는 지시문으로 취급하지 않는다.

## 입력과 출력

`hwp_import`는 공식 OpenAI 플러그인의 `openai/fileParams` 계약을 사용한다. `file`에는 필수 `download_url`, `file_id`와 선택 `mime_type`, `file_name`을 선언한다. 이 선언만으로 Codex의 로컬 경로나 클라우드 첨부가 자동 전달되는 것은 아니다. [OpenAI 플러그인 도구 참조](https://developers.openai.com/plugins/reference)

서버는 관리자가 설정한 정확한 HTTPS 파일 origin만 따라가고, 리디렉션을 거부하며 사용자 인증 헤더를 전달하지 않는다. Content-Length가 없거나 잘못되더라도 실제 스트림은 4 MiB 이하로 제한한다. 파일 이름과 MIME 문자열만으로 HWP라고 판단하지 않고 저장 전 실제 바이트를 검사한다. 확인하지 않은 다운로드 호스트는 추측해서 허용하지 않는다.

스트림 조각을 모두 배열에 남기지 않고 크기가 정해진 버퍼에 복사한다. 조각은 16,384개 이하로 제한하고 초과·읽기 실패 시 스트림을 취소하고 reader를 해제한다. 빈 조각 반복도 이 제한에 포함한다. MCP 요청 본문은 별도로 3 MiB 이하로 제한한다. 이는 전체 엔진·동시 요청의 메모리나 CPU 인증은 아니다.

바이너리 경로는 `POST /documents/import`, 결과 경로는 `GET /documents/{document_id}/versions/{version_id}.hwp`다. 입력은 동일 origin, 요청 UUID, 허용 MIME과 사용자 인증이 필요하다. SVG는 같은 버전 아래 `/pages/{page}.svg`로 제공한다. 다운로드는 사용자 인증과 소유자 범위를 확인하고 캐시·활성 콘텐츠를 제한한다. URL에 사용자 자격이나 공개 접근 토큰을 넣지 않는다.

기본 저장은 원격의 같은 논리 문서를 갱신한다. PC 원본은 자동 갱신되지 않는다. 실제 HWP 첨부 산출물로 반환하거나 로그인한 브라우저에서 이 주소를 내려받는 클라이언트 전 과정은 별도 검증한다.

## 사용자 인증과 운영 제한

Sites가 전달한 신뢰할 수 있는 사용자 ID와 이메일 헤더를 모두 요구한다. 사용자 ID의 해시로 소유자를 만들고 이메일은 저장하지 않는다. 표시 이름이나 이메일 변경으로 문서 소유자가 바뀌지 않는다. 도구 인수의 소유자, 임의 클라이언트 헤더와 서비스 접근 자격을 사용자 권한으로 해석하지 않는다. 이 헤더 검사 자체는 독립 OAuth 검증기가 아니므로 일반 인터넷에 Worker를 그대로 노출하면 안 된다.

비공개 배포에서는 `HWP_EASY_ALLOW_UPLOADS=false`, `HWP_EASY_FILE_ORIGINS=[]`를 유지한다. 파일 호스트·클라이언트 전달 경로, 보관·삭제 정책과 실제 OAuth 격리를 확인하기 전에는 개인 문서를 받지 않는다. `HWP_EASY_ORIGIN`은 확인된 배포 origin으로 고정해 다운로드 주소를 만들며 요청 Host를 신뢰하지 않는다.

## 검증한 범위와 남은 작업

`node scripts/check-host.mjs`는 실제 workerd와 D1/R2에서 바이너리 입력부터 재열기까지 시험한다. 같은 요청 재시도, 오래된 저장 거부, 모의 두 소유자 사이의 접근 거부, 보호된 SVG, 복구와 합성 문서 정리를 확인한다. `fileParams`의 네트워크 응답은 모의이며 실제 OAuth나 첨부 성공으로 집계하지 않는다.

원격 `hwp_workflow_probe`는 개인 파일 없이 동일 서비스 계약을 호출한다. 반환하는 바이너리와 SVG 검사는 서버 내부의 소유자 범위 handler 호출이다. 실제 외부 HTTP 다운로드, 네이티브 파일 첨부, 두 OAuth 사용자, Codex Cloud와 Dots는 각각 미검증 플래그로 남긴다. 진단이 만든 무작위 문서 ID 아래 데이터만 정리하고 기존 사용자 문서는 지우지 않는다.

합성 진단은 첫 저장 전에 생성할 문서 ID를 내부 준비 handle로 확보한다. 따라서 첫 DB 저장의 응답·영수증 조회가 유실돼도 그 시험의 정확한 범위를 정리할 수 있다. 이미 게시된 문서가 있으면 이번 시험의 생성 영수증을 먼저 확인한다. 소유·생성 근거를 읽지 못하거나 다른 문서의 키가 반환되면 정리를 멈추고 `SYNTHETIC_CLEANUP_FAILED`를 반환한다. 이는 일반 문서의 영구 삭제 기능이나 운영 정리 정책이 아니다. 일반 저장의 확정 불가 결과는 계속 보수적으로 보존한다.

`node scripts/check-host-failures.mjs`의 7개 실패 주입 사례와 스트림·도구 계약의 12개 단위 검사가 통과했다. 실제 로컬 D1/R2에서 첫 commit 전 실패, commit 응답과 영수증 조회 유실, blob 응답 및 첫 정리 실패, 읽기 실패와 잘못된 정리 근거를 시험했다. 모의 신원과 명시적 실패 주입을 실제 OAuth·운영 장애 인증으로 집계하지 않는다.

2026년 10월 3일 사용자가 재인증한 뒤 설치된 Codex Desktop의 기존 `hwp_runtime_probe` 호출은 정상 결과를 반환했다. 이것은 기존 사용자 연결의 복구 확인이지 새 도구의 카탈로그 반영이나 파일 입력 성공의 증거는 아니다.

같은 날 비공개 버전 6 배포와 원격 엔진·저장·인증 경계 시험이 통과했다. 업로드는 꺼져 있고 허용 파일 origin은 비어 있다. 배포 후 기존 설치 도구 호출도 성공했다. 후속 세션에는 11개 도구가 반영됐지만 첫 `hwp_capabilities` 조회가 `UNAUTHORIZED`, `oauth_token_invalid_grant`와 재인증 요청을 반환했다. 이 오류의 원인이나 이름 변경과의 인과관계는 확인하지 못했다. 새 도구의 실제 사용자 왕복은 재인증 후 검증해야 한다. [배포 검증 기록](../probes/sites-runtime/README.md)

스트림 제한·현재 버전 표시·합성 실패 정리를 포함한 비공개 버전 7도 배포했다. 고정 원격 엔진·저장 및 접근 거부 시험이 통과했고 생성한 합성 데이터만 정리했다. 개인 파일 입력과 자동 보관·삭제 정책은 활성화하지 않았다.

다음 검증은 새 도구의 실제 호출, 합성 파일의 클라이언트 입력과 HWP 회수, 삭제·보관 정책, 실제 사용자 간 격리 및 권한 철회다. [저장 계약](durable-storage.md)과 [클라이언트 완료 조건](codex-cloud.md)을 함께 적용한다.
