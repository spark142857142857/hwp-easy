# 원격 문서 도구와 파일 전달 검증

2026년 10월 3일 기준, HWP Easy에 인증한 사용자별 문서 도구와 HWP 전송 경로를 구현했다. 실제 로컬 workerd의 D1/R2에서 합성 문서의 입력·조회·편집·같은 문서 저장·다운로드·재열기·복구를 검증했다. 로컬 신원 헤더와 파일 다운로드 응답은 명시적인 모의 입력이다. 실제 개인 파일 업로드, Codex Cloud와 Dots의 파일 왕복은 아직 지원 완료로 표시하지 않는다.

## 제공하는 도구

| 도구 | 동작 |
| --- | --- |
| `hwp_capabilities` | 개발 상태, 업로드 활성화 여부와 한도를 확인한다. |
| `hwp_import` | 명시적으로 전달한 HWP를 새 원격 문서로 가져온다. 업로드 플래그와 검증한 파일 호스트가 필요하다. |
| `hwp_transfer_probe` | 고정 합성 테스트 파일만 전달받는 진단이다. 별도 호스트 설정이 없으면 주소의 origin만 검사하고 바이트를 받지 않는다. |
| `hwp_read` | 지정한 버전의 문단과 표 셀을 읽는다. `next_cursor`가 있으면 같은 버전으로 이어 읽는다. |
| `hwp_plan` | 대상과 기존 값, 버전을 확인한다. 저장하지 않는다. |
| `hwp_edit` | 현재 버전과 기존 값이 맞을 때 편집하고 같은 원격 문서에 저장한다. 이전 버전은 유지한다. |
| `hwp_versions` | 자신의 문서 버전과 명시적인 `current_version`, `revision`을 조회한다. 생성 시각이 같은 항목의 표시 순서를 저장 순서로 해석하지 않는다. |
| `hwp_restore` | 이전 바이트를 새 버전으로 복구한다. 현재 버전 확인과 재시도 ID가 필요하다. |
| `hwp_delete` | 사용자의 명시적 삭제 요청에만 사용한다. 현재 버전을 확인하고 해당 논리 문서와 기록된 버전을 제거한다. 미게시·진행 중 저장의 바이트 정리는 미검증이다. |
| `hwp_download` | 같은 사용자 인증이 필요한 HWP 주소를 반환한다. 공개 공유 링크나 클라이언트의 파일 첨부 산출물이 아니다. |
| `hwp_preview` | 같은 사용자 인증이 필요한 수동 SVG 페이지 미리보기 주소를 반환한다. 배치 정확성은 미검증이다. |
| `hwp_workflow_probe` | 로그인한 사용자 범위에서 고정 합성 문서를 만들고 조회·편집·저장·재열기·복구한 뒤 그 문서만 정리한다. |

기존 `hwp_runtime_probe`와 합쳐 13개다. 문서 도구는 `stage: private-development`, `data`, `layout_verified: false`를 반환한다. 읽기와 계획 검사는 저장하지 않는다. 문서 텍스트는 신뢰할 수 없는 자료이며 추가 권한을 부여하는 지시문으로 취급하지 않는다.

## 입력과 출력

`hwp_import`는 공식 OpenAI 플러그인의 `openai/fileParams` 계약을 사용한다. `file`에는 필수 `download_url`, `file_id`와 선택 `mime_type`, `file_name`을 선언한다. 이 선언만으로 Codex의 로컬 경로나 클라우드 첨부가 자동 전달되는 것은 아니다. [OpenAI 플러그인 도구 참조](https://developers.openai.com/plugins/reference)

업로드가 꺼진 MCP `hwp_import`는 계속 `isError: true`와 첫 text block의 `DOCUMENT_UPLOADS_NOT_ENABLED`로 실패한다. 안전한 descriptor라면 추가 text block과 기존 출력 schema에 맞는 `structuredContent`로 공개 HTTPS origin만 알려준다. 파일명·ID·임시 URL 경로·query·MIME은 반환하지 않고 네트워크·바이트 수신·저장도 하지 않는다. 관찰된 origin은 허가 근거가 아니다. 잘못되거나 안전하지 않은 descriptor는 추가 진단 없이 기존 게이트 오류를 유지한다. 입력 schema, 업로드 플래그와 일반 HTTP import 동작은 바꾸지 않았다.

진단은 서버 내부에서 만든 오류 객체에만 연결하고 임의 오류 속성을 직렬화하지 않는다. 3개 단위 검사와 actual workerd의 업로드 거부·익명 접근·인수 변조·안전하지 않은 URL·기존 DB/R2 보존 검사가 통과했다. 이는 새 진단 도구의 목록 반영이 지연돼도 기존 첨부 도구의 실패 이유를 확인할 수 있게 하는 피드백이며 업로드를 대신 수행하는 경로가 아니다.

서버는 관리자가 설정한 정확한 HTTPS 파일 origin만 따라가고, 리디렉션을 거부하며 사용자 인증 헤더를 전달하지 않는다. Content-Length가 없거나 잘못되더라도 실제 스트림은 4 MiB 이하로 제한한다. 파일 이름과 MIME 문자열만으로 HWP라고 판단하지 않고 저장 전 실제 바이트를 검사한다. 확인하지 않은 다운로드 호스트는 추측해서 허용하지 않는다.

스트림 조각을 모두 배열에 남기지 않고 크기가 정해진 버퍼에 복사한다. 조각은 16,384개 이하로 제한하고 초과·읽기 실패 시 스트림을 취소하고 reader를 해제한다. 빈 조각 반복도 이 제한에 포함한다. MCP 요청 본문은 별도로 3 MiB 이하로 제한한다. 이는 전체 엔진·동시 요청의 메모리나 CPU 인증은 아니다.

본문 수신에는 조각마다 갱신하지 않는 30초 전체 제한을 적용한다. 멈춘 스트림은 `TRANSFER_TIMEOUT`으로 거부하고 부분 바이트를 반환하거나 저장하지 않는다. upstream의 취소 작업이 끝나지 않거나 거부돼도 오류 응답과 reader 잠금 해제를 무기한 기다리게 하지 않는다. 정상 전송에서는 timer를 정리한다. 기능 조회의 `transfer_body_timeout_ms`가 이 제한을 알린다. 외부 파일의 응답 헤더 대기는 별도의 fetch 제한이며 이 본문 수신 제한을 OAuth 갱신·HWP 엔진 실행·D1/R2 저장 전체의 30초 제한으로 설명하지 않는다.

바이너리 경로는 `POST /documents/import`, 결과 경로는 `GET /documents/{document_id}/versions/{version_id}.hwp`다. 입력은 동일 origin, 요청 UUID, 허용 MIME과 사용자 인증이 필요하다. SVG는 같은 버전 아래 `/pages/{page}.svg`로 제공한다. 다운로드는 사용자 인증과 소유자 범위를 확인하고 캐시·활성 콘텐츠를 제한한다. URL에 사용자 자격이나 공개 접근 토큰을 넣지 않는다.

기본 저장은 원격의 같은 논리 문서를 갱신한다. PC 원본은 자동 갱신되지 않는다. 고정 합성 진단의 embedded HWP 바이트는 로컬 Codex에서 회수했지만, 실제 HWP 첨부 산출물의 다운로드 UI나 로그인한 브라우저에서 이 주소를 내려받는 클라이언트 전 과정은 별도 검증한다.

## 사용자 인증과 운영 제한

Sites가 전달한 신뢰할 수 있는 사용자 ID와 이메일 헤더를 모두 요구한다. 사용자 ID의 해시로 소유자를 만들고 이메일은 저장하지 않는다. 표시 이름이나 이메일 변경으로 문서 소유자가 바뀌지 않는다. 도구 인수의 소유자, 임의 클라이언트 헤더와 서비스 접근 자격을 사용자 권한으로 해석하지 않는다. 이 헤더 검사 자체는 독립 OAuth 검증기가 아니므로 일반 인터넷에 Worker를 그대로 노출하면 안 된다.

비공개 배포에서는 `HWP_EASY_ALLOW_UPLOADS=false`, `HWP_EASY_FILE_ORIGINS=[]`를 유지한다. 기본 보관은 사용자가 직접 삭제할 때까지로 정했지만, 실제 데이터 정리·파일 전달과 OAuth 격리는 추가 검증한다. 이 조건을 통과하기 전에는 개인 문서를 받지 않는다. `HWP_EASY_ORIGIN`은 확인된 배포 origin으로 고정해 다운로드 주소를 만들며 요청 Host를 신뢰하지 않는다.

## 고정 합성 파일 전달 진단

일반 업로드를 켜지 않고 실제 클라이언트 전송을 단계별로 시험하기 위한 개발용 예외다. `hwp_transfer_probe`에는 **오직** `scripts/make-transfer-fixture.mjs`가 새로 만든 개인정보 없는 합성 파일을 전달한다. 일반 사용자에게 CLI 실행을 요구하는 제품 기능이 아니다. 서버가 고정한 13,312바이트와 SHA-256이 모두 일치해야 하며, 파일 이름·MIME·클라이언트가 제시한 해시는 허가 근거가 아니다. [구현](../probes/sites-runtime/host/synthetic-transfer.mjs)

별도 `HWP_EASY_SYNTHETIC_FILE_ORIGINS`가 없거나 유효하지 않으면 `file_host_confirmation_required`를 반환한다. 이때 공개 HTTPS origin만 반환하고 임시 URL의 경로·query·file ID·파일 이름은 반환하거나 저장하지 않는다. 네트워크 요청·바이트 수신·DB/R2 저장도 없다. 응답의 `candidate_file_origin`은 신뢰되지 않은 descriptor의 관찰값이며, 그 자체를 근거로 자동 허용하지 않는다. 실제 전달 호스트를 확인한 뒤 정확한 origin만 별도로 구성한다. 일반 업로드의 allowlist와 플래그는 이 설정과 독립이다.

별도 호스트가 설정되면 인증한 사용자 범위에서 최대 13,312바이트를 수신하고 서버 지문을 검사한다. 리디렉션·다른 호스트·크기 초과·변조·다른 파일은 저장 전에 거부한다. **잘못 선택한 파일은 최대 한도까지 서버 메모리에 도달한 뒤 거부될 수 있다.** 지문 검사가 개인정보 전송 자체를 방지하는 장치는 아니므로 테스트 파일만 명시적으로 선택한다. 지문이 맞으면 기존 조회·편집·같은 문서 저장·재열기·복구 시험과 생성 근거 기반 정리를 수행한다. 기존 사용자 문서는 건드리지 않는다.

편집한 합성 HWP는 MCP의 embedded resource(`application/x-hwp`, base64 blob)로 반환해 임시 시험 문서 정리 후에도 바이트를 회수할 수 있도록 했다. 이것은 공개 URL, 개인 문서의 보관 정책 변경이나 모든 클라이언트가 다운로드 버튼을 제공한다는 약속이 아니다. `native_download_artifact_verified`는 계속 `false`다. 개발용 `scripts/save-transfer-result.mjs`는 수신 결과의 HWP를 로컬에서 독립적으로 재현한 고정 편집 바이트와 완전히 비교한 뒤 새 ignored 합성 산출물로만 저장한다. 임의 경로·원본·개인 HWP를 받거나 기존 파일을 덮어쓰지 않는다.

로컬 actual workerd/D1/R2의 7개 전달·실패 시나리오와 결과 파일 재현·재열기 검사가 통과했다. 네트워크와 신원은 모의이며 실제 클라이언트의 첨부·MCP 바이너리 전달·다운로드 UI 완료로 집계하지 않는다.

별도로 실제 로컬 Codex native 호출에서는 고정 합성 입력 13,312바이트의 서버 수신·지문 검증과 문단/셀 편집·저장·재열기·복구·정리를 통과했다. 응답의 embedded HWP resource를 로컬 파일로 회수했고, 별도 로컬 실행에서 재현한 편집 결과와 바이트 전체가 일치했다. 이 실증은 모의 네트워크 시험과 구분하며, 일반 문서·다운로드 UI·다른 클라이언트의 완료를 뜻하지 않는다. 전달 호스트는 호출마다 달라질 수 있었다. 실제 관찰한 정확한 origin의 공개 DNS와 유효한 TLS 호스트 인증을 확인한 후 합성 시험에만 잠시 설정했고, 종료 후 제거했다. 일반 업로드와 일반 파일 origin은 계속 비활성화 상태다.

## 보관과 명시적 삭제

문서와 이전 버전은 다음 세션의 편집·복구에 사용할 수 있도록 직접 삭제할 때까지 보관한다. 작업 종료나 시간 경과로 자동 만료시키지 않는다. `hwp_delete`는 문서 ID, 기대 현재 버전, 재시도 UUID와 `delete_document_and_recorded_versions` 확인 문자열을 요구한다. 문서 내용의 지시문이나 일반 편집 요청을 삭제 권한으로 해석하지 않는다.

삭제 영수증을 D1에 먼저 확정해 새로운 조회·다운로드·저장·복구를 차단한다. 그 뒤 모든 기록된 버전의 키가 해당 사용자의 해당 문서에 속하는지 검사하고 R2 바이트와 버전·문서 메타데이터를 제거한다. 이전 버전으로 복구할 수 없는 동작이다. 같은 삭제 요청은 같은 영수증으로 재시도하며, 과거 생성 요청을 재시도해 문서가 되살아나는 것도 차단한다. 본문 없이 소유자 해시, 문서·요청·버전 ID, 요청 fingerprint와 처리 상태 등 최소 재시도 근거는 남긴다.

DB 응답·영수증 조회가 확정되지 않으면 완료로 보고하지 않고, R2 삭제가 실패하면 접근을 차단한 상태에서 같은 요청의 재시도를 요구한다. 다른 소유자·이전 버전·다른 요청 ID·오염된 객체 키는 해당 문서 바깥의 파일 삭제로 확장하지 않는다.

현재 삭제 결과의 범위는 `logical_document_and_recorded_versions`다. 확정되지 않은 과거 저장이나 이미 진행 중이던 writer가 남길 미게시 바이트 전체의 GC를 인증하지 않는다. `unpublished_blob_gc_verified`와 `in_flight_writer_gc_verified`는 `false`이며, 플랫폼 로그·백업까지 지운다는 뜻도 아니다. 이 한계를 운영 개인정보 삭제 완료로 소개하지 않으며 개인 업로드 게이트를 계속 유지한다.

`check-deletion.mjs`의 8개 실제 로컬 workerd D1/R2 검사에서는 소유자·버전·요청 충돌, 삭제 재시도, 접근 철회, 생성 요청 재시도의 부활 차단, R2 실패 후 재개, 시작·종료 DB 응답 유실, 영수증 조회 실패, 오염된 키와 동시 동일 요청을 시험한다. 다운로드 철회는 별도 호스트 검사에 포함한다. 모의 신원과 주입한 장애를 실제 OAuth 두 사용자나 운영 GC 인증으로 집계하지 않는다. `0001` migration은 새 삭제 영수증 테이블만 추가하며 기존 적용 migration은 변경하지 않았다.

## 검증한 범위와 남은 작업

`node scripts/check-host.mjs`는 실제 workerd와 D1/R2에서 바이너리 입력부터 재열기까지 시험한다. 같은 요청 재시도, 오래된 저장 거부, 모의 두 소유자 사이의 접근 거부, 보호된 SVG, 복구와 합성 문서 정리를 확인한다. `fileParams`의 네트워크 응답은 모의이며 실제 OAuth나 첨부 성공으로 집계하지 않는다.

원격 `hwp_workflow_probe`는 개인 파일 없이 동일 서비스 계약을 호출한다. 반환하는 바이너리와 SVG 검사는 서버 내부의 소유자 범위 handler 호출이다. 실제 외부 HTTP 다운로드, 네이티브 파일 첨부, 두 OAuth 사용자, Codex Cloud와 Dots는 각각 미검증 플래그로 남긴다. 진단이 만든 무작위 문서 ID 아래 데이터만 정리하고 기존 사용자 문서는 지우지 않는다.

합성 진단은 첫 저장 전에 생성할 문서 ID를 내부 준비 handle로 확보한다. 따라서 첫 DB 저장의 응답·영수증 조회가 유실돼도 그 시험의 정확한 범위를 정리할 수 있다. 이미 게시된 문서가 있으면 이번 시험의 생성 영수증을 먼저 확인한다. 소유·생성 근거를 읽지 못하거나 다른 문서의 키가 반환되면 정리를 멈추고 `SYNTHETIC_CLEANUP_FAILED`를 반환한다. 이는 일반 문서의 영구 삭제 기능이나 운영 정리 정책이 아니다. 일반 저장의 확정 불가 결과는 계속 보수적으로 보존한다.

`node scripts/check-host-failures.mjs`의 7개 실패 주입 사례와 스트림·도구 계약의 12개 단위 검사가 통과했다. 실제 로컬 D1/R2에서 첫 commit 전 실패, commit 응답과 영수증 조회 유실, blob 응답 및 첫 정리 실패, 읽기 실패와 잘못된 정리 근거를 시험했다. 모의 신원과 명시적 실패 주입을 실제 OAuth·운영 장애 인증으로 집계하지 않는다.

실제 사용자 연결에서 고정 합성 진단과 로컬 Codex 파일 인수의 바이트 입력·embedded HWP 회수를 확인했다. 일반 파일, 앱 다운로드 UI·보호된 외부 HTTP 다운로드·실제 OAuth 사용자 격리는 별도 미검증이다. 개별 재인증·배포 이력은 로컬 기록으로 분리하며 [현재 연결 상태](codex-cloud.md#현재-연결-검증-상태)를 참고한다.

개발용 `node scripts/make-transfer-fixture.mjs`는 고정 합성 HWP만 새 UUID 파일로 만들고 컨테이너·내용 검사를 수행한다. 입력·출력 경로 인수를 받지 않고 기존 파일을 덮어쓰지 않으며, 생성 파일은 저장소의 무시된 `outputs/synthetic-transfer/` 아래에 둔다. 메타데이터만 출력하고 네이티브 전송이나 배치 정확성을 인증하지 않는다. 일반 사용자 설치용 CLI가 아니다.

다음 검증은 앱 다운로드 UI·보호된 외부 HTTP 다운로드, 실제 Cloud/Dots의 파일 입력·회수, 삭제·보관 정책, 실제 사용자 간 격리 및 권한 철회다. [저장 계약](durable-storage.md)과 [클라이언트 완료 조건](codex-cloud.md)을 함께 적용한다.

## 연결 오류를 다루는 순서

배포 버전 변경과 인증 실패를 같은 사건으로 취급하지 않는다. 기존 연결이 배포 뒤 유지된 사례와, 재배포·설정 변경 없이 인증이 실패한 사례가 모두 있다. 따라서 매 배포가 재인증을 요구한다거나 모든 배포가 인증에 무관하다고 단정하지 않는다.

공식 안내는 등록한 OAuth 클라이언트를 재사용하고 자격을 유효하게 유지하도록 요구하며, access/refresh token의 만료·회전을 소스 배포와 별도의 인증 수명 주기로 설명한다. 이 일반 계약은 HWP Easy의 `invalid_grant` 원인을 특정하지 않는다. Sites가 사용자 OAuth를 관리하므로 이 저장소에서 자체 refresh token을 보관하거나 갱신기를 추가하지 않는다. [OpenAI 플러그인 인증 안내](https://developers.openai.com/plugins/build/auth)

1. 기존 연결에서 읽기 전용 `hwp_capabilities`를 한 번 호출한다. 오류 코드와 완료 여부를 기록하고, 대기 상태만으로 HWP 작업 진행을 추정하지 않는다.
2. `UNAUTHORIZED` 또는 재인증 요청이면 문서 쓰기·합성 workflow 호출을 중단한다. 서비스 자격·임의 신원 헤더로 사용자 인증을 대신하거나 인증 게이트를 완화하지 않는다.
3. 읽기 전용 Sites 조회로 배포 버전, OAuth 클라이언트 ID, 플러그인 ID, MCP 주소·resource, 접근 정책 revision과 업로드 환경 revision의 변경 여부만 비교한다. 토큰·비밀·개인 문서 내용은 기록하지 않는다. Worker 로그에 원인이 없다는 사실도 모든 OAuth 계층의 정상 근거가 아니다.
4. 사용자가 기존 연결을 재인증하면 같은 클라이언트에서 기능 조회부터 재시도한다. 성공한 뒤에만 허용된 고정 합성 진단을 실행한다. Cloud와 Desktop 확인은 순서대로 수행하며, 이 순서 자체가 인증 오류의 해결책으로 입증됐다고 설명하지 않는다.
5. 재인증 직후 같은 오류가 다시 나오면 해당 클라이언트, 발생 시각, 안전한 오류 코드와 변경 여부만 남기고 사용자 또는 플랫폼의 추가 조치가 필요한 상태로 보고한다. 원인 확인 전에 토큰 만료·갱신 경쟁·앱 이름 변경·재배포 중 하나를 확정 원인으로 말하지 않는다.
