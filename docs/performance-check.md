## 운영 버전 49의 공개 양식 왕복과 짧은 읽기

2026년 10월 9일 제한된 본문 mini-sector 반환을 포함한 GitHub main `6c481e1d3db645ccce31783ce8fbb37980fa97d0`을 Sites 소스 `2411efeb14e2afb60cc2b28977aaa191834fe7b7`로 동기화하고 버전 **49** 배포 성공을 확인했다. 한 소유자 계정의 비공개 접근·기존 D1/R2 바인딩·마이그레이션과 컴파일된 Worker/WASM 대응을 확인했다. Node 482개·전체 compiled Worker 회귀 및 Windows·Ubuntu의 네 CI 작업이 통과했다. 환경 revision 8의 정확한 첨부 전달 origin 보완과 실제 문서 왕복은 [공개 양식 검사](first-form-check.md#운영-버전-49의-할당-보완과-외부-한글-비교)를 따른다.

이번 공개 양식은 원본 16,384바이트·187블록이며 40만 단위 합성 입력과 다르다. 각 단계 한 번의 native 도구 시간 구간에 있는 `/mcp` POST 성공 이벤트를 대응했다. 로그가 HWP 도구 이름을 제공하지 않으므로 **작업별 연결은 호출 구간에 근거한 추론**이고 종단 간 request ID로 직접 결합한 결과는 아니다.

| 단계 | 클라이언트 ms | Worker CPU ms | Worker wall ms |

| 직접 가져오기 | 3,343 | 209 | 1,832 |

클라이언트 시간은 첨부·연결·응답 전달을 포함하며 Worker CPU와 같은 측정 시작점이 아니다. 실제 수정본/복구본은 독립 로컬 결과/원본과 바이트 전체가 같았고 정확한 재시도와 세 버전 이력을 유지했다. 작은 공개 양식의 한 번 성공을 일반 성능 보장이나 큰 파일의 비용으로 확대하지 않는다. 같은 구간의 사이트 루트 조회에 관측된 CPU를 HWP 수정 CPU로 집계하지 않았다.

이어 경상국립대 두 공개 원본의 지원 내용 전체 읽기를 클라이언트에서 두 요청씩 묶어 3라운드 실행했다. 각 응답의 76/35블록이 세 라운드에서 같았고 두 문서의 현재 버전·revision·각 세 버전 이력도 불변이었다. 첫 라운드의 클라이언트 시간은 4,677/5,204ms, 다음 두 라운드는 1,210–1,483ms였다. 여섯 대응 MCP 이벤트는 CPU **17–96ms**, wall **655–768ms**, outcome `ok`였다. 캐시 hit/miss·같은 isolate·실제 서버 실행 구간의 겹침을 독립적으로 확인한 것은 아니며 클라이언트 병렬 제출을 서버 동시 부하 인증으로 집계하지 않는다.

전체 isolate JS/WASM RAM·통계적 백분위·일반 동시 부하·운영 비용·설정 CPU 한도는 미검증이다. 기존 400,000 UTF-16 단위 원격 한도와 120만 자 입력의 사전 거부는 유지하며 인증 자동 갱신 해결을 주장하지 않는다. 숫자 이벤트·호출 시각·실제 회수본·외부 한글 비교·브라우저 화면은 ignored `outputs/mvp-finish-20261009/`에 보관한다.

## 단일 raw 서식이 확인된 긴 문단의 조회 절감

2026년 10월 9일 후속 원격 소스에서 긴 단일 서식 문단의 반복 WASM 조회를 줄였다. 원본 바이트와 전체 엔진 모델의 순서 대응을 먼저 확인하고, 본문 또는 최상위 셀 문단의 plain UTF-16 텍스트·종료 CR·문단 길이/레코드 수·단일 tag-68 시작 위치 0을 검사한다. 문단의 자식 레코드는 text/shape/line 세 개만 허용하며 중첩·추가 제어·혼합 서식·불일치에는 적용하지 않는다. 엔진의 첫·중간·마지막 글자 서식 ID도 raw ID와 같아야 한다. 증명이 없거나 표본이 다르면 기존 글자별 검사로 돌아간다.

고정 한글 입력은 `합성`, 100,000·99,999·99,999·99,999자 본문, `끝`의 6문단이며 합계 **400,000 UTF-16 단위**다. 같은 입력의 마지막 글자 `끝`을 `검`으로 바꾸는 로컬 자식 Node 프로세스 측정에서 다음 값을 얻었다. 입력 생성은 별도 단계이며 각 경로를 한 번씩 측정했다. 조회 범주는 글자 속성 외 다른 모델 조회를 포함하고 계측 오버헤드도 있다.

| 로컬 단계 | 기존 경로 | 단일 raw 서식 증명 경로 |
| --- | ---: | ---: |
| 열기 | 17.371초 | 1.025초 |
| 저장하지 않는 수정 전 검사 | 34.798초 | 2.148초 |
| 열기 조회 호출 수 | 400,033 | 48 |
| 수정 전 검사 조회 호출 수 | 800,067 | 97 |

수정 전 검사의 원본·결과 WASM 생성자는 두 경로 모두 **2회**다. 결과 바이트를 별도로 재열고 그 실제 바이트에서 새 raw 증명을 만든다. 조회 생략만큼 서식 예산을 늘리지 않으며 기존 800,000 코드 포인트 검사 예산을 그대로 차감한다. 원격 합산 400,000 UTF-16 단위, 개별 문단 100,000 코드 포인트, 원본 값·버전 충돌·raw 보존·비대상 및 DocInfo 서식 비교를 유지한다. 로컬 Python/stdio의 기본 경로는 이 최적화를 활성화하지 않는다.

같은 400,000단위 파일을 실제 로컬 compiled Worker/D1/R2로 업로드해 7회 전체 읽기·무저장 계획·새 버전 저장·정확한 재시도·보호된 다운로드·원본 복구를 확인했다. 최초·수정·복구 3개 버전을 유지했고, 다른 모의 owner의 접근 거부 뒤 저장 상태도 같았다. 별도 Python/olefile는 WASM 없이 9개 CFB 스트림·6개 raw 문단의 원문/결과 400,000단위와 요청한 한 문단 외 레코드·DocInfo 보존을 비교했으며 복구본은 원본 바이트 전체와 같았다. 합성 본문·표 셀의 이모지/결합 문자, 기존 20종 모델 일치, 혼합 서식 fallback, 증명 불일치와 예산 유지도 검사한다. `node --test tests/uniform-style.test.mjs`와 `node scripts/check-uniform-style.mjs`를 `probes/sites-runtime`에서 실행하며 Windows·Ubuntu CI에 등록했다.

측정은 이 고정 입력의 로컬 wall-clock 관측값이다. 모든 문서의 지연·전체 isolate RAM·동시 처리·외부 HWP 시각 배치나 인증 갱신의 성공을 보장하지 않는다. **10월 9일 운영 버전 47에 반영했으며 120만 자 입력은 계속 거부한다.** 수치 기록은 ignored `outputs/improvement-loop-20261009/style-distribution-after-uniform-proof.json`, Worker 회수 바이트와 독립 비교는 `outputs/uniform-style-check/`에 둔다. 실제 Sites 검사는 다음 절로 구분하며 아래의 느린 로컬 수치는 최적화 전 기준선이다.

## 운영 버전 47의 40만 단위 왕복과 CPU 관측

2026년 10월 9일 GitHub main `3161ec7b9455ec11bf08479b99efb8ecd80ba538`을 Sites 소스 `cbcf99bccafc7ff1086f1b9a98809bd2720cd2d2`로 동기화해 버전 **47** 배포 성공을 확인했다. 소유자 한 계정의 비공개 접근, 기존 D1/R2 바인딩·마이그레이션과 환경 revision 7을 유지했다. 경로를 옮긴 소스의 Node 472개와 전체 compiled Worker 회귀를 통과했으며 Worker는 생성 경로 주석 외 main 빌드와 같고 WASM도 일치했다.

위의 **74,240바이트·400,000 UTF-16 단위·6문단** 합성 HWP를 실제 Codex Desktop native 연결에서 가져왔다. 7회 이어 읽기·끝 문단 한 글자의 무저장 계획·같은 문서 저장·정확한 재시도·embedded 다운로드·원본 복구가 통과했다. 계획은 저장하지 않았고 재시도는 새 버전을 만들지 않았으며 최초·수정·복구 세 버전을 유지했다. 계획과 저장의 페이지 수 안내는 원본/결과 각 227쪽과 `layout_verified: false`를 반환했다.

실제 회수한 수정본과 복구본은 각각 독립 로컬 결과 및 원본과 바이트 전체가 같았다. 회수 파일을 새 엔진으로 재열어 각각 7회 전체 읽기·400,000단위·6문단을 확인했다. 별도 Python/olefile는 WASM 없이 9개 CFB 스트림·6개 raw 문단을 검사해 요청한 한 문단 외 레코드·DocInfo 보존과 원본 복구를 확인했다. 실제 로그인 브라우저에서는 이전/현재 버전 표시, 기본 미리보기 이미지 로드, 수정본 HWP 다운로드의 해시 일치, 이름 저장과 그 이름의 검색 결과가 현재 복구본으로 연결되는 것을 확인했다. 이름 변경 전후 버전·revision·해시는 같았다. 읽기 요청의 직접 복사 안내가 선택한 이전 버전을 고정한 것도 확인했지만 실제 OS 클립보드 바이트는 미검증이다.

## 편집 대상의 서식 검사 비용

2026년 10월 9일 후속 소스에서 고정 합성 HWP를 로컬 자식 Node 프로세스로 검사했다. 영문·한글 각 1,000·10,000·30,000·100,000자의 단일 문단 8개 사례가 모두 열렸고, 입력 생성 시간은 열기 측정에서 분리했다. 각 사례는 한 번만 실행했으며 계측의 호출 시간 오버헤드를 포함한다. 운영 서버 CPU·전체 메모리·통계적 지연이나 독립 HWP 조판을 측정한 결과는 아니다.

10만 자 한 문단의 열기는 영문 2.062초, 한글 4.365초였다. 생성자는 각각 0.140·0.269초, 글자·문단·모델 조회 범주는 1.615·3.788초였다. 이 범주는 주로 글자별 서식 확인이지만 조회 전체를 묶은 값이므로 세부 원인과 시간 복잡도를 확정하지 않는다. 제목·끝 문단을 포함한 입력 전체는 각각 100,003 UTF-16 단위였다.

그다음 한글 합산을 정확히 400,000 UTF-16 단위로 맞춘 두 입력을 별도로 생성했다. 각 입력은 제목 2단위와 끝 문단 1단위를 포함하고 7회 이어 읽기의 합산도 400,000이었다.

한 긴 문단은 개별 편집 한도 초과로 서식 전수 검사를 하지 않는 읽기 전용 대상이다. 네 문단은 개별 편집 한도 이내여서 검사량이 늘었다. 후보 수는 저장 성공 수와 구분한다. 같은 합계라도 문단 구성과 서식 검사에 따라 비용이 달라지며, 400,000단위를 CPU 처리 성공을 보장하는 값으로 해석하지 않는다.

네 문단 입력의 마지막 한 글자를 같은 UTF-16 길이로 바꾸는 로컬 사전 검사를 추가로 한 번 실행했다. 기존 snapshot을 얻은 뒤의 사전 검사만 **34.798초**였고, 메모리 내 생성·재열기·raw 보존 검사에는 통과했으며 저장하지 않았다. 사전 검사에서 독립 원본/결과 생성자 2회 1.879초, 조회 범주 800,067회 30.421초를 기록했다. 실제 Sites 요청·저장·서버 CPU나 설정 한도를 검증한 것은 아니다. 기존 보존 검사를 줄이거나 입력을 자동으로 축약하지 않았으며, 다음 성능 작업은 이 글자별 서식 검사 경로의 원인과 안전한 절감 방법을 우선 조사한다.

자식 프로세스의 단계 시간은 45초로 제한했고 모든 측정 단계가 종료됐다. 합성 입력과 숫자 결과는 ignored `outputs/improvement-loop-20261009/style-scan-profile.json`, `style-distribution-profile.json`, `style-distribution-preflight.json`에 보관한다. 처리·편집·인증 설정이나 운영 배포는 바꾸지 않았다.

Worker는 생성 주석을 제외하면 main 빌드와 같고 WASM 바이트도 일치한다. 실제 사용자 기능 조회는 400,000단위·WASM 전 검사·편집 안내를 확인했다. 고정 소형 합성 문서의 전체 조회·계획·수정·빈 셀 작업·복구·embedded 회수·시험 문서 정리와 클라이언트의 독립 바이트 재현·재열기가 통과했다. 이후 실제 연결의 [합성 경계 검사](#운영-버전-45의-합성-경계-검사)도 수행했다. 아래 사전 검사 절의 시간 수치는 로컬 측정이며 실제 서버 CPU·정확한 조판 검증으로 확대하지 않는다. 배포 후 재연결 오류가 있었고 사용자 재연결 뒤 성공했으므로 자동 인증 갱신은 별도 미해결이다.

2026년 10월 6일 Linux Cloud 작업에서 최신 `origin/main`의 기준 커밋 `4541b26317bddfc2016519f0b44d735671aca0c5`를 포함하는 코드로 조사했다. Node 24.19.0, 고정 `@rhwp/core` 0.8.6, Python `olefile` 0.47이다. 이 절은 로컬 합성 검사이며 운영 배포·실제 OAuth·플랫폼 CPU 사용량을 재검증한 결과가 아니다. 이전 실패 로그의 CPU **32,000ms는 관측 사용량**이며 실제 설정 한도는 계속 미확인이다.

같은 고정 생성기의 결정적 ASCII 350,009 / 1,200,009단위 HWP를 생성해 로컬 Node에서 각 한 번 열고 호출을 계측했다. 입력 생성은 열기 시간에서 제외했고 결과는 고정된 시간 보장이 아니다. 35만 자 열기는 2,071.8ms 중 WASM 생성자 1,990.5ms, 120만 자 열기는 22,219.8ms 중 생성자 21,932.9ms였다. 업로드 서비스는 저장 전 `engine.open`을 한 번 호출한다. 고정 엔진의 생성자는 열기 중 쪽 조판을 수행하며, 이 비용이 이번 로컬 측정의 대부분이었다. 이를 운영 실패의 모든 비용·원인에 대한 종단 간 입증으로 확대하지 않는다.

후속 구현은 원격 문서 엔진에 **400,000 UTF-16 단위**의 본문·표 셀 합산 검사를 추가했다. 파서 raw 집계 후 WASM 생성·읽기 캐시 접근·저장 전에 초과를 `HOSTED_WORKLOAD_LIMIT_EXCEEDED`로 거부한다. 수정은 검증한 원본 값과 새 값으로 요청 전체의 결과 길이를 계산해 변경 전에 같은 한도를 검사한다. 일반 로컬 어댑터의 기존 2,000,000 raw 한도와 4 MiB 전송 한도는 유지한다. 400,000은 실패한 120만 자 입력과 기존 성공한 350,009단위 사례를 구분하는 보수적 범위이며, CPU 시간을 예측하는 공식이나 설정 CPU 한도에서 계산한 값이 아니다. 한도 이하의 모든 복잡한 문서·메모리·동시 처리 성공을 보장하지 않는다.

`npm run test:limits`의 실제 compiled workerd/D1/R2 검사에서 압축된 1,200,000단위 부정 입력은 약 84.1ms에 명확히 거부됐고 문서·버전·요청 기록·R2 객체가 모두 0이며 입력 해시도 유지됐다. 이 부정 입력은 외부 CFB 텍스트 레코드 재구성 사례이고 유효한 편집·조판 코퍼스로 집계하지 않는다. 2,000,001단위 입력의 기존 raw 거부, 4 MiB 경계, 작은 문서와 45셀 양식의 저장·다운로드·복구 6회도 통과했다. 시간은 로컬 HTTP 왕복 관측값이며 운영 CPU·응답 시간 보장이 아니다.

WASM 생성 0회·캐시 접근 0회, 구역·셀 합산과 UTF-16 이모지 계산, 정확한 경계, 요청 전체의 수정 길이·기존 값 불일치·변경 0회, 고정 오류 안내의 정보 비노출과 브라우저 재시도 차단을 회귀 검사한다. 기존 문서·버전을 삭제하지 않으며 직접 보호된 HWP 다운로드 경로를 유지한다. 운영 버전 45 반영과 실제 기능 조회의 새 제한은 이후 확인했다. 실제 연결의 합성 경계 결과는 아래 별도 절에 기록한다. 120만 자 처리 성공·인증 자동 갱신·전체 isolate RAM·외부 HWP 시각 배치는 미검증이다.

앞서 실제 고정 writer로 생성하고 로컬 열기를 통과한 **1,248,768바이트·1,200,009단위** HWP도 새 compiled Worker에 넣었다. 브라우저 업로드 2회는 73.1 / 64.9ms, 모의 파일 가져오기 MCP 2회는 77.6 / 51.0ms에 같은 오류로 거부됐다. 경로별로 동일 UUID를 재사용했고, 기존 35만 자 문서의 D1 문서·버전·요청 행과 모든 R2 키·바이트 해시가 거부 전후 그대로였다. 파일 전송 응답은 모의이며 외부 네트워크·운영 업로드를 사용하지 않았다.

기존 **376,832바이트·350,009단위** 문서는 같은 로컬 Worker에서 가져오기 5.00초, 6회 전체 이어 읽기 2.83초, 마지막 짧은 문단의 수정 전 검사 6.01초, 저장 5.93초, 원본 복구 2.81초로 통과했다. 수정·복구 HWP를 보호된 로컬 다운로드 경로로 받아 해시와 전체 읽기를 확인했고 최초·수정·복구의 3개 버전이 남았다. 독립 Python/olefile 검사에서 선택한 마지막 문단 외의 본문 원시 레코드·비대상 스트림·DocInfo가 보존됐고 복구본은 원본 바이트 전체와 일치했다. 이 시간은 각 로컬 호출 1회의 HTTP 왕복이며 운영 CPU 시간이 아니다.

앞선 Linux 검증은 `npm test`의 Node 412개와 전체 compiled Worker·저장/격리/장애/삭제/파일 전달/목록/한도 검사를 통과했다. 공통 엔진 34개와 독립 Python 비교 20종(스트림 180·본문 canonical 60·DocInfo 20 비교), 저장소 링크·파일 제외 검사도 통과했다. 새 Windows CI나 실제 운영 배포 검사는 수행하지 않았다.

### 운영 버전 45의 합성 경계 검사

2026년 10월 6일 실제 소유자 native MCP 연결로 확인했다. 고정 엔진 0.8.6의 writer가 만든 각 424,960바이트 HWP 세 개를 사용했으며 로컬 raw 합산·엔진 재열기로 399,999 / 400,000 / 400,001단위를 확인했다. 여러 본문 문단과 표 셀의 여러 문단, 😀·👩‍💻·🚀를 포함한다. 개인 문서는 전송하거나 수정하지 않았다.

저장된 400,000단위 버전은 버전·해시를 고정해 최대 64 KiB 조각 7개를 회수했다. client collector가 각 조각의 위치·크기·해시·resource URI와 전체 해시를 검사했고, 같은 고정 원본·두 작업의 로컬 독립 재현과 **전체 바이트가 일치**했다. 실제 엔진 재열기의 본문·셀 모델과 raw 집계가 모두 400,000단위였다. 별도 Python `olefile` 0.47은 11문단 중 요청한 두 대상 외의 canonical 본문 레코드·비대상 스트림·DocInfo 보존을 확인했다. 사용자의 명시적 삭제 요청 후 이번에 만든 시험 문서 하나와 기록된 네 버전만 삭제했다. 미게시·진행 중 블롭 GC 인증은 아니다.

실행 기록은 ignored `outputs/server-boundary/`에 보관한다. 파일 전달 origin은 요청마다 달라질 수 있으며 위의 초기 경계 검사에서는 후보만으로 허용 목록을 넓히거나 같은 요청을 반복하지 않았다. 한도 도입 전 초과 저장본의 실제 서버 복구 거부와 새 화면의 실제 로그인 브라우저 조작은 미검증이다. 초과 이전 버전의 복구 거부는 앞선 로컬 compiled Worker 검사 범위로 남는다. 초기 경계 검사는 원격 설정·소스·배포를 변경하지 않았으며 서버 CPU 측정·전체 RAM·동시 처리·외부 프로그램 조판·OAuth 자동 갱신 해결을 증명하지 않는다. 이미 통과한 전체 로컬 검사는 반복하지 않았다.

### 파일 전달 호스트 설정 후 직접 가져오기

같은 날 앞선 `FILE_URL_NOT_ALLOWED` 진단에서 관측한 정확한 origin의 공개 DNS와 HTTPS 호스트 인증 검사를 통과했다. 루트 요청의 HTTP 400은 파일 전송 성공이 아니며 DNS·TLS 확인과 실제 합성 파일 가져오기를 구분한다. 기존 세 origin에 관측한 주소 하나만 추가한 설정은 정확한 네 주소 허용, 유사·미관측·HTTP·사용자 정보·포트·fragment 주소 여섯 개의 fetch 전 거부, 리디렉션 거부와 사용자 인증 헤더 미전달 검사를 통과했다. 네트워크는 이 설정 검사에서 모의다.

사용자의 명시적 승인 후 `HWP_EASY_FILE_ORIGINS` 하나만 갱신해 환경 revision **6 → 7**로 바꾸고, 기존 소스·archive의 버전 **45**를 소유자 전용으로 재배포했다. 배포 `succeeded`, 적용 revision 7과 MCP 제공을 확인했다. 다른 runtime entries, 기존 코드·D1/R2 바인딩·스키마와 접근 범위를 유지했고 소유자 한 명·editor/group 0도 다시 확인했다. 합성 전용 origin 설정은 새로 열지 않았다.

새 설정에서 기존 writer 합성 **424,960바이트·400,000단위** 파일을 native `hwp_import`로 직접 가져와 저장에 성공했다. 입력·저장 해시가 같았고 저장본의 첫 읽기 조각·11블록 집계·표 한 개와 저장 해시를 확인했다. 이번 읽기는 첫 조각만 조회했으며 전체 읽기 완료로 표시하지 않는다. 이어서 400,001단위 파일은 한도 오류와 `saved: false`, 재시도 비권고로 거부됐고 시험 문서의 현재 버전·revision 1·한 버전 이력·해시는 유지됐다. 앞서 받은 명시적 시험 문서 삭제 요청에 따라 이번 문서 하나와 기록된 버전 하나만 삭제했다.

성공 응답에는 실제 파일 전달 origin이 없으므로 **추가한 특정 호스트를 이번 native 호출이 사용했다는 증거는 아니다.** 정확한 네 주소 설정과 실제 가져오기 성공을 확인한 범위이며, 모든 향후 파일 호스트·임의 양식·조판을 인증하지 않는다. 미관측 주소는 계속 거부하고 관찰값만으로 자동 허용하지 않는다. 설정 준비 중 합성 진단은 `oauth_token_invalid_grant`로 실패했으며 사용자 재연결 후 기능 조회·적용 뒤 업로드는 성공했다. OAuth 자동 갱신 문제는 별도 미해결이다. 코드가 바뀌지 않아 기존 전체 검사를 다시 돌리지 않았으며 새 설정·실제 입력·문서 검사를 수행했다. 세부 실행 기록은 ignored `outputs/deployment/`에 둔다.

로컬 검사일: 2026년 10월 5일. Windows x64, Node 22.17.0, 고정 `@rhwp/core` 0.8.6에서 측정했다. 아래 로컬 절은 **로컬 기준선과 경계 검증**이며 실제 Sites 지연·전체 isolate 메모리·동시 처리·운영 비용이나 서비스 수준을 인증한 결과는 아니다. 로컬 절에는 개인 문서와 원격 저장 문서를 사용하지 않았다. 10월 6일 실제 소유자 배포의 합성 문서 측정은 마지막 절에 별도로 기록한다.

## 재현 방법

개발 환경의 `probes/sites-runtime`에서 실행한다. 사용자용 설치 명령이나 제품 CLI가 아니다.

```sh
npm run test:limits
npm run benchmark:synthetic
npm run profile:large
```

경계 검사는 빌드한 실제 workerd·D1·R2·WASM을 사용하되 신원은 모의 값이고 저장소는 실행 종료 뒤 폐기한다. 외부 네트워크 요청은 금지한다. 성능 도구는 인수·입력 경로를 받지 않고 고정 합성 문서만 메모리에서 생성한다. 보고서는 저장소에서 제외한 `outputs/synthetic-performance/`에 새 파일로 기록한다. 문서 내용·HWP 바이트·OAuth 토큰은 보고하지 않는다.

각 Node 문서는 새 프로세스에서 실행한다. 작은 문서·45셀 양식은 5회, 나머지 정상 사례는 3회 반복하고 회차 사이에 명시적으로 GC를 실행한다. 초과 본문 거부는 1회 확인한다. 초기화와 입력 생성 시간은 별도 기록하며 아래 시간은 첫 회를 제외한 반복의 중앙값이다. 표본이 적고 같은 PC의 다른 작업 영향을 받으므로 처리 시간 보장이나 통계적 백분위로 해석하지 않는다.

## 로컬 엔진 측정

아래 표는 최적화 전 기준선이다. 이어 읽기와 재열기 중복을 줄인 이후 결과는 다음 절에 별도로 남긴다.

시간 단위는 ms다. 끝까지 읽기는 기본 8,000자 응답을 이어 읽고 누락·중복·전체 길이를 검사하는 비용을 포함한다. 편집은 긴 첫 문단을 바꾸는 대신 짧은 마지막 문단 또는 양식 셀 한 곳을 바꾼다. 수정 전 검사도 실제 직렬화·재열기·독립 레코드 보존 검사를 수행한다.

| 합성 사례 | 입력 bytes | 읽기 호출 수 | 열기 | 전체 읽기 | 수정 전 검사 | 편집 | WASM 용량 MiB | 프로세스 최고 RSS MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 작은 본문·표 | 13,312 | 1 | 2.5 | 0.2 | 7.5 | 6.7 | 3.4 | 174.7 |
| 45셀·52블록 양식 | 13,312 | 1 | 6.9 | 0.8 | 22.8 | 21.8 | 3.7 | 240.9 |
| 반복 한글 20만 자 | 44,544 | 26 | 847.3 | 128.7 | 3,432.6 | 3,421.5 | 35.0 | 319.7 |
| 결정적 ASCII 6.4만 자 | 82,944 | 9 | 1,151.2 | 7.5 | 3,897.0 | 3,128.0 | 5.7 | 293.8 |
| 결정적 ASCII 35만 자 | 376,832 | 44 | 859.6 | 152.4 | 3,453.3 | 3,446.2 | 19.3 | 303.7 |

WASM 수치는 실행 후 선형 메모리 **확보 용량**이고 살아 있는 할당의 합계가 아니다. RSS는 초기화·합성 입력 생성·검사·명시적 GC를 포함하는 **Node 프로세스 수명 전체의 최고 값**이다. 단계 끝 `process.memoryUsage()` 값도 원시 보고서에 보관하지만 순간 최대 메모리는 아니다. 256 MiB V8 old-space 설정은 전체 RAM 제한이 아니며, 이 수치를 실제 Worker isolate 사용량과 비교해 안전하다고 판정하지 않는다.

작은 문서·45셀 양식은 첫 페이지 SVG도 측정했다. 큰 단일 문단의 렌더링은 이번 측정에서 제외했다. 모든 완료 사례에서 원본 불변·대상 텍스트·비대상 텍스트와 독립 raw 보존 검사를 확인했으며, 배치 정확성은 미검증이다.

## 이어 읽기와 검증 결과 재사용

같은 날 같은 고정 입력으로 다시 측정했다. 매 응답마다 문단 전체를 문자 배열로 만들고 JSON 복사하던 동작을 없앴다. 보조 평면 문자가 있는 위치만 문서 스냅샷 내부에 보관하고, Unicode code point 기준으로 요청한 조각만 잘라낸다. 응답의 서식 정보는 여전히 깊은 복사이므로 호출자가 바꿔도 스냅샷을 바꾸지 못한다.

공통 엔진이 직렬화 결과를 다시 열어 확인한 모델을 호스트에 함께 반환한다. 호스트는 **동일한 바이트 객체가 유지된 경우에만** 이 검사 결과를 재사용한다. 셀 보존 보정으로 바이트가 바뀌면 새로 열어 검사한다. 원문 검사·정확한 대상/비대상 텍스트·스타일/표 모델·독립 raw 보존 검사는 유지했다. 실제 WASM 생성자 계수 검사에서 일반 편집은 초기 열기를 포함해 4회에서 3회, 보정 편집은 5회에서 4회로 줄었다. 로컬 브리지는 기존 바이트 반환 계약을 유지한다.

| 합성 사례 | 기준선 전체 읽기 ms | 개선 후 전체 읽기 ms | 개선 후 수정 전 검사 ms | 개선 후 편집 ms |
| --- | ---: | ---: | ---: | ---: |
| 작은 본문·표 | 0.2 | 0.5 | 11.0 | 27.4 |
| 45셀·52블록 양식 | 0.8 | 1.4 | 23.1 | 18.3 |
| 반복 한글 20만 자 | 128.7 | 2.7 | 3,343.7 | 2,968.7 |
| 결정적 ASCII 6.4만 자 | 7.5 | 0.8 | 2,157.7 | 2,159.4 |
| 결정적 ASCII 35만 자 | 152.4 | 4.1 | 3,560.8 | 3,764.4 |

반복 한글 20만 자와 ASCII 35만 자의 전체 읽기는 각각 약 98%, 97% 감소했다. 편집·수정 전 검사 시간은 사례별로 섞여 있고 작은 문서의 측정도 흔들렸다. PC 부하가 통제된 A/B 실험이나 편집 시간의 일관된 개선으로 해석하지 않는다. 큰 문서의 직렬화·재열기 비용은 여전히 남아 있다.

120만 자는 기존 60초 **전체** 측정 제한에서 여전히 `limited`였다. 이를 숨기거나 기본 제한을 늘리지 않고, `profile:large`에서 같은 고정 문서의 한 번의 작업을 별도 진단했다. 이 도구만 단계별 45초·전체 180초 제한을 사용하며 제품 설정은 바꾸지 않는다. 입력 생성 28.8초, 열기 8.5초, 전체 읽기 13.2ms, 수정 전 검사 31.4초, 편집 30.8초, 재열기 8.8초, 수정 후 전체 읽기 15.6ms로 완료했다. 대상/비대상 텍스트와 원본 해시·raw 보존 검사를 통과했다. 단일 표본이고 원격 업로드·실제 Worker 요청·미리보기·배치 정확성 검증은 포함하지 않는다.

## 불필요한 글자 스타일 복원 줄이기

`profile:large`에 생성자·텍스트 수정·스타일 지정·내보내기의 호출 수와 소요 시간을 추가했다. 인수·반환값·문서 내용은 보관하지 않는다. 첫 계측의 생성자 집계 누락을 수정하고 실제 WASM 편집의 바이트·모델 동일성과 생성자 계수를 검사한 뒤 재측정했다. 계측 자체의 비용을 포함하며 각 비교는 같은 고정 120만 자 문서의 단일 실행이다.

| 단계 | 개선 전 전체 s | 개선 후 전체 s | 개선 전 생성자 합계 s | 개선 후 생성자 합계 s | 개선 전 스타일 지정 s | 개선 후 스타일 지정 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 수정 전 검사 | 28.50 | 19.70 | 18.42 | 18.61 | 9.13 | 호출 생략 |
| 편집 | 29.32 | 17.80 | 19.92 | 16.76 | 8.42 | 호출 생략 |

개선 전 실제 내보내기는 각각 약 45ms·51ms였다. 큰 비용은 두 번의 문서 생성과, 이미 맞는 스타일을 다시 지정하는 동작이었다. 고정 버전의 원본 코드에서도 문서 열기가 재조판·페이지 계산을 수행하고 글자 모양 지정이 해당 구역을 재구성함을 확인했다. [0.8.6 문서 생성 코드](https://github.com/edwardkim/rhwp/blob/v0.8.6/src/document_core/commands/document.rs), [글자 모양 코드](https://github.com/edwardkim/rhwp/blob/v0.8.6/src/document_core/commands/formatting.rs)

이제 **1,024 code points 이하의 새 텍스트**는 모든 위치의 글자 모양 ID가 원래 값과 같은지 먼저 확인하고, 모두 같을 때만 재지정을 생략한다. 한 위치라도 다르면 기존 복원을 수행한다. 긴 삽입 범위는 추가 속성 조회 비용을 피하기 위해 기존 복원 경로를 그대로 사용한다. 이는 최적화 범위이며 편집 허용 길이를 줄이는 제품 한도가 아니다. 셀 비우기의 빈 범위 복원과 저장 후 재열기·정확한 스타일/표 모델·독립 raw 보존 검사는 유지한다.

실제 합성 편집에 중간 이모지 위치의 다른 스타일을 주입해 양 끝만 확인하는 구현이 통과하지 못하도록 검사했다. 복원 실패 시 내보내기 호출·결과 바이트가 없고 원본이 유지된다. 1,025자 범위는 추가 사전 조회 없이 기존 복원을 수행한다. 큰 문서 후속 실행은 입력 생성 29.28초, 전체 읽기 12.42ms, 재열기 8.26초, 수정 후 읽기 11.90ms로 완료했으며 대상/비대상 내용·원본 해시·raw 보존 검사를 통과했다.

편집 시간은 이번 단일 비교에서 약 39% 감소했지만 처리 시간 보장이 아니다. 남은 비용의 대부분은 엔진의 문서 생성이다. 실제 서버 전체 RAM·동시 요청·원격 지연·큰 문서 미리보기·배치 정확성은 여전히 미검증이며, 이 결과로 사용 한도를 늘리지 않는다.

## 요청 전체에서 중복 원본 열기 제거

저장·수정 전 검사 요청은 저장소의 소유권·버전·바이트 해시를 확인한 후 원본 스냅샷을 만들고, 그 스냅샷에서 편집하기 위해 같은 원본을 다시 열었다. 일반 결과에서는 독립 결과 재열기까지 요청당 WASM 생성자가 3회 호출됐다. 이제 원본의 새 엔진 세션에서 검사한 모델로 호스트가 raw 대상 매핑·지원 범위·요청을 검사한 뒤, 같은 세션에서 편집한다. 모델은 호스트 콜백에 분리 복사되어 전달되고 실제 엔진 객체는 전달되지 않는다. 결과 재열기·스타일/표/내용 비교·독립 raw 검사·복원본 재열기·저장소 조건부 교체는 유지한다. 살아 있는 엔진 세션은 요청 안에서 해제되며 캐시하지 않는다.

일반 요청의 생성자는 3→2회, 메타데이터 복원이 필요한 요청은 4→3회다. 20개 합성 편집 코퍼스에서 이전 스냅샷 경로와 새 경로의 결과 바이트·검증 필드·수정 전 검사 응답이 같았다. 원본/요청 복사, 해시 불일치의 WASM 이전 거부, 중복/오래된 대상, 빈 셀 채우기·비우기, 복원본 재열기, 불투명 쪽 번호 바이트 훼손 시 저장 0회도 검사했다.

`node scripts/profile-large-synthetic.mjs --request-sessions`는 고정 120만 자 합성 문서 한 번으로 **요청마다 원본을 여는 비용을 포함**해 두 경로를 비교한다. 같은 입력·편집에서 수정 전 검사는 31.33→16.93초, 편집·검증은 25.54→17.96초로 완료했다. 결과 바이트와 검증 응답이 일치했고, 결과 재열기·대상/비대상 텍스트·원본 해시·raw 보존 검사가 통과했다. 앞 절의 17.80초는 이미 열린 스냅샷에서 편집하는 시간으로, 이번 요청 전체 측정과 시작점이 다르다. 입력 생성은 별도 31.76초이며 이번 실행은 로컬 1회 관측이다. 서버 응답 시간·백분위·RAM·배치 정확성을 보장하지 않고 기존 제품 한도와 일반 벤치마크의 60초 전체 제한을 유지한다.

## 별도 읽기 요청 사이의 검사 모델 재사용

원격 `hwp_read`는 매 호출마다 저장소에서 소유권·문서·선택 버전·삭제 상태를 확인하고 R2 바이트를 가져온다. 이제 같은 사용자·문서·불변 버전·SHA-256의 검사 모델만 해당 Worker 프로세스 안에서 재사용한다. 매번 새 바이트의 해시·raw 작업량·raw/모델 대상 매핑을 다시 검사하고, 내용을 반환하기 직전에 선택 버전이 삭제되지 않았는지도 저장소에서 재확인한다. 저장·수정 전 검사·미리보기에는 캐시를 사용하지 않고 새 엔진 세션을 사용한다.

캐시는 분리 복사 가능한 JSON의 UTF-8 바이트만 보관하며 합계 최대 8 MiB·2개 항목으로 제한한다. HWP 바이트·raw 스트림·살아 있는 WASM 문서·인증·권한 결과는 보관하지 않는다. 항목을 만든 뒤 5분이 지나면 재사용하지 않으며 읽기 성공으로 기한을 늘리지 않는다. 만료된 항목은 다음 캐시 접근 때 제거되므로, 유휴 메모리가 정확히 5분에 물리적으로 지워진다는 보장은 아니다. 명시적 삭제는 실행 전후에 해당 사용자의 문서 항목을 제거하고, 읽기 후 삭제 상태 재확인이 실패해도 제거한다. 캐시 누락·기한 만료·초과 모델은 새 검사로 처리하며 원본·이전 저장 버전의 보관 계약을 바꾸지 않는다. 8 MiB는 직렬화된 캐시만의 예산이며 전체 JS·WASM RAM 한도가 아니다.

`node scripts/profile-large-synthetic.mjs --read-requests`로 고정 1,200,009자·1,248,768 bytes 문서의 별도 요청 3개를 비교했다. 매번 새 엔진 인스턴스를 만들었고, 앞선 경로는 각 호출에서 새 WASM 검사, 개선 경로는 첫 검사 뒤 공유 캐시를 사용했다.

| 요청 | 매번 검사 ms | 개선 후 ms |
| --- | ---: | ---: |
| 첫 조각 | 8,119.6 | 8,085.7 |
| 다음 조각 | 8,154.4 | 28.9 |
| 세 번째 조각 | 8,023.7 | 27.8 |

세 응답이 완전히 같았고, 별도 호출 151개로 전체 본문을 재조립한 결과도 새 검사 모델과 같았다. 이미 캐시가 있는 전체 호출 체인은 재조립·검사 비용을 포함해 약 4.04초였다. cache miss 1회·hit 153회, 직렬화된 모델 1,230,285 bytes였고 원본 해시가 유지됐다. 입력 생성 27.28초와 독립 비교용 새 검사 8.09초는 별도로 측정했다. 캐시 없는 151개 요청의 총시간을 측정한 것은 아니다.

실제 WASM 검사는 여러 엔진 인스턴스의 이어 읽기에서 생성자·해제 각각 1회, 따뜻한 캐시 이후 편집은 독립 원본/결과 생성자·해제 각각 2회를 확인했다. 사용자·문서·버전·해시·엔진 공급자 분리, 응답 변경의 캐시 오염 방지, 실제 UTF-8 예산, LRU·절대 기한·초과 모델 대체를 검사했다. 실제 로컬 D1/R2에서 최초 검사와 캐시 재사용 각각에 대해 읽기 중 삭제 시작·완료의 네 경합을 주입해 텍스트 반환 거부와 항목 제거를 확인했다. 이는 모의 신원의 로컬 검사이며 실제 OAuth 철회를 인증하지 않는다.

측정은 로컬 단일 실행의 엔진 경로이며 D1/R2·OAuth·네트워크·배포 Worker의 지연과 메모리는 포함하지 않는다. 프로세스 재시작·다른 isolate·기한 만료는 캐시 누락이 된다. 기존 같은 스냅샷의 약 12ms 전체 읽기와 시작점이 다르며, 서버 응답 보장이나 파일 한도 확대의 근거로 사용하지 않는다.

## 확인된 느린 사례와 개선

120만 자 사례는 입력 생성 약 27.2초, 첫 열기 약 8.1초, 전체 읽기 약 1.75초를 완료한 뒤 첫 수정 전 검사 중 **측정용 자식 프로세스 전체의 60초 제한**에 도달했다. 초기화·입력 생성·여러 검사까지 합한 제한이므로 이를 제품의 개별 호출 시간 초과나 편집 성공으로 표시하지 않는다. 도구는 완료한 단계와 마지막 단계를 보존하고 종료 코드 2 및 `limited`를 반환한다. 예기치 않은 검사 실패는 종료 코드 1이다.

추가로, 본문 2,000,001 UTF-16 code units를 가진 17,408 bytes의 압축 합성 HWP가 엔진 파싱 전에 제한되지 않는 문제를 재현했다. 개선 후 모든 BodyText 텍스트 레코드의 보이는 UTF-16 길이를 **WASM 실행 전에 합산**하며, 2,000,000을 넘으면 `RAW_TEXT_LIMIT_EXCEEDED`로 거부한다. 이 추가 raw 작업량 한도는 본문·셀뿐 아니라 BodyText에 있는 미지원 목록의 텍스트에도 적용한다. 기존 모델 검사와 보존 검사는 유지한다.

실제 압축 합성 HWP를 이용한 검사에서 WASM 생성자를 호출하지 않았고, 로컬 compiled Worker는 약 23.6ms에 거부했다. D1 문서·R2 객체가 생기지 않았으며 입력 해시는 유지됐다. 이 파일은 읽기 거부 전용의 외부 CFB 재구성 사례이며, 정상 편집·서식 호환성 코퍼스에 합산하지 않는다. 정확한 경계에서 100만 이모지의 UTF-16 길이, 여러 구역·셀의 합산, 제어 슬롯·탭·문단 끝 문자의 계산을 별도로 검사했다.

## 업로드·저장 경계

- 전송의 4,194,303 / 4,194,304 bytes는 크기 검사를 통과하고, 4,194,305 bytes는 `TRANSFER_LIMIT_EXCEEDED`로 거부한다. Content-Length 없는 스트림도 같은 경계에서 검사하고 reader를 해제한다. 선언한 길이가 초과하면 reader를 받기 전에 거부한다.
- 위 경계 입력은 형식이 없는 0 바이트 배열이다. 한도 이하에서 HWP 형식 검사로 거부되고 D1/R2는 비어 있음을 확인했다. **유효한 4 MiB HWP의 편집 성공을 검증한 것은 아니다.**
- 한도 이하 경계는 Miniflare의 Node HTTP 업로드를 통과한다. 초과 스트림과 초과 선언 길이는 테스트 전용 메모리 진입점에서 요청을 만들고 실제 compiled Worker를 호출한다. 초과 본문 취소 시 Node HTTP 연결이 끊기는 Windows 경합을 검사 결과와 분리하기 위한 것으로, 배포 산출물에는 이 진입점이 없다. 초과 입력의 실제 브라우저 HTTP 응답 전달은 이 검사로 인증하지 않는다.
- 작은 문서와 45셀 양식을 로컬 Worker에서 각각 3회 업로드→읽기→수정 전 검사→같은 문서 편집·저장→다시 읽기→다운로드→원본 복구했다. 각 문서의 3개 버전, 다운로드·복구 해시와 비대상 내용이 일치했다. 첫 회 이후 단계 시간 합계는 각각 약 95–102ms와 143–148ms였으며 OAuth·네트워크 지연은 포함하지 않는다.
- 4 MiB 입력·128개 버전 제한과 직접 삭제까지 보관하는 계약은 유지한다. 인증 자동 갱신 문제와 운영 저장 비용은 이번 검사로 해결하거나 인증하지 않는다.

다음 성능 검증은 느린 큰 문서의 원인 분리, 실제 Worker의 JS·WASM 전체 메모리와 동시 요청, 유효한 큰 HWP의 파일 전달·미리보기, 운영 저장 비용이다. 현재 결과를 근거로 사용 한도를 늘리지 않는다.

## 실제 소유자 배포의 CPU·응답과 복구 검사

2026년 10월 6일 비공개 Sites 버전 44에서 기존 소유자 계정의 Codex Desktop 연결을 사용했다. 같은 고정 생성기로 만든 결정적 ASCII 35만 자와 120만 자에 짧은 마지막 합성 문단을 붙였다. 입력은 각각 376,832 / 1,248,768 bytes다. 개인 파일을 사용하지 않았으며 계정 접근·제품 한도·인증 설정을 바꾸지 않았다.

각 경우 1회 실행했다. 클라이언트 시간은 native 도구 호출 시작부터 완료까지이며 첨부 업로드·연결·응답 전달을 포함한다. 서버 수치는 읽기 전용 Sites Worker 로그의 `cpuTimeMs`·`wallTimeMs`다. `/mcp` 경로와 호출 시간 구간의 후보 이벤트를 대응했고 종단 간 request ID로 연결한 것은 아니다. 35만 자의 아래 단계에는 각각 성공 이벤트 하나가 관찰됐다. 서버 전체 RAM·동시 요청·통계적 백분위와 서비스 수준은 측정하지 않았다.

| 35만 자 단계 | 클라이언트 s | 서버 CPU s | 서버 처리 s |
| --- | ---: | ---: | ---: |
| 가져오기·저장 | 16.033 | 10.202 | 14.493 |
| 6회 전체 이어 읽기 합계 | 62.053 | 36.321 | 51.326 |
| 마지막 짧은 문단 수정 전 검사 | 13.669 | 9.893 | 13.048 |

읽기의 합계는 별도 6개 요청 시간의 합이며 요청 사이 에이전트 처리·관찰 시간은 제외했다. 각 읽기 요청의 서버 CPU는 4.522–6.609초였다. 이 로그만으로 검사 모델 캐시 hit/miss나 같은 isolate 재사용을 판정할 수 없으며, 로컬의 약 28ms 재사용 결과를 실제 배포의 지연으로 설명하지 않는다.

35만 자 본문과 마지막 9자를 버전 고정·변경하지 않은 cursor 체인으로 끝까지 확인했다. 생성한 원문과 모든 조각이 같았고, 마지막 짧은 문단만 편집했다. 최초·수정·복구의 3개 버전을 보존했다. 같은 계정 브라우저에서 수정본·복구본을 실제 내려받아 해시·재열기·독립 Python/olefile의 비대상 원시 레코드를 확인했고 복구본은 원본과 바이트 단위로 같았다. 첫 기본 미리보기와 113페이지 표시를 확인했으며 나머지 페이지나 독립 HWP 조판을 인증하지 않았다. 확인한 세 HWP를 로컬에 별도 보관했다.

120만 자 입력은 로컬 생성·열기 검사에는 통과했으나 실제 가져오기 호출은 83.775초 뒤 `-32603 / Internal error`로 실패했다. 의도적인 도구 호출은 한 번이었고 에이전트가 다시 업로드하지 않았다. 그 호출 구간에 `/mcp`의 `exceededCpu` 이벤트 두 개가 기록됐으며 각각 CPU 32,000ms, 처리 40,727 / 33,679ms였다. 플랫폼 내부 재시도의 이유와 정확한 설정 CPU 한도는 확인하지 않았다. 이 결과는 실제 CPU 한도 초과 사례이며 인증 만료나 전체 메모리 초과로 바꿔 설명하지 않는다. [Worker CPU·처리 시간과 한도](https://developers.cloudflare.com/workers/platform/limits/)

오류 후 실제 로그인 문서 목록에는 해당 1.2 MiB 문서가 나타나지 않았고 기존 합성 문서의 현재 버전·revision은 유지됐다. 직접 D1/R2 상태와 미게시 객체 부재를 검사한 것은 아니다. 실패한 입력의 편집·복구를 시도하거나 실패를 완료로 집계하지 않았다. 따라서 4 MiB 입력·2,000,000 UTF-16 상한 이하라는 사실은 처리 성공 보장이 아니다. 다음 우선순위는 실제 호스팅에 맞춘 WASM 전 작업량 거부 또는 엔진·호스팅 CPU 경로 보완이다. 해당 실패가 해소될 때까지 큰 문서의 일반 지원과 한도 확대를 선언하지 않는다.
