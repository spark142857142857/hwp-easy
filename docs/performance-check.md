# 합성 HWP 성능·한도 검사

검사일: 2026년 10월 5일. Windows x64, Node 22.17.0, 고정 `@rhwp/core` 0.8.6에서 측정했다. **로컬 기준선과 경계 검증**이며 실제 Sites 지연·전체 isolate 메모리·동시 처리·운영 비용이나 서비스 수준을 인증한 결과는 아니다. 개인 문서와 원격 저장 문서는 사용하지 않았다.

## 재현 방법

개발 환경의 `probes/sites-runtime`에서 실행한다. 사용자용 설치 명령이나 제품 CLI가 아니다.

```sh
npm run test:limits
npm run benchmark:synthetic
npm run profile:large
```

경계 검사는 빌드한 실제 workerd·D1·R2·WASM을 사용하되 신원은 모의 값이고 저장소는 실행 종료 뒤 폐기한다. 외부 네트워크 요청은 금지한다. 성능 도구는 인수·입력 경로를 받지 않고 고정 합성 문서만 메모리에서 생성한다. 보고서는 저장소에서 제외한 `outputs/synthetic-performance/`에 새 파일로 기록한다. 문서 내용·HWP 바이트·OAuth 토큰은 보고하지 않는다.

각 Node 문서는 새 프로세스에서 실행한다. 작은 문서·45셀 양식은 5회, 나머지 정상 사례는 3회 반복하고 회차 사이에 명시적으로 GC를 실행한다. 초과 본문 거부는 1회 확인한다. 초기화와 입력 생성 시간은 별도 기록하며 아래 시간은 첫 회를 제외한 반복의 중앙값이다. 표본이 적고 같은 PC의 다른 작업 영향을 받으므로 처리 시간 보장이나 통계적 백분위로 해석하지 않는다.

## 로컬 엔진 측정

아래 표는 최적화 전 기준선이다. 이어 읽기와 재열기 중복을 줄인 이후 결과는 다음 절에 별도로 남긴다.

시간 단위는 ms다. 끝까지 읽기는 기본 8,000자 응답을 이어 읽고 누락·중복·전체 길이를 검사하는 비용을 포함한다. 편집은 긴 첫 문단을 바꾸는 대신 짧은 마지막 문단 또는 양식 셀 한 곳을 바꾼다. 수정 전 검사도 실제 직렬화·재열기·독립 레코드 보존 검사를 수행한다.

| 합성 사례 | 입력 bytes | 읽기 호출 수 | 열기 | 전체 읽기 | 수정 전 검사 | 편집 | WASM 용량 MiB | 프로세스 최고 RSS MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 작은 본문·표 | 13,312 | 1 | 2.5 | 0.2 | 7.5 | 6.7 | 3.4 | 174.7 |
| 45셀·52블록 양식 | 13,312 | 1 | 6.9 | 0.8 | 22.8 | 21.8 | 3.7 | 240.9 |
| 반복 한글 20만 자 | 44,544 | 26 | 847.3 | 128.7 | 3,432.6 | 3,421.5 | 35.0 | 319.7 |
| 결정적 ASCII 6.4만 자 | 82,944 | 9 | 1,151.2 | 7.5 | 3,897.0 | 3,128.0 | 5.7 | 293.8 |
| 결정적 ASCII 35만 자 | 376,832 | 44 | 859.6 | 152.4 | 3,453.3 | 3,446.2 | 19.3 | 303.7 |

WASM 수치는 실행 후 선형 메모리 **확보 용량**이고 살아 있는 할당의 합계가 아니다. RSS는 초기화·합성 입력 생성·검사·명시적 GC를 포함하는 **Node 프로세스 수명 전체의 최고 값**이다. 단계 끝 `process.memoryUsage()` 값도 원시 보고서에 보관하지만 순간 최대 메모리는 아니다. 256 MiB V8 old-space 설정은 전체 RAM 제한이 아니며, 이 수치를 실제 Worker isolate 사용량과 비교해 안전하다고 판정하지 않는다.

작은 문서·45셀 양식은 첫 페이지 SVG도 측정했다. 큰 단일 문단의 렌더링은 이번 측정에서 제외했다. 모든 완료 사례에서 원본 불변·대상 텍스트·비대상 텍스트와 독립 raw 보존 검사를 확인했으며, 배치 정확성은 미검증이다.

## 이어 읽기와 검증 결과 재사용

같은 날 같은 고정 입력으로 다시 측정했다. 매 응답마다 문단 전체를 문자 배열로 만들고 JSON 복사하던 동작을 없앴다. 보조 평면 문자가 있는 위치만 문서 스냅샷 내부에 보관하고, Unicode code point 기준으로 요청한 조각만 잘라낸다. 응답의 서식 정보는 여전히 깊은 복사이므로 호출자가 바꿔도 스냅샷을 바꾸지 못한다.

공통 엔진이 직렬화 결과를 다시 열어 확인한 모델을 호스트에 함께 반환한다. 호스트는 **동일한 바이트 객체가 유지된 경우에만** 이 검사 결과를 재사용한다. 셀 보존 보정으로 바이트가 바뀌면 새로 열어 검사한다. 원문 검사·정확한 대상/비대상 텍스트·스타일/표 모델·독립 raw 보존 검사는 유지했다. 실제 WASM 생성자 계수 검사에서 일반 편집은 초기 열기를 포함해 4회에서 3회, 보정 편집은 5회에서 4회로 줄었다. 로컬 브리지는 기존 바이트 반환 계약을 유지한다.

| 합성 사례 | 기준선 전체 읽기 ms | 개선 후 전체 읽기 ms | 개선 후 수정 전 검사 ms | 개선 후 편집 ms |
| --- | ---: | ---: | ---: | ---: |
| 작은 본문·표 | 0.2 | 0.5 | 11.0 | 27.4 |
| 45셀·52블록 양식 | 0.8 | 1.4 | 23.1 | 18.3 |
| 반복 한글 20만 자 | 128.7 | 2.7 | 3,343.7 | 2,968.7 |
| 결정적 ASCII 6.4만 자 | 7.5 | 0.8 | 2,157.7 | 2,159.4 |
| 결정적 ASCII 35만 자 | 152.4 | 4.1 | 3,560.8 | 3,764.4 |

반복 한글 20만 자와 ASCII 35만 자의 전체 읽기는 각각 약 98%, 97% 감소했다. 편집·수정 전 검사 시간은 사례별로 섞여 있고 작은 문서의 측정도 흔들렸다. PC 부하가 통제된 A/B 실험이나 편집 시간의 일관된 개선으로 해석하지 않는다. 큰 문서의 직렬화·재열기 비용은 여전히 남아 있다.

120만 자는 기존 60초 **전체** 측정 제한에서 여전히 `limited`였다. 이를 숨기거나 기본 제한을 늘리지 않고, `profile:large`에서 같은 고정 문서의 한 번의 작업을 별도 진단했다. 이 도구만 단계별 45초·전체 180초 제한을 사용하며 제품 설정은 바꾸지 않는다. 입력 생성 28.8초, 열기 8.5초, 전체 읽기 13.2ms, 수정 전 검사 31.4초, 편집 30.8초, 재열기 8.8초, 수정 후 전체 읽기 15.6ms로 완료했다. 대상/비대상 텍스트와 원본 해시·raw 보존 검사를 통과했다. 단일 표본이고 원격 업로드·실제 Worker 요청·미리보기·배치 정확성 검증은 포함하지 않는다.

## 확인된 느린 사례와 개선

120만 자 사례는 입력 생성 약 27.2초, 첫 열기 약 8.1초, 전체 읽기 약 1.75초를 완료한 뒤 첫 수정 전 검사 중 **측정용 자식 프로세스 전체의 60초 제한**에 도달했다. 초기화·입력 생성·여러 검사까지 합한 제한이므로 이를 제품의 개별 호출 시간 초과나 편집 성공으로 표시하지 않는다. 도구는 완료한 단계와 마지막 단계를 보존하고 종료 코드 2 및 `limited`를 반환한다. 예기치 않은 검사 실패는 종료 코드 1이다.

추가로, 본문 2,000,001 UTF-16 code units를 가진 17,408 bytes의 압축 합성 HWP가 엔진 파싱 전에 제한되지 않는 문제를 재현했다. 개선 후 모든 BodyText 텍스트 레코드의 보이는 UTF-16 길이를 **WASM 실행 전에 합산**하며, 2,000,000을 넘으면 `RAW_TEXT_LIMIT_EXCEEDED`로 거부한다. 이 추가 raw 작업량 한도는 본문·셀뿐 아니라 BodyText에 있는 미지원 목록의 텍스트에도 적용한다. 기존 모델 검사와 보존 검사는 유지한다.

실제 압축 합성 HWP를 이용한 검사에서 WASM 생성자를 호출하지 않았고, 로컬 compiled Worker는 약 23.6ms에 거부했다. D1 문서·R2 객체가 생기지 않았으며 입력 해시는 유지됐다. 이 파일은 읽기 거부 전용의 외부 CFB 재구성 사례이며, 정상 편집·서식 호환성 코퍼스에 합산하지 않는다. 정확한 경계에서 100만 이모지의 UTF-16 길이, 여러 구역·셀의 합산, 제어 슬롯·탭·문단 끝 문자의 계산을 별도로 검사했다.

## 업로드·저장 경계

- 전송의 4,194,303 / 4,194,304 bytes는 크기 검사를 통과하고, 4,194,305 bytes는 `TRANSFER_LIMIT_EXCEEDED`로 거부한다. Content-Length 없는 스트림도 같은 경계에서 검사하고 reader를 해제한다. 선언한 길이가 초과하면 reader를 받기 전에 거부한다.
- 위 경계 입력은 형식이 없는 0 바이트 배열이다. 한도 이하에서 HWP 형식 검사로 거부되고 D1/R2는 비어 있음을 확인했다. **유효한 4 MiB HWP의 편집 성공을 검증한 것은 아니다.**
- 작은 문서와 45셀 양식을 로컬 Worker에서 각각 3회 업로드→읽기→수정 전 검사→같은 문서 편집·저장→다시 읽기→다운로드→원본 복구했다. 각 문서의 3개 버전, 다운로드·복구 해시와 비대상 내용이 일치했다. 첫 회 이후 단계 시간 합계는 각각 약 95–102ms와 143–148ms였으며 OAuth·네트워크 지연은 포함하지 않는다.
- 4 MiB 입력·128개 버전 제한과 직접 삭제까지 보관하는 계약은 유지한다. 인증 자동 갱신 문제와 운영 저장 비용은 이번 검사로 해결하거나 인증하지 않는다.

다음 성능 검증은 느린 큰 문서의 원인 분리, 실제 Worker의 JS·WASM 전체 메모리와 동시 요청, 유효한 큰 HWP의 파일 전달·미리보기, 운영 저장 비용이다. 현재 결과를 근거로 사용 한도를 늘리지 않는다.
