# Codex Cloud 지원과 검증 기준

HWP Easy는 로컬 Codex 세션뿐 아니라 새 Codex Cloud 작업에서 HWP를 읽고 수정해 결과를 돌려주는 것을 목표로 한다. 현재 한글 없는 엔진과 로컬 MCP는 구현되어 있고, 원격 Sites 플러그인은 합성 시험만 제공한다. **ChatGPT Work Cloud 채팅의 native MCP 합성 진단은 통과했지만, 저장소를 준비한 Codex Cloud 작업의 연결과 실제 파일 왕복은 아직 검증하지 않았다.**

## 실행 환경과 연결의 구분

Codex Cloud는 게시한 환경에서 도구·저장소·의존성을 준비하고, 작업마다 별도 파일 영역을 사용한다. PC 파일, 실행 중인 프로그램, 브라우저 로그인과 VPN 상태는 자동으로 전달되지 않는다. 따라서 로컬 `testdocs`를 클라우드에서 바로 볼 수 있다고 가정하거나 개인 문서를 시험 때문에 업로드하지 않는다. [Codex 환경](https://learn.chatgpt.com/docs/environments/modes), [클라우드 환경 준비](https://learn.chatgpt.com/docs/environments/cloud-environments)

한글 없는 Node/WASM 경로가 Linux에서 동작하므로 준비된 클라우드 작업 환경에서도 엔진을 실행할 수 있는 구조라는 판단이다. 이는 실제 클라이언트 연결을 완료했다는 뜻이 아니다. 데스크톱에 설치한 플러그인·사용자 인증·첨부 파일이 클라우드 작업으로 그대로 넘어가는지는 따로 시험한다. Agents API의 파일·산출물 기능을 Codex Cloud 앱의 확인된 동작으로 대신 설명하지 않는다.

| 경로 | 현재 확인한 범위 | 남은 검증 |
| --- | --- | --- |
| 로컬 Node와 Python MCP | 합성 HWP 읽기·수정·기본 저장·복구, 실제 MCP SDK 왕복 | 사용자용 간편 연결, 실제 양식 호환성 |
| Linux 실행과 CI | 한글·GUI 없는 합성 문서 처리 | 실제 Codex Cloud 작업과 파일 회수 |
| Sites와 Codex Desktop 플러그인 | 실제 사용자 연결에서 고정 합성 HWP의 조회·계획·D1/R2 저장·복구·정리, 파일 descriptor 전달 후 업로드 게이트의 거부 | 실제 첨부 바이트·HWP 회수·개인 문서·두 OAuth 사용자 격리 |
| ChatGPT Work Cloud 채팅 | 기존 사용자 연결의 native 기능 조회·고정 엔진 진단·합성 문서 저장·복구·기록된 버전 삭제·정리 | 실제 첨부 바이트·외부 다운로드·HWP 회수, 저장소 Codex Cloud와의 별도 검증 |
| Codex Cloud 작업 | 지원 목표 및 검증 기준 정의 | 작업 환경 준비, 실제 도구 연결, 입력부터 HWP 회수까지 전 과정 |
| Dots | 같은 원격 플러그인을 사용하는 지원 목표와 공식 연결 조건 확인 | 실제 Dot의 인증·문서 입력·편집·결과 HWP 회수 |

## 2026-10-03 ChatGPT Work Cloud native 진단

기존 Cloud 채팅 `HWP Easy 연결 검증`에서 설치된 HWP Easy 도구 12개가 노출된 것을 확인했다. 첫 기능 조회는 약 51분 뒤 `UNAUTHORIZED`, `oauth_token_invalid_grant`와 재인증 요청으로 실패했다. 실행 상태가 `inProgress`였다는 사실만으로 엔진이나 문서 작업이 진행 중이라고 판단하지 않는다.

사용자가 기존 연결을 재인증한 뒤 같은 채팅에서 `hwp_capabilities`, `hwp_runtime_probe`, `hwp_workflow_probe`를 각각 한 번 native 호출했다. 세 호출이 모두 완료됐고, 도구 실행 기록의 소요 시간은 각각 약 5.7초·8.6초·23.3초였다. 기능 조회는 업로드 비활성화·빈 파일 origin·직접 삭제할 때까지 보관을 반환했다. 엔진 진단은 고정 합성 HWP의 읽기·편집·재열기·raw 보존·메모리 내 계약을, workflow는 로그인한 사용자 범위의 합성 문서 조회·편집·같은 문서 저장·복구·기록된 버전 삭제·시험 자료 정리를 통과했다.

검증은 같은 비공개 버전 8에서 수행했다. 재시도 사이에 재배포하거나 OAuth 클라이언트·플러그인 ID·MCP 주소·접근 대상·업로드 환경값을 바꾸지 않았다. Cloud 진단 완료 후 Codex Desktop에서도 읽기 전용 기능 조회가 성공했다. 연결 복구를 확인한 것이며 반복 인증 실패의 세부 원인은 미확정이다. [연결 복구 기준](remote-documents.md#연결-오류를-다루는-순서)

실제 첨부 파일 바이트, 로그인한 브라우저의 외부 HTTP 다운로드, 사용자에게 HWP 결과를 돌려주는 경로, 두 OAuth 사용자 격리, Dots와 시각적 배치는 시험하지 않았다. 합성 서버 내부 handler 왕복이나 native 도구 호출을 이 항목의 성공으로 집계하지 않는다. `codex_cloud_client_verified`, `native_file_attachment_verified`, `dots_client_verified`, `layout_verified`는 계속 `false`이며 개인 업로드도 꺼 둔다. 로컬 압축 꼬리 호환성 개선은 이 진단 시점의 버전 8에 아직 게시하지 않았다.

### 비공개 버전 9 배포 뒤 재검증

같은 날 압축 꼬리 호환성과 전송 본문 deadline을 버전 9로 게시한 뒤, 기존 Desktop 연결의 기능 조회·합성 workflow가 성공했다. 같은 ChatGPT Work Cloud 채팅에서도 native `hwp_capabilities`, `hwp_runtime_probe`, `hwp_workflow_probe`를 각각 한 번 호출해 모두 완료됐다. 도구 기록의 소요 시간은 약 1.2초·13.3초·20.6초였다. 기능 조회는 새 `transfer_body_timeout_ms=30000`과 업로드 비활성화를 반환했고 합성 엔진·저장·복구·기록된 버전 삭제·자료 정리가 통과했다.

추가 재인증은 없었다. OAuth 클라이언트·플러그인 ID·MCP 주소·접근 정책·환경 revision 1을 유지했다. 이는 이번 배포에서 기존 연결이 유지됐다는 근거이지 모든 배포·세션에서 연결 만료가 없다는 보장이 아니다. 실제 첨부 바이트·외부 HTTP 다운로드·HWP 회수·두 OAuth 사용자·저장소 기반 Codex Cloud·Dots·시각 배치의 미검증 상태와 개인 업로드 제한은 바꾸지 않았다. [배포와 로컬 검사](../probes/sites-runtime/README.md#비공개-버전-9-전송-시간-제한과-호환성-반영)

## 공통 엔진과 저장 계층

`src/one_hwp/rhwp_api.mjs`는 경로·Node 파일 API 없이 문서 모델을 읽고 수정한다. Node JSON bridge와 browser ESM이 이 코드를 함께 사용한다. `probes/sites-runtime/engine/document.mjs`는 browser ESM에서 바이트 snapshot, SHA-256 기반 대상, 이어 읽기, 계획·편집·미리보기 계약을 제공한다.

메모리 내 snapshot은 caller의 입력 변경과 조회 결과 변경에 영향을 받지 않는다. 수정은 새 HWP 바이트와 검사 결과를 반환하고 `saved: false`를 표시한다. 이 기능만으로 같은 파일 저장, 원격 사용자 격리, 지속 버전과 복구가 구현된 것은 아니다. 파일 연결층이 사용자와 문서를 확인하고 기대 현재 버전과 실제 저장소 버전이 일치할 때만 결과를 저장해야 한다.

읽기는 한 번에 지원 본문 전체를 생략하지 않고, 긴 문단도 이어 읽기를 통해 끝까지 조회할 수 있게 한다. 응답의 이어 읽기 위치는 문서 버전과 연결된 검증 가능한 위치 정보이며, 인증 자격이나 서버가 발급한 비밀 토큰이 아니다. 위치를 바꿔 부분 조회할 수 있고 `content_complete`는 처음부터 이어 읽은 지원 텍스트 범위에만 적용된다. 머리말 등 미지원 내용이 있으면 문서 전체를 읽었다고 표시하지 않는다.

## 실제 Codex Cloud 완료 조건

첫 클라이언트 검증은 개인 문서 대신 합성 HWP를 사용한다. 환경 생성이나 별도 작업 실행은 사용자가 요청한 흐름에서 수행하며, 검증을 이유로 클라이언트 설정·MCP 등록·사용자 문서 공유를 자동 변경하지 않는다.

1. 새 Codex Cloud 작업의 준비된 환경에서 HWP Easy 코드·고정 엔진·필요 의존성에 접근한다. 한글·COM·Wine·GUI 없이 실행해야 한다.
2. 지원하는 파일 전달 방식으로 합성 HWP를 해당 작업에 넣는다. PC 절대 경로나 첨부 URL이 자동 전달된다고 가정하지 않는다.
3. 에이전트가 문단과 표 셀을 구분하고, 긴 내용의 끝과 반복 문구의 위치를 조회한다. 읽기·요약·계획 검사에서 파일은 바뀌지 않는다.
4. 선택한 문단·셀만 수정하고 HWP로 검증해 현재 작업 문서에 기본 저장한다. 사용자가 요청할 때만 다른 이름으로 저장한다. 같은 버전의 동시 수정과 오래된 대상·기존 값 불일치는 거부한다.
5. 저장 후 재열어 대상 텍스트·비대상 내용·스타일·표 구조와 독립 레코드 보존을 검사한다. 저장 전 버전 복구와 실패 시 기존 정상본 보호를 확인한다.
6. 사용자가 작업의 최종 HWP를 회수하고 외부 뷰어로 열 수 있다. 기본 미리보기가 실패해도 HWP 출력과 검사 상태를 혼동하지 않는다.
7. 실행 경로, 실제 파일 전달 방식, 저장 위치와 다운로드·산출물 회수 방법, 미지원 내용과 권한 경계를 기록한다. 서버 실행·CI·합성 도구 호출 성공만으로 이 항목을 통과 처리하지 않는다.

Sites에 인증한 사용자별 개발용 문서 도구와 공식 `fileParams` 입력 계약, 보호된 HWP·SVG 반환 경로를 구현했다. 개인 파일 업로드는 기본 비활성화 상태다. 실제 로컬 workerd의 합성 바이너리 왕복은 통과했지만 클라이언트 첨부 입력·로그인한 브라우저의 HWP 회수, 운영 보관·삭제와 실제 OAuth 격리는 남아 있다. [파일 전달 계약](remote-documents.md)과 [저장 검증 경계](durable-storage.md)를 참고한다. 실제 클라우드 작업 파일에 직접 접근하는 로컬형 어댑터가 더 단순할 수 있지만, 간편 연결과 파일 회수까지 확인한 뒤 배포 경로를 결정한다.

## Dots 연결 목표

공식 안내에 따르면 Dots는 계정에 설치·활성화하고 연결한 지원 플러그인을 기존 권한으로 사용할 수 있다. 같은 HWP Easy 원격 MCP를 재사용할 수 있는 방향이라는 판단이며, 실제 지원 완료를 뜻하지 않는다. 클라우드 컴퓨터는 별도 파일·로그인 상태를 가지고 로컬 PC 연결은 별도 권한이다. [Dots의 컴퓨터와 앱 연결](https://learn.chatgpt.com/docs/dots/computers-and-apps)

실제 Dot에서도 합성 HWP의 입력 → 문단·셀 조회 → 국소 편집 → 현재 문서 저장 → 재열기 → 최종 HWP 회수를 따로 확인한다. 연결 만료·재연결, 파일 전달 범위와 권한 밖 문서 거부도 기록한다. 클라우드 컴퓨터에서 처리한 결과가 PC 원본에 자동 반영된다고 가정하지 않는다. 사용자가 요청하지 않은 Dot 생성·이벤트 구독·상시 감시를 호환성 검증 때문에 추가하지 않는다.
