# Codex Cloud 지원과 검증 기준

Codex Cloud에서 HWP를 읽고 편집한 뒤 결과를 받는 방법과 검증 범위를 정리했다. 한글 없이 실행하는 엔진과 로컬 MCP를 구현했고, 원격 Sites에는 소유자 전용 파일 가져오기 시험 경로를 열었다. 실제 연결 검사는 합성 HWP로 수행했다.

저장소를 준비한 실제 Cloud 작업에서 파일 입력부터 읽기, 편집, 저장, 원본과 편집본의 조각 회수, 독립 바이트 검사, 복구까지 확인했다. 보호된 링크로 편집본을 PC에 내려받는 것도 확인했다. Cloud 결과 첨부 화면과 외부 뷰어의 배치는 아직 검증하지 않았다.

## 실행 환경과 연결의 구분

Codex Cloud는 게시한 환경에서 도구, 저장소, 의존성을 준비하고, 작업마다 별도 파일 영역을 사용한다. PC 파일, 실행 중인 프로그램, 브라우저 로그인과 VPN 상태는 자동으로 전달되지 않는다. 따라서 로컬 `testdocs`를 클라우드에서 바로 볼 수 있다고 가정하거나 개인 문서를 시험 때문에 업로드하지 않는다. [Codex 환경](https://learn.chatgpt.com/docs/environments/modes), [클라우드 환경 준비](https://learn.chatgpt.com/docs/environments/cloud-environments)

한글 없는 Node/WASM 경로가 Linux에서 동작하므로 준비된 클라우드 작업 환경에서도 엔진을 실행할 수 있는 구조라는 판단이다. 이는 실제 클라이언트 연결을 완료했다는 뜻이 아니다. 데스크톱에 설치한 플러그인, 사용자 인증, 첨부 파일이 클라우드 작업으로 그대로 넘어가는지는 따로 시험한다. Agents API의 파일, 산출물 기능을 Codex Cloud 앱의 확인된 동작으로 대신 설명하지 않는다.

| 경로 | 현재 확인한 범위 | 남은 검증 |
| --- | --- | --- |
| 로컬 Node와 Python MCP | 합성 HWP 읽기, 수정, 기본 저장, 복구, 실제 MCP SDK 왕복 | 사용자용 간편 연결, 실제 양식 호환성 |
| Linux 실행과 CI | 한글, GUI 없는 합성 문서 처리 | 이 검사만으로 실제 클라이언트 전송을 인증하지 않음 |
| Sites와 Codex Desktop 플러그인 | 실제 사용자 연결의 고정 합성 파일 입력, 편집, 저장, 복구, 정리와 embedded HWP 회수. Chrome의 합성 문서 저장 → native MCP 문단과 셀 편집 → 저장 버전 미리보기, 이전/현재 HWP 다운로드와 바이트 검사 | 에이전트 앱의 파일 UI, 개인 문서, 두 OAuth 사용자 격리 |
| ChatGPT Work Cloud 채팅 | 기존 사용자 연결의 native 기능 조회, 고정 엔진 진단, 합성 문서 저장, 복구, 기록된 버전 삭제, 정리 | 실제 첨부 바이트, 외부 다운로드, HWP 회수, 저장소 Codex Cloud와의 별도 검증 |
| Codex Cloud 작업 | 게시한 저장소 환경의 native 합성 파일 입력, 전체 지원 내용 조회, 문단/셀 편집, 저장/조각 재시도, 독립 바이트 검사/재열기, 원본 복구. 보호된 편집 버전 링크의 PC 다운로드와 해시 일치 | Cloud 결과 첨부 UI, 일반 사용자 파일, 두 OAuth 사용자 격리, 외부 뷰어와 시각 배치 |
| Dots (추후 확장) | 사용자 결정으로 MVP 지원 대상에서 제외 | 확장 착수 시 실제 Dot의 인증, 문서 입력, 편집, 결과 HWP 회수를 별도 검증. MVP 완료 조건에 포함하지 않음 |

## 현재 연결 검증 상태

10월 9일 로컬 후속 검사에서 같은 계정 Chrome의 운영 합성 저장본에 있는 읽기 요청 복사 버튼을 누른 뒤 한글 2020의 새 빈 문서에 네이티브 `Ctrl+V`로 붙여넣었다. PC 편집기의 다른 합성 문구로 복사, 붙여넣기 기준 검사를 먼저 통과했으며, 실제 붙여넣은 5줄, 350 UTF-16 단위 전체가 보기 화면의 요청과 SHA-256까지 일치했다.

정확한 보기 링크, 문서 ID, 불변 버전 ID와 수정, 저장 금지 지시도 유지됐다. Browser Use의 가상 클립보드 조회와 구분되는 PC 전달 검증 1건이며 ChatGPT 웹 대화 호출, Cloud 결과 첨부 UI나 자동 인증 갱신의 확인은 아니다. 시험 입력은 저장하지 않았고 원격 문서, 버전, 설정, 배포는 변경하지 않았다.

10월 7일 운영 버전 **46**에 혼합 글자 서식을 유지하는 제한된 치환을 반영했다. 한 서식 구간 안에서 글자 수와 각 위치의 UTF-16 길이가 같은 변경만 허용한다. 이번 저장소 Cloud 세션에서 사용자 재연결 뒤 실제 native 기능 조회와 합성 본문, 일반 셀, 병합 셀의 가져오기, 계획, 저장, 정확 재시도, embedded 바이트 회수, 원본 복구를 확인했다.

지원하지 않는 수정은 부분 저장 없이 거부하고 현재 버전, 이력을 유지했다. 회수 바이트의 독립 재현, 재열기와 Python/olefile 스트림, 서식 기록 비교도 통과했다. 로컬 Python/stdio는 혼합 문단의 기존 읽기 전용 제한을 유지한다. 새 화면의 로그인 브라우저 조작, 일반 양식, 외부 프로그램의 시각 배치와 Cloud 결과 첨부 UI는 별도 미검증이다. 재연결 성공을 자동 갱신 해결로 간주하지 않는다.

[지원 계약](remote-documents.md#혼합-글자-서식의-제한된-치환)

10월 6일 CPU 실패 후속 코드에는 원격 본문과 표 셀 합산 **400,000 UTF-16 단위**의 사전 한도와 수정 결과, 복구 원본 검사를 추가했다. 초과는 기존 저장본을 유지하며 재시도를 권하지 않는 안내를 반환한다. 이 후속 변경은 로컬 compiled Worker의 합성 검사와 운영 버전 **45** 배포까지 완료했다. 실제 기능 조회에서 새 한도와 편집 안내 플래그도 확인했다.

기존 연결 성공을 새 한도의 실제 배포 검증이나 OAuth 자동 갱신 해결로 간주하지 않는다. 32,000ms는 앞선 실패의 관측 CPU 사용량이며 설정 한도는 미확인이다. [현재 처리 제한과 검사](performance-check.md#cloud-후속-원격-작업량-사전-검사)

같은 날 사용자가 앱을 재연결한 뒤 이번 Cloud 세션에서 읽기 전용 `hwp_capabilities` 호출이 성공했다. 현재 인증된 기능 조회만 확인한 결과이며 자동 갱신의 연속 동작이나 재인증을 에이전트가 실행할 수 있다는 근거는 아니다. main의 기존 저장본 다운로드, 버전 이력 보기 보완도 운영 버전 45에 반영했다. 배포 뒤 첫 기능 조회에 재연결 오류가 재발했고 사용자가 다시 연결한 뒤 새 한도 조회와 고정 합성 문서의 읽기, 수정, 복구, embedded HWP 회수, 시험 문서 정리가 성공했다.

회수한 바이트는 로컬 독립 재현, 전체 일치, 재열기를 확인했다. 이후 실제 연결에서 합성 399,999단위 가져오기, 전체 조회와 400,001단위 가져오기, 수정 거부, 본문과 셀 합산 400,000단위 저장, 7조각 회수, 독립 재현, 재열기, 복구를 확인했다. 거부 뒤 기존 현재 버전, 이력, 해시가 같았고 명시적 요청으로 이번 시험 문서와 네 버전을 삭제했다. [실제 합성 경계 결과](performance-check.md#운영-버전-45의-합성-경계-검사)

400,000단위 파일의 첫 직접 가져오기는 해당 요청의 전달 origin이 허용 목록 밖이라 네트워크, 바이트 수신 전에 차단됐다. 이후 관측된 정확한 origin의 공개 DNS, HTTPS와 설정 검사를 통과하고 사용자 승인으로 기존 세 주소에 하나만 추가했다.

환경 revision 7로 기존 비공개 버전 45를 재배포한 뒤 같은 합성 파일의 직접 가져오기, 저장 해시 일치, 첫 조각 조회가 성공했고, 400,001단위 입력은 저장 없이 한도로 거부됐다. 기존 시험 버전, 해시를 유지했고 명시적 요청으로 시험 문서와 한 버전을 삭제했다. [설정 후 실제 가져오기](performance-check.md#파일-전달-호스트-설정-후-직접-가져오기)

파일 주소는 요청마다 달라질 수 있으므로 이 성공이 모든 전달 호스트의 허용이나 추가한 특정 호스트를 사용했다는 뜻은 아니다. 미관측 주소는 계속 차단하고 자동 추가하지 않는다. 초과 이전 버전의 실제 서버 복구 거부와 새 화면의 로그인 브라우저 조작은 미검증이다. 설정 준비 중에도 `oauth_token_invalid_grant`가 재발했고 사용자 재연결 뒤 성공했으므로 인증 자동 갱신은 별도 미해결이다. 검증 범위와 남은 제한은 [보기 제한 계약](remote-documents.md#cpu-실패-후속-보완)을 따른다.

2026년 10월 4일 실제 저장소 Codex Cloud 작업에서 고정 합성 HWP 13,312바이트를 생성하고 명시적으로 붙인 HWP Easy native 플러그인에 파일 인수로 전달했다. 지원 내용 10개 블록 전체 조회, 문단, 표 셀 계획/저장, 같은 UUID의 저장 재시도, 원본, 편집본 각각 13조각 회수를 확인했다. 원본 첫 조각과 정확한 재시도 뒤 편집본을 저장하고 원본 나머지를 회수해 버전 고정을 확인했다. Cloud에서 회수 helper의 전체 해시, 실제 엔진 재열기, 독립 생성 바이트 일치를 검사했고 원본 복구 뒤 세 버전이 유지됐다.

복구 후 회수한 편집본도 검증 파일과 바이트 전체 일치했다. Cloud 응답의 보호된 편집 버전 링크로 Chrome에서 실제 파일을 내려받았으며 편집본 해시와 일치했다. Cloud 결과 첨부는 지정 출력 경로의 권한 오류로 제공하지 못했다. 이는 한 사용자, 고정 합성 문서의 실제 전송 실증이며 일반 문서, 첨부 UI, 외부 뷰어, Dots, 시각 배치 완료를 뜻하지 않는다.

이 Cloud 시험 중 기존 연결의 공식 재인증 뒤 기능 조회와 같은 파일, 같은 UUID의 가져오기가 성공했다. 앞선 `FILE_URL_NOT_ALLOWED`의 실제 전달 origin은 관찰하지 못해 원인이 미확정이다. 호스트, 인증 설정을 확대하지 않았고, 이후 검증된 HTTPS origin의 허용 목록 불일치에는 경로, 쿼리, 파일 식별자 없이 안전한 origin 진단을 반환하도록 보완했다. 뒤의 성공을 앞선 거부 원인의 입증으로 해석하지 않는다.

후속 Cloud 첨부 검사에서 시스템 지정 출력 폴더가 없고 해당 부모를 생성할 권한도 없음을 확인했다. 직접 채팅 첨부 도구는 제공되지 않았으며, Page 파일 업로드는 별도의 Page 목적지가 필요해 작업 첨부를 대체하는 것으로 처리하지 않았다. 검증된 작업 파일과 원격 버전은 보존했다. 별도로 이 Cloud 문서의 보호된 보기 화면에서 편집 버전, 복구된 현재 버전, 세 버전 목록과 기본 SVG 미리보기를 확인했다.

두 버전의 다운로드 버튼으로 받은 HWP는 각각 고정 원본/편집본의 독립 생성 바이트와 전체 일치했고 엔진 재열기를 통과했다. 이 브라우저 경로는 확인됐으나 Cloud 첨부 카드와 외부 뷰어, 시각 배치는 여전히 미검증이다. [첨부 제한 시 검증 절차](cloud-client-check.md#결과-첨부가-막힌-경우)

Desktop의 실제 native 도구 결과로 고정 합성 원본과 편집본을 각각 조각 회수해 합성 전용 client helper에서 전체 해시, 엔진 재열기, 독립 생성 바이트 일치를 확인했다. 원본 첫 조각을 받은 뒤 같은 문서에 편집본을 저장하고 원본의 나머지 조각을 회수했으며, 정확한 조각/저장 재시도와 원본 복구도 확인했다. 실제 저장소 Cloud 작업과 파일 UI는 이 Desktop 검사의 범위에 포함하지 않는다. helper는 캡처 입력만으로 실행 클라이언트를 인증하지 않으므로 포괄적인 Cloud, Dots, 첨부 UI 완료 플래그는 계속 거짓이다.

Codex Desktop와 ChatGPT Work Cloud 채팅에서 실제 사용자 연결로 기능 조회, 고정 합성 엔진 진단, 합성 저장, 복구, 정리를 확인했다. 추가로 로컬 Codex에서는 고정된 13,312바이트 합성 HWP를 실제 native 파일 인수로 전달했고, 서버 지문 확인, 편집, 저장, 재열기, 복구, 정리 후 embedded MCP resource를 회수했다. 회수 바이트는 별도 로컬 실행에서 재현한 고정 편집 HWP와 완전히 일치했다. 이는 파일 인수 입력과 MCP 바이트 반환 경로의 제한된 실증이며, 사용자가 누르는 앱 다운로드 UI나 일반 HWP 지원을 인증한 결과는 아니다.

그 뒤 사용자 요청으로 소유자 전용 비공개 배포의 일반 `hwp_import`를 활성화했다. Codex Desktop에서 실제 합성 파일을 가져와 전체 지원 내용 조회, 문단/셀 편집, 같은 원격 문서 저장, 원본/현재 버전 재열기와 정확한 재시도를 통과했다. 이전 버전, 비대상 내용, 기존 보관 문서는 유지됐다. 새 업로드 결과의 보호된 다운로드 주소 반환까지 확인했으며, 이번 결과의 브라우저 수신은 아직 별도다. 개인 문서와 Cloud/Dots 검증으로 확대해서 보고하지 않는다. [소유자 전용 시험 범위](remote-documents.md#소유자-전용-파일-가져오기-시험)

개발 모드 관리 화면의 도구 새로 고침 뒤 웹 목록과 새 로컬 대화에서 13개 도구 및 `hwp_transfer_probe`를 확인했다. 이후 기존 로컬 대화의 새 턴에도 해당 도구가 노출됐다. 반영되지 않은 기존 Cloud 대화의 결과를 전체 클라이언트로 일반화하지 않는다. 새 도구 목록 반영과 사용자 인증은 별개다.

공식 안내도 개발 모드 refresh 후 새 대화에서 재시험하도록 구분하며, 공개 제출 플러그인의 continuous review를 이 비공개 연결의 확인된 원인으로 적용하지 않는다. [OpenAI 개발 모드 도구 갱신](https://developers.openai.com/plugins/deploy/connect-chatgpt#refresh-metadata)

같은 로컬 합성 파일을 반복 전달해도 첨부 descriptor의 정확한 HTTPS origin이 달라졌다. 한 호스트만 설정한 첫 전송은 `FILE_URL_NOT_ALLOWED`로 거부됐고, 이것은 OAuth 오류가 아니었다. 실제 관찰한 공개 DNS 목적지와 유효한 TLS 호스트 인증을 확인한 정확한 origin만 고정 합성 시험에 임시 설정했다. 와일드카드, 일반 업로드 허용은 추가하지 않았고 시험 종료 후 설정을 제거했다. 관찰된 호스트를 자동 신뢰하거나 모든 향후 첨부 호스트가 지원된다고 약속하지 않는다.

서버와 회수 helper의 포괄적인 native UI, Cloud, Dots 완료 플래그는 계속 `false`다. 서버만으로 클라이언트의 실제 파일 표시, 다운로드 조작을 인증할 수 없으며, helper만 실행한 결과도 실제 전송의 근거가 아니다. 위 제한된 실증은 실제 native 도구 결과와 그 결과의 로컬 검사를 함께 확인한 범위다.

재배포, OAuth, 접근 설정을 바꾸지 않은 상태에서도 읽기 전용 호출이 `oauth_token_invalid_grant`로 실패한 사례가 있다. 재인증이 요구되면 사용자 문서 작업과 합성 쓰기 진단을 중단한다. 인증 수명, 갱신 경쟁 등 세부 원인은 미확정이며 서비스 자격으로 사용자 신원을 대체하지 않는다. [연결 오류 처리](remote-documents.md#연결-오류를-다루는-순서)

개인 세션의 시각, 개별 배포, 인증 재시도 이력은 Git에 넣지 않는 `docs/local/`에 둔다. 위 표와 완료 조건에는 재현 가능한 검증 범위와 남은 제한만 유지한다.

이후 실제 저장된 버전의 브라우저 보기 화면과 명시적 고정 합성 문서 생성 경로를 구현했다. 로컬 실제 workerd의 모의 신원으로 읽기 불변, MCP 편집, 불변 버전 링크, 재시작, 삭제 후 접근 차단을 확인했다. 사용자 재인증 뒤 실제 로그인 Chrome에서 고정 합성 문서를 D1/R2에 저장하고, Codex Desktop native MCP로 해당 문단과 셀을 수정해 새 버전을 저장했다.

MCP의 보기 링크에서 수정된 SVG를 표시하고 이전, 현재 HWP를 실제 다운로드했다. 각 해시와 재열기 내용, 별도 로컬 재현의 전체 바이트 일치를 확인했다. 이 시험은 한 사용자의 저장된 합성 문서에 한정하며 일반 개인 파일, 두 사용자 격리, 에이전트 앱의 파일 UI, Codex Cloud/Dots를 인증하지 않는다. [저장 버전 화면](remote-documents.md#저장된-버전의-보기-화면)

별도 브라우저 진단 `/diagnostics/download`에서도 실제 ChatGPT 사이트 로그인 후 버튼을 눌러 HWP를 내려받았다. 받은 13,312바이트의 SHA-256은 `1d3f1472a2637a5fed2672109de946843acd07034756a4273b7fcd43ef159286`이며, 앞선 native MCP 결과와 바이트 전체가 일치했다.

서버에서 동일 고정 편집을 다시 생성하는 읽기 전용 경로로서 D1/R2 문서, 버전 다운로드나 에이전트 앱의 산출물 UI 검증을 대체하지 않는다. 이 배포 뒤 기존 native 기능 조회는 재인증 없이 성공했다. 브라우저 사이트 로그인과 MCP OAuth 연결은 별개다. [브라우저 진단 계약](remote-documents.md#고정-합성-브라우저-다운로드)

## 공통 엔진과 저장 계층

`src/one_hwp/rhwp_api.mjs`는 경로, Node 파일 API 없이 문서 모델을 읽고 수정한다. Node JSON bridge와 browser ESM이 이 코드를 함께 사용한다. `probes/sites-runtime/engine/document.mjs`는 browser ESM에서 바이트 snapshot, SHA-256 기반 대상, 이어 읽기, 계획, 편집, 미리보기 계약을 제공한다.

메모리 내 snapshot은 caller의 입력 변경과 조회 결과 변경에 영향을 받지 않는다. 수정은 새 HWP 바이트와 검사 결과를 반환하고 `saved: false`를 표시한다. 이 기능만으로 같은 파일 저장, 원격 사용자 격리, 지속 버전과 복구가 구현된 것은 아니다. 파일 연결층이 사용자와 문서를 확인하고 기대 현재 버전과 실제 저장소 버전이 일치할 때만 결과를 저장해야 한다.

읽기는 한 번에 지원 본문 전체를 생략하지 않고, 긴 문단도 이어 읽기를 통해 끝까지 조회할 수 있게 한다. 응답의 이어 읽기 위치는 문서 버전과 연결된 검증 가능한 위치 정보이며, 인증 자격이나 서버가 발급한 비밀 토큰이 아니다. 위치를 바꿔 부분 조회할 수 있고 `content_complete`는 처음부터 이어 읽은 지원 텍스트 범위에만 적용된다. 머리말 등 미지원 내용이 있으면 문서 전체를 읽었다고 표시하지 않는다.

## 실제 Codex Cloud 완료 조건

실제 작업 환경 준비, native 입력, 편집, 불변 버전의 조각 회수와 결과 HWP 제공은 [Cloud 합성 파일 왕복 절차](cloud-client-check.md)를 따른다. 합성 전용 회수 helper와 mock 검사는 실행 준비이며 Cloud 완료 근거를 대신하지 않는다.

첫 클라이언트 검증은 개인 문서 대신 합성 HWP를 사용한다. 환경 생성이나 별도 작업 실행은 사용자가 요청한 흐름에서 수행하며, 검증을 이유로 클라이언트 설정, MCP 등록, 사용자 문서 공유를 자동 변경하지 않는다.

1. 새 Codex Cloud 작업의 준비된 환경에서 HWP Easy 코드, 고정 엔진, 필요 의존성에 접근한다. 한글, COM, Wine, GUI 없이 실행해야 한다.
2. 지원하는 파일 전달 방식으로 합성 HWP를 해당 작업에 넣는다. PC 절대 경로나 첨부 URL이 자동 전달된다고 가정하지 않는다.
3. 에이전트가 문단과 표 셀을 구분하고, 긴 내용의 끝과 반복 문구의 위치를 조회한다. 읽기, 요약, 계획 검사에서 파일은 바뀌지 않는다.
4. 선택한 문단과 셀만 수정하고 HWP로 검증해 현재 작업 문서에 기본 저장한다. 사용자가 요청할 때만 다른 이름으로 저장한다. 같은 버전의 동시 수정과 오래된 대상, 기존 값 불일치는 거부한다.
5. 저장 후 재열어 대상 텍스트, 비대상 내용, 스타일, 표 구조와 독립 레코드 보존을 검사한다. 저장 전 버전 복구와 실패 시 기존 정상본 보호를 확인한다.
6. 사용자가 작업의 최종 HWP를 회수하고 외부 뷰어로 열 수 있다. 기본 미리보기가 실패해도 HWP 출력과 검사 상태를 혼동하지 않는다.
7. 실행 경로, 실제 파일 전달 방식, 저장 위치와 다운로드, 산출물 회수 방법, 미지원 내용과 권한 경계를 기록한다. 서버 실행, CI, 합성 도구 호출 성공만으로 이 항목을 통과 처리하지 않는다.

Sites에 인증한 사용자별 개발용 문서 도구와 공식 `fileParams` 입력 계약, 보호된 HWP, SVG 반환 경로를 구현했다. 업로드는 기본 비활성화이며 현재 소유자 전용 시험 배포만 명시적으로 열었다. 로컬 Codex와 실제 저장소 Codex Cloud의 합성 파일 입력, 저장, 재열기, 바이트 회수 및 Chrome 다운로드는 위 범위에서 확인했다.

Cloud 결과 첨부 UI, 일반 사용자 문서, 운영 보관, 삭제와 실제 OAuth 격리는 남아 있다. [파일 전달 계약](remote-documents.md)과 [저장 검증 경계](durable-storage.md)를 참고한다. 실제 클라우드 작업 파일에 직접 접근하는 로컬형 어댑터가 더 단순할 수 있지만, 간편 연결과 파일 회수까지 확인한 뒤 배포 경로를 결정한다.

## Dots 연결 목표

Dots는 사용자 결정으로 **MVP에서 제외한 추후 확장 항목**이다. 아래 연결 방향과 검증 절차는 확장 착수 시의 참고 사항이며 현재 MVP 출시를 막는 미완료 조건이나 지금 실행할 작업이 아니다.

공식 안내에 따르면 Dots는 계정에 설치, 활성화하고 연결한 지원 플러그인을 기존 권한으로 사용할 수 있다. 같은 HWP Easy 원격 MCP를 재사용할 수 있는 방향이라는 판단이며, 실제 지원 완료를 뜻하지 않는다. 클라우드 컴퓨터는 별도 파일, 로그인 상태를 가지고 로컬 PC 연결은 별도 권한이다. [Dots의 컴퓨터와 앱 연결](https://learn.chatgpt.com/docs/dots/computers-and-apps)

실제 Dot에서도 합성 HWP의 입력 → 문단과 셀 조회 → 국소 편집 → 현재 문서 저장 → 재열기 → 최종 HWP 회수를 따로 확인한다. 연결 만료, 재연결, 파일 전달 범위와 권한 밖 문서 거부도 기록한다. 클라우드 컴퓨터에서 처리한 결과가 PC 원본에 자동 반영된다고 가정하지 않는다. 사용자가 요청하지 않은 Dot 생성, 이벤트 구독, 상시 감시를 호환성 검증 때문에 추가하지 않는다.
