# 원격 HWP 저장 계약과 검증 경계

2026년 10월 7일 기준, 내부 D1/R2 저장 서비스와 인증한 사용자별 개발용 문서 도구·바이너리 전송 경로를 구현했다. 업로드는 기본 비활성화이며 사용자가 요청한 소유자 전용 비공개 배포에서만 파일 가져오기와 브라우저 업로드를 열었다. 실제 검증에는 합성 HWP만 사용했고 일반 개인 문서나 운영 편집 지원을 선언하지 않는다. 로컬 실제 workerd에서 저장·재시작·복구와 합성 파일 왕복을, 한 사용자의 실제 Desktop·Cloud·브라우저에서 제한된 문서 흐름을 검증했다. [파일 전달 계약](remote-documents.md), [원격 실행 기록](../probes/sites-runtime/README.md), [MVP 진행 상태](mvp-status.md)에 검증 범위를 구분한다.

## 문서와 버전

D1은 소유자·문서·현재 버전·이전 버전·요청 영수증을 저장하고, R2는 변경하지 않는 HWP 바이트를 저장한다. 모든 문서 조회는 소유자와 문서 ID를 함께 조건으로 사용한다. 문서 연결층은 Sites의 신뢰할 수 있는 인증 결과에서 소유자를 공급하며 사용자 도구 인수·서비스 접근 자격·임의 헤더로 만들지 않는다. 고정 storage 진단의 무작위 시험 이름공간과 로그인한 사용자 범위의 workflow 진단을 구분한다.

버전은 SHA-256과 별개인 새 UUID다. 예전 내용으로 복구해 해시가 같아져도 새 버전과 revision을 만들기 때문에, 복구 전의 오래된 작업이 통과하는 ABA 문제를 막는다. 기본 저장은 같은 논리 문서의 현재 버전 포인터만 갱신하며 직전 정상본은 지우지 않는다. 이것은 PC의 같은 경로 파일을 직접 덮어쓰는 기능이 아니다.

버전 목록과 현재 포인터·revision은 하나의 D1 조회에서 읽고 반환한다. UUID·해시·크기·현재 버전의 존재가 잘못된 메타데이터는 거부한다. 시각이 같은 버전들의 UUID 정렬이 실제 저장 순서라는 보장은 없으므로 명시적인 현재 포인터를 사용한다.

입력은 현재 4 MiB, 문서별 버전은 128개로 제한한다. 한도에 도달하면 저장을 거부하며 자동으로 과거 버전을 삭제하지 않는다. 사용자는 문서와 이전 버전을 직접 삭제할 때까지 보관하는 방식을 선택했다. 자동 만료를 추가하지 않는다. 사용량 정책·새 사본 UX와 미게시 바이트 전체의 정리는 남아 있다.

새 수정·복구의 기대 현재 버전이 다르면 `VERSION_CONFLICT`, 기대 버전은 맞지만 128개 한도에 도달했으면 `DOCUMENT_VERSION_LIMIT`로 구분한다. 두 조건이 함께 보이면 충돌을 먼저 보고한다. 실제 저장소에서 판별한 거부에는 한국어 `save_diagnostic`과 후속 행동을 반환한다. 충돌은 최신 버전과 내용을 끝까지 다시 읽고 대상·수정 의도를 확인한 뒤 새 요청으로 처리하며, 한도는 재시도·자동 삭제·요청하지 않은 다른 문서 저장으로 우회하지 않는다. 삭제 중이거나 접근할 수 없는 문서는 `DOCUMENT_OR_VERSION_NOT_FOUND`로 숨긴다. 확정된 무저장 이후 관찰한 상태만으로 원인을 판단할 수 없으면 `SAVE_GUARD_REJECTED`로 표시하며 원인을 추정하지 않는다. 정확한 기존 요청 재시도는 이 제한 판별보다 먼저 영수증으로 처리한다.

명시적 삭제에는 `hwp_deletions` 영수증을 사용한다. 기대 현재 버전으로 삭제를 확정하면 새 조회·다운로드·저장·복구를 먼저 차단하고 해당 문서의 기록된 R2 버전과 버전·문서 메타데이터를 제거한다. 최소 요청 근거는 남겨 같은 삭제의 재시도와 과거 생성 요청의 부활 차단에 사용한다. 기록된 버전 삭제는 되돌릴 수 없으며 미참조·진행 중 writer·플랫폼 로그·백업 전체의 제거 인증은 아니다. [삭제 계약과 검증](remote-documents.md#보관과-명시적-삭제)

원격 엔진은 압축 해제한 모든 BodyText의 보이는 UTF-16 길이 합계를 WASM 파싱 전에 검사한다. 2,000,000 code units를 넘으면 `RAW_TEXT_LIMIT_EXCEEDED`로 거부하고 저장하지 않는다. 작은 압축 파일도 이 한도에 걸릴 수 있다. 이는 공통 엔진의 상한이며, 운영 원격 서비스에는 더 좁은 **400,000 UTF-16 단위**의 본문·셀 합산 사전 한도가 적용된다. 업로드·새 수정 결과·복구 원본이 이를 초과하면 저장 없이 `HOSTED_WORKLOAD_LIMIT_EXCEEDED`로 거부한다. 기존 8 MiB 본문 압축 해제·모델 검사·4 MiB 입력 제한도 각각 적용하며, 한도 이하의 모든 문서가 편집되거나 정해진 시간 안에 완료된다는 뜻은 아니다. [합성 성능·한도 검사](performance-check.md)

## 검증과 저장 순서

1. 내부 HWP 서비스가 원본을 읽고 계획·기존 값·대상·지원 범위를 확인한다.
2. 수정한 HWP를 엔진으로 재열고 독립 raw 레코드 보존 검사까지 통과한다.
3. 새로운 무작위 R2 키에 바이트를 저장한다. 기존 키를 덮어쓰지 않는다.
4. D1의 원자적인 `batch`에서 기대 현재 버전과 요청 기록을 확인하고 새 버전·현재 포인터·요청 영수증을 게시한다. 같은 버전에 대한 동시 저장은 하나만 성공한다.
5. 영수증으로 확정된 저장 결과를 반환한다. 저장되지 않은 메모리 내 결과와 구분한다.

D1과 R2 전체가 하나의 분산 트랜잭션은 아니다. R2 저장 전 실패나 확정된 버전 충돌이면 현재 문서는 유지된다. D1 응답이 유실되면 영수증으로 성공을 조회한다. 그 조회까지 불가능하면 `COMMIT_OUTCOME_UNKNOWN`을 반환하고 바이트를 삭제하지 않는다. 같은 요청 ID와 같은 의도로 재시도해 확정 결과를 복구한다. 다른 의도로 ID를 재사용하면 거부한다. 이 보수적 처리로 남는 미참조 바이트의 운영 정리 정책은 아직 필요하다.

읽기는 메타데이터의 blob key를 소유자·문서·버전에서 계산한 정확한 키와 대조하고 크기·SHA-256도 확인한다. 손상된 메타데이터가 다른 소유자의 임의 R2 파일을 읽게 하지 않는다. 오류 응답은 고정 코드이고 문서 본문·키·예외 원문을 전달하지 않는다. 플랫폼 전체 로그와 운영 보관 정책은 별도 검증한다.

R2 읽기와 해시 확인이 끝난 뒤에는 선택 버전이 여전히 해당 사용자의 문서에 존재하고 삭제 영수증이 없는지 D1에서 다시 확인한다. 마지막 검사가 실패하거나 저장소가 응답하지 않으면 저장층은 버퍼에 담아 둔 바이트를 반환하지 않는다. 정상 편집으로 현재 버전이 바뀐 경우에는 남아 있는 선택 이전 버전을 계속 읽을 수 있다. 이는 이미 반환·전달된 데이터의 회수나 마지막 검사와 응답 전송 사이 전체의 원자적 접근 철회 보장이 아니다.

저장은 기존 요청 영수증의 정확한 재시도를 먼저 처리한다. 새 바이트를 R2에 쓰기 전 삭제·기대 현재 버전·128개 이력 한도를 검사해 이미 불가능한 저장을 조기 거부한다. 이 조회는 잠금이 아니므로 최종 D1 batch의 같은 조건 검사를 유지한다. 저장 응답을 확인하는 사이 일치하는 영수증의 문서가 삭제되면 `DOCUMENT_DELETION_IN_PROGRESS` 또는 `DOCUMENT_DELETED`를 반환하고 이번 writer가 만든 정확한 임시 키만 정리를 시도한다. 그 외 확정 불가 저장은 계속 `COMMIT_OUTCOME_UNKNOWN`으로 보존하며 광범위한 객체 목록 삭제로 바꾸지 않는다.

## 재현과 남은 검사

`probes/sites-runtime`에서 `npm test`를 실행한다. 실제 workerd의 D1/R2를 임시 디렉터리에 저장한 뒤 runtime을 폐기·재생성해 현재·이전 버전과 재시도 결과를 확인한다. DB 응답 유실·영수증 조회 실패·R2 저장 실패는 명시적으로 주입한 실패이며 실제 장애나 사용자 인증 시험으로 표시하지 않는다. 실제 저장 바이트를 손상시키는 실패 검사도 포함한다.

고정 `/storage-probe`는 소유자 전용 Site 접근 경계에서만 사용할 개발용 POST 진단이다. 입력 본문과 query를 받지 않고 개인 문서를 열지 않는다. 합성 문서의 저장·조회·편집·복구·동시 저장·재시도·서로 다른 합성 소유자의 접근 거부를 시험한 뒤 생성한 데이터만 정리한다. 기존 읽기 전용 MCP 도구에 저장 작업을 숨겨 넣지 않는다.

사용자 범위의 고정 workflow 진단에는 저장 전 내부 준비 handle과 생성 영수증 확인을 추가했다. 첫 저장의 확정 불가 오류도 정확한 시험 문서 범위만 정리하며, 생성 근거가 불확실하면 삭제하지 않고 실패를 알린다. 7개 명시적 실패 주입에서 기존 문서 보존과 정리 제한을 확인했다. 일반 문서의 확정 불가 바이트 보존과 운영 보관·삭제 정책은 이 시험 전용 동작과 구분한다.

`check-deletion-races.mjs`는 실제 임시 D1/R2에서 실행 시점을 명시적으로 멈춰 삭제와 읽기·저장을 겹친다. 삭제 중/완료의 저장층·HTTP HWP 읽기, 읽기 최종 검사 실패, 이전 버전 읽기 유지, 이미 거부할 저장의 R2 쓰기 방지, R2 쓰기 전/후 삭제 우선과 정확한 candidate 정리, 저장 commit 뒤 삭제와 정상/유실 응답을 확인한다. 별도 보존 문서는 매 검사에서 그대로 읽힌다. 이 모의 신원·주입한 시점 시험은 실제 OAuth 철회나 모든 운영 미게시 바이트 GC를 인증하지 않는다.

한 사용자·고정 합성 문서의 실제 Desktop·Codex Cloud 파일 입력·저장·회수·버전 복구와 명시적 시험 문서 삭제는 확인했다. 실제 두 OAuth 사용자 격리·철회, 미게시 바이트를 포함한 운영 삭제, 큰 문서/동시 요청 자원 한도, 일반 양식·정확한 배치와 Cloud 결과 첨부 UI는 미검증이다. Dots는 현재 MVP에서 제외한다. 합성 소유자 격리 성공으로 실제 사용자 검증을 대체하지 않는다.

## 실제 버전 복구와 운영 백업 경계

10월 6일 기존 소유자 계정의 실제 배포에서 376,832 bytes·35만 자 합성 HWP의 마지막 짧은 문단을 수정한 뒤 최초 버전으로 복구했다. 같은 문서에 최초·수정·복구의 3개 불변 버전과 새 현재 포인터가 남았다. 브라우저에서 수정본·복구본을 내려받아 원본과 함께 로컬에 보관했고, 해시·독립 재열기·비대상 원시 레코드 비교를 통과했다. 복구 HWP는 최초 바이트와 같다. 기존 다른 합성 문서의 현재 버전·revision도 유지됐다. [실제 배포 측정과 실패](performance-check.md#실제-소유자-배포의-cpu응답과-복구-검사)

이 흐름은 남아 있는 문서 버전의 복구와 선택한 HWP의 별도 보관을 확인한다. 저장소 자체가 손실된 상황에서의 복구는 아직 검증하지 않았다. 실제 Sites에 연결된 D1/R2의 백업 식별자·보관 기간·내보내기 범위·복원 권한은 이번 도구 응답에 나오지 않았다. [Cloudflare D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)은 데이터베이스의 시점 복구 기능이며 복원은 기존 DB를 덮어쓴다. 이 제품은 HWP 바이트를 R2에 따로 저장하므로, D1 시점 복원만으로 같은 시점의 HWP 바이트나 삭제 영수증과의 일관성이 복구된다고 추정할 수 없다.

운영 복구 완료를 판단하려면 다음 근거가 필요하다.

1. 운영자가 확인한 D1 메타데이터와 기록된 R2 버전의 같은 복구 지점·목록·크기·해시 및 실제 보관 정책.
2. 원본 서비스와 격리된 복구 환경에 해당 데이터를 복원하고 문서·버전·현재 포인터·revision·요청 영수증의 연결을 확인한 결과.
3. 모든 기록된 HWP의 바이트 해시·읽기·재열기, 실제 권한과 정확한 기존 요청 재시도를 확인한 결과. 누락된 바이트는 오류로 남긴다.
4. 삭제 영수증을 반영해 명시적으로 삭제된 문서의 접근과 이전 생성 요청에 의한 부활을 차단한 결과. 백업 보관 중의 삭제 처리 정책도 별도로 명시한다.

현재 운영 DB를 덮어쓰거나 문서를 삭제하는 작업은 이 검사에서 실행하지 않았다. 운영 미게시 바이트 정리·두 실제 OAuth 사용자·전체 메모리·동시 처리·플랫폼 백업 복원은 계속 미검증이다. 로컬 HWP 사본은 문서 내용 보관의 근거이며 원격 메타데이터·권한·이력 전체 백업의 근거가 아니다.

## 독립 로컬 저장소의 합성 복구 시험

2026년 10월 9일 [check-recovery.mjs](../probes/sites-runtime/scripts/check-recovery.mjs)를 추가했다. 실제 로컬 workerd의 D1/R2에서 모의 두 소유자의 합성 문서 2개·불변 버전 4개와 완료된 삭제 영수증 1개를 준비한다. 쓰기가 끝난 시험 환경에서 D1의 네 테이블을 한 batch로 읽고, 기록된 버전의 정확한 R2 키·크기·SHA-256을 확인해 복구 파일에 함께 보관한다. 원래 runtime을 닫고 원본 바이트 Map을 비운 뒤 파일을 다시 열어 별도 새 저장 위치에 합성 데이터만 복사한다. 복구 runtime을 다시 시작해 모든 HWP의 재열기와 이전/현재 버전·revision·표시 이름·이름 변경 번호를 확인한다. 손상된 복구 파일은 새 저장소가 비어 있는 상태에서 거부한다.

최초 생성·편집·복구·이름 변경의 정확한 재시도와 오래된 버전 저장 차단도 복구 후 확인한다. 완료된 삭제 문서의 보기·다운로드·과거 생성 요청 재시도는 계속 거부한다. 같은 이메일·같은 요청 ID를 가진 모의 소유자 둘을 분리하고 compiled Worker의 다운로드·미리보기·타인 접근 거부도 검사한다. 실제 OAuth 사용자 격리나 플랫폼 백업 복원의 성공으로 집계하지 않는다. 임의 개인 파일이나 운영 자격을 받지 않으며 검사를 마친 자기 임시 저장소만 정리한다.

[recovery-audit.mjs](../probes/sites-runtime/scripts/recovery-audit.mjs)는 별도의 읽기 전용 개발 helper다. 스키마·소유자·현재 포인터·버전 수·revision·요청 영수증·삭제 영수증의 연결과 모든 기록된 HWP 바이트의 크기·해시를 검사한다. 잘못된 키·메타데이터는 바이트 조회 전에 거부하고, 누락·손상·조회 실패는 고정 오류로 반환한다. 결과에는 수량과 검증 경계만 넣고 이름·본문·소유자·객체 키·예외 원문을 출력하지 않는다. 복원은 수행하지 않으며 `restored`는 항상 거짓이다. 배포 Worker·HTTP·MCP에는 연결하지 않았다.

삭제 원장은 복구 지점과 독립적으로 확보한 최신 전체 기록을 필수 인수로 받는다. 나중에 삭제된 문서가 예전 자료에 남거나 삭제 영수증이 다르면 `RECOVERY_DELETION_LEDGER_MISMATCH`, 삭제가 진행 중이면 `RECOVERY_DELETION_PENDING`으로 거부한다. 완료된 삭제에서도 버전 수만큼 과거 요청 영수증과 마지막 현재 버전의 요청 기록이 남아 있어야 한다. 이 기록이 빠지면 과거 생성 요청이 새 문서로 받아들여질 수 있으므로 복구 가능한 자료로 판정하지 않는다. helper는 자료의 진본성이나 원장의 최신 여부를 스스로 증명하지 않으며 두 검증 필드는 거짓으로 반환한다. 시험의 고정 원장을 운영 원장 조회로 해석하지 않는다.

helper의 처리 예산은 테이블당 10,000행, 메타데이터 문자열 합계 2,097,152 UTF-16 단위, 버전당 4 MiB와 기록된 바이트 합계 64 MiB다. 이는 오프라인 검사 예산이며 운영 문서의 본문 한도·보관 정책 변경이 아니다. 메타데이터는 복사 전에 한도를 검사한다. 미게시 R2 객체는 이 복구 집합에서 제외하며 전체 객체 백업·정리를 인증하지 않는다.

선택적인 `listBlobPage` 인수로 [storage-inventory-audit.mjs](../probes/sites-runtime/scripts/storage-inventory-audit.mjs)의 읽기 전용 객체 목록 점검을 함께 실행할 수 있다. 기록된 모든 버전의 스키마·소유자·키·바이트 검사를 통과한 뒤 정규화된 전체 객체 목록을 페이지별로 받아 기록된 키와 크기를 대조한다. 기록에 연결되지 않은 HWP 형태의 객체와 그 외 객체는 개수·바이트 합계만 보고한다. 기록된 객체 누락·크기 불일치, 중복 키, 반복 cursor·진행 없는 페이지·조회 실패는 고정 오류로 거부하며 일부 목록을 성공으로 반환하지 않는다. 반환값에 본문·이름·소유자·키·cursor·예외 원문을 넣지 않는다.

목록 점검의 예산은 기록된 키 10,000개, 전체 객체 20,000개, 최대 128페이지, 키와 cursor 각각 1,024 UTF-16 단위, 누적 문자열 4 Mi 단위다. 객체 바이트는 목록 검사에서 추가로 읽지 않는다. 같은 로컬 합성 시험에서 실제 R2를 세 페이지로 읽고 기록된 파일 4개·미게시 파일 1개(13,312바이트)를 구분했으며, 점검 전후 모든 DB 행과 파일 5개의 키·크기·해시가 같았다. 삭제·정리는 수행하지 않았다.

목록의 끝에 도달했다는 사실은 공급자가 전체 자료를 전달했다거나 동시에 쓰고 있는 저장소의 원자적인 시점을 확보했다는 증명이 아니다. 미참조 객체는 진행 중인 저장이나 결과 불명확 상태의 바이트일 수 있으므로 삭제 가능 객체로 판정하지 않는다. `atomic_snapshot_verified`, `listing_completeness_independently_verified`, `unreferenced_objects_deletable`, `cleaned`, `production_GC_verified`는 항상 거짓이다. 운영 점검에는 권한 있는 운영자가 확보한 일관된 전체 메타데이터·객체 목록과 별도의 저장·삭제 경합 확인이 필요하며 운영 GC 완료로 집계하지 않는다.

개발자용 실행 위치는 `probes/sites-runtime`이다.

```sh
npm run test:recovery
```

운영 복구에는 여전히 플랫폼에서 확인한 백업 식별자·보관 범위, 쓰기를 중지하거나 일관성을 보장한 복구 지점, 원래 서비스와 격리된 복원 대상, 복구 지점 이후의 최신 삭제 기록과 실제 권한 검증이 필요하다. 예전 백업의 삭제 충돌을 자동으로 정리하거나 기존 운영 DB를 덮어쓰는 명령은 제공하지 않는다. D1/R2의 함께 복구 가능한 운영 내보내기와 플랫폼 복원 권한은 이번 작업에서 확인하지 않았다.

## 오프라인 복구 파일과 공개 검증 문서의 로컬 복원

[recovery-bundle.mjs](../probes/sites-runtime/scripts/recovery-bundle.mjs)는 검사한 네 테이블과 기록된 불변 HWP 바이트를 단일 `.hwpbak` 파일로 묶고 다시 읽는 개발자용 라이브러리다. 기존 메타데이터 연결·삭제 원장·크기·해시 검사를 통과한 자료만 반환한다. 메타데이터는 비동기 조회 전에 복사하고 각 HWP도 수신 시 복사한다. 재읽기에서는 입력 파일을 복사해 검사하고 바이트를 꺼낼 때도 새 복사본을 반환한다. 호출자의 이후 수정으로 검사한 바이트가 바뀌지 않는다. 배포 Worker·HTTP·MCP와 일반 사용자 흐름에는 연결하지 않았다.

파일 구조는 `HWPEBK01` 8바이트, big-endian uint32 메타데이터 길이·버전 수, UTF-8 JSON 메타데이터, 메타데이터 버전 순서의 SHA-256 32바이트·uint32 바이트 수·HWP 바이트, 앞선 전체 payload의 SHA-256 32바이트다. 메타데이터 파일 인코딩은 최대 16 MiB이며 기존 행·문자열·HWP 예산도 함께 적용한다. 누락·손상·초과·추가 payload와 잘못된 객체 키를 거부하며 파일에 든 경로로 디스크 파일을 쓰거나 저장소를 복원하지 않는다.

파일 checksum은 손상을 확인하는 근거이며 서명·암호화·진본성 증명이 아니다. 파일에는 문서 이름·소유자 구분·요청 기록과 HWP 내용이 들어가므로 비공개로 보관한다. 생성·재읽기 모두 별도로 확보한 최신 삭제 원장을 요구하며 파일 속 삭제 기록을 그 원장으로 자동 사용하지 않는다. 라이브러리만으로 HWP를 엔진에서 열었다고 판단하지 않고 `hwp_format_verified`는 거짓으로 반환한다. 원장 최신성·진본성·플랫폼 복원 검증도 계속 거짓이다.

같은 날 운영 버전 **49**와 한 계정 전용 접근을 읽기 전용 Sites 조회로 확인했다. 도구가 돌려준 다음 offset만 따라 네 테이블의 모든 응답 페이지를 두 차례 읽었고 응답의 행·열·값 잘림이 없었다. 그중 기존 공개 양식 검증 문서 한 개의 메타데이터만 골랐으며 두 관찰에서 문서 1개·버전 3개·요청 기록 3개가 같았다. 두 번째 조회의 해당 문서 삭제 기록을 별도 입력으로 사용했다. 이 일치는 원자적 시점이나 독립적으로 확인한 전체 운영 원장 최신성의 증명이 아니다.

앞서 브라우저로 받은 수정본·복구본의 SHA-256과 크기가 기록된 세 버전과 일치해 **50,127바이트**의 비공개 복구 파일을 만들었다. 새 로컬 D1/R2에 파일을 재읽어 복원하고 runtime을 재시작한 뒤 세 버전 각각의 전체 187블록·해시·현재 포인터·revision·문서 이름·이름 변경 번호를 확인했다. 기존 생성·수정·복구 요청의 정확한 재시도와 오래된 버전 저장 거부 후 모든 로컬 행·블롭 해시가 같았다. 검사를 마친 격리 임시 저장소만 정리하고 복구 파일·수량 중심 결과는 ignored 로컬 기록에 보관했다.

실제 운영 메타데이터와 이전에 회수한 특정 HWP 사본을 함께 복원한 결과이며, 이번에 운영 R2에서 새로 바이트를 내보낸 검사는 아니다. 다른 운영 문서·개인 HWP는 파일에 넣지 않았고 운영 DB·R2·접근·환경·배포를 바꾸지 않았다. 새 로컬 저장소의 내부 서비스 호출이므로 실제 OAuth·분리된 장애 영역·전체 운영 백업·플랫폼 복원 성공으로 집계하지 않는다. 현재 Sites 도구·참조 문서에서 DB 조회는 확인했지만 D1/R2 통합 내보내기와 격리된 플랫폼 복원 경로는 확인되지 않았다. 이것은 플랫폼에 해당 기능이 없다는 판정이 아니다.

## 실제 Sites 조회와 HWP 사본 보관

2026년 10월 9일 기존 소유자 권한으로 운영 버전 46의 배포 성공과 환경 revision 7을 다시 확인했다. Sites의 설정·데이터베이스 화면과 연결 도구에서 `DB`의 `hwp_documents`, `hwp_versions`, `hwp_requests`, `hwp_deletions` 조회를 확인했다. 확인한 데이터베이스 화면에는 테이블 선택·새로고침·행 조회·페이지 이동이 있었으며, D1/R2 통합 내보내기나 복구 지점·복원 대상 선택 기능은 보이지 않았다. 이는 현재 확인한 화면·도구의 범위이며 플랫폼에 백업 기능 자체가 없다는 판정은 아니다. 설정·배포·문서·권한은 변경하지 않았다.

같은 계정 브라우저에서 기존 합성 45셀 문서의 현재 저장본과 이전 저장본 세 개를 각각 내려받았다. 네 사본의 크기는 각각 13,312바이트이며 보기 화면의 버전 ID·SHA-256과 일치했다. 별도 로컬 사본에서 네 파일 모두 전체 52블록(본문 6·셀 문단 46)을 읽고 재열기·원본 바이트 불변을 확인했다. 최초 저장본과 원본 복구본은 서로 다른 버전 ID로 유지되면서 바이트가 같았고, 현재 저장본은 복구본 대비 지정한 한 셀 문단만 달랐다. 나머지 51블록은 일치했다. 마지막 화면에서도 기존 현재 버전과 네 버전의 이력을 유지했다.

이 사본은 HWP 내용의 보관 확인이다. D1의 소유자·현재 포인터·이름·revision·요청·삭제 영수증을 복원하는 자료가 아니며, 같은 PC의 다른 폴더에 둔 사본은 별도 장애 영역의 백업도 아니다. 일반 개인 양식의 호환성·새 조판 검증·운영 복원 성공으로 집계하지 않는다. 보호된 보기·다운로드 링크는 같은 계정의 접근이 필요하다.

운영 백업 경로를 정하려면 플랫폼 담당자에게 다음 사실을 확인해야 한다.

- D1과 기록된 R2 버전 바이트를 함께 확보할 수 있는 내보내기 경로·백업 식별자·보관 기간과 복구 지점의 일관성.
- 기존 운영 저장소를 덮어쓰지 않고 격리된 D1/R2에 복원할 권한·방법과 실패 시 원래 서비스 보존 방법.
- 복구 지점 뒤의 최신 삭제 원장과 삭제된 문서의 과거 요청 영수증을 독립적으로 확보·반영하는 방법 및 백업 안의 삭제 데이터 처리 정책.

소스 버전의 배포 archive는 코드·WASM·manifest를 보관하는 자료이며 사용자 문서 DB와 R2 바이트의 백업으로 취급하지 않는다. 전체 운영 내보내기나 복원을 확인하기 전에는 사용자에게 HWP 사본 보관을 안내하는 기존 원칙을 유지한다.
