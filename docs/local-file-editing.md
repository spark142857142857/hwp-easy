# 로컬 HWP 직접 편집

2026년 10월 11일 구현·검증. Codex가 실행 환경에서 접근할 수 있는 **지정한 HWP 파일을 직접 읽고, 수정 후 같은 경로에 저장**하는 로컬 기능이다. 문서를 서버로 업로드하거나 브라우저·다운로드 링크를 열지 않는다. 기존 원격 플러그인 0.1.9의 심사와는 별개이며 이번 코드를 그 제출본에 반영하지 않았다.

사용자는 파일을 지정하고 바꿀 내용을 요청한다. 에이전트가 읽기, 대상 확인, 저장 전 검사, 수정과 저장 후 재열기를 수행한다.

> 이 로컬 HWP의 ‘지원 동기’ 칸을 다음 두 문단으로 바꿔줘. 같은 파일에 저장해줘.

파일 경로를 지정하면 해당 경로에 저장한다. 대화에 첨부한 사본만 접근할 수 있다면 그 사본을 편집한다. 첨부 사본이 PC 원본 경로와 자동 연결되어 있다고 판단하지 않는다. Cloud에서는 Cloud 실행 환경의 파일을 편집하며 PC 파일이 자동 동기화되지 않는다.

## 추가한 기능

- 기존 본문·표 셀의 텍스트 교체와 빈 칸 채우기. 기존 원격 엔진의 raw 보존·혼합 서식·글꼴 선택 검사를 로컬에서 재사용한다.
- 여러 줄 답변을 **실제 HWP 문단**으로 저장. 표 셀 안의 새 문단과 기존 LF 줄바꿈이 있는 대상도 검사한다.
- 본문 문단 뒤에 새 문단 추가, 직사각형 표 생성과 셀 내용 입력. 기존 문단·표의 위치가 이동해도 비대상 내용을 비교한다.
- 본문 문단 삭제, 인접 본문·셀 문단 병합, 첫 문단 다음의 셀 문단 삭제. 삭제 대상에 숨은 제어가 있으면 저장 전 거부하며 병합할 두 문단의 내용·서식을 확인한다.
- 병합되지 않은 직사각형 표의 행·열 추가/삭제. 지우는 칸의 전체 문단 내용을 확인하고 기존 칸의 위치·서식·헤더 바이트를 보존한다. 새 칸은 인접 칸의 지원 서식을 사용하며 변경 축 방향의 표 크기가 늘거나 줄어든다.
- 검증된 페이지 번호 제어의 원시 바이트를 그대로 보존하면서 다른 지원 대상의 구조 변경을 허용한다. 페이지 번호 자체를 읽거나 바꾸는 기능은 아니다.
- 같은 파일 저장과 저장 전 이전 버전 보관. 요청한 경우에만 Save As를 사용한다. 현재 해시와 다른 파일에는 저장하지 않는다.
- 원본 바이트 복구, 버전에 고정된 이어 읽기, 기본 SVG 미리보기.

구조 변경은 균일 글자 서식의 지원 대상에 대해 한 작업씩 수행한다. 표 행·열 변경은 병합 없는 행 우선 저장과 지원 가능한 균일 표 크기를 요구한다. 첫 셀 문단 삭제, 서로 다른 서식의 문단 병합, 임의 혼합 서식의 재구성, 병합 표의 행·열 변경, 이미지·필드·중첩 표·일반 쪽 배치 변경은 아직 지원하지 않는다. 입력·출력 4 MiB, 일반 모델 2,000,000 UTF-16 단위, 작업 프로세스 60초의 한도를 적용한다. 원격의 400,000 단위 한도는 로컬 실행에 적용하지 않는다.

## 저장과 검증

읽기·미리보기·계획은 파일을 저장하지 않는다. 편집은 현재 파일 해시, 대상 ID와 기존 전체 텍스트를 확인하고, 메모리에서 수정·직렬화·재열기·내용 및 raw 레코드 검사를 거쳐 게시한다. 구조 변경에서는 기존 블록의 위치 이동, 요청한 새 문단/표의 내용, 셀 문단 수와 끝 플래그, 기존 글자/문단 정의 및 다른 스트림을 확인한다.

이전 파일은 같은 폴더의 `.hwp-easy-backups`에 문서별로 연결해 보관한다. 복구할 때도 현재 버전을 새로 보관한다. 이 폴더는 개인 문서를 포함할 수 있어 공유·업로드하지 않는다. 스크립트 간 잠금과 파일 해시 확인을 사용하지만 다른 프로그램 전체를 묶는 OS 트랜잭션은 아니며 Windows ACL·전원 장애 복구와 외부 뷰어의 모든 배치를 인증하지 않았다.

최초 검증은 개인정보 없는 실제 합성 HWP로 수행했다. 한국어·공백 경로의 같은 파일 저장, 무저장 계획, 여러 문단 셀 답변, 새 본문 문단·표 생성, 재열기·기본 SVG·이전 바이트 복구를 **node_modules가 없는 분리 폴더의 실제 패키지 프로세스**에서 통과했다. 별도 Python `olefile`/레코드 판독으로 새 셀 문단·본문·표 텍스트와 기존 글꼴·문단 정의 및 다른 스트림 보존을 확인했다. 이 합성 검사에는 사용자 문서를 사용하지 않았다.

### 사용자 제공 문서의 로컬 복사본 검사

같은 날 사용자가 `testdocs/`의 실문서로 편집 검증을 요청한 뒤 최상위 HWP **3개를 로컬 복사본으로만** 검사했다. 이전 10월 3·5·7일 보고서는 `testdocs/`의 HWP 3개에 대한 읽기·구조 검사였으며 실제 편집·저장 성공 기록이 아니었다. 첫 복사본 검사에서 한 양식의 구조 편집에 `CELL_PRESERVATION_MISMATCH`가 발생했다. pinned writer가 기존 셀 LIST_HEADER의 불투명한 zero word를 `0x0400`으로 바꾸는 현상이 새 구조 경로에서도 발생한 것이다.

기존 헤더 순서·이동된 호스트·전체 셀 문단 수와 나머지 헤더 바이트를 먼저 대조하고 **그 정확한 두 바이트 전이만 원본 값으로 복구**했다. 새 표의 헤더는 바꾸지 않으며 재열기 모델 일치와 전체 raw 보존 검사를 유지한다. 합성 회귀에 셀 여러 문단·본문 문단 추가·표 생성의 zero word 보존과 다른 전이 거부를 추가했다.

첫 단계는 12개 작업 중 9개가 통과하고 첫 문서의 구조 변경 3개가 거부됐다. 후속 조사에서 해당 문서의 미지원 요소는 페이지 번호 제어임을 확인했다. 기존의 엄격한 페이지 번호 원시 바이트 보존 프로필을 구조 편집에도 적용했으며, 읽기 결과는 여전히 부분 지원으로 표시한다. 또한 빈 문단의 표 생성 시 엔진이 현재 문단을 재사용하는 동작을 보완해 선택 문단 **뒤**에 표를 넣도록 했다.

로컬 후보 **0.2.1**로 각 문서에 12개씩, 총 **36개 편집 사례**를 다시 검사했다.

| 익명 문서 | 기존 텍스트·여러 문단 | 새 본문 문단·표 | 본문/셀 문단 삭제·병합 | 직사각형 표 행·열 추가·삭제 |
| --- | --- | --- | --- | --- |
| 1 | 기존 셀에서 통과 | 통과 | 통과 | 통과 |
| 2 | 기존 셀에서 통과 | 통과 | 통과 | 통과 |
| 3 | 기존 본문에서 통과 | 통과 | 통과 | 통과 |

문단 삭제·병합은 실문서에 추가한 시험 문단으로 검증했고, 행·열 네 작업은 실문서에 만든 2×2 시험 표에서 수행했다. 표가 없는 세 번째 문서의 셀 삭제·병합도 새 시험 표에서 확인했다. 원래 병합 표의 행·열 편집으로 확대하지 않는다. 기존 셀/본문 텍스트 치환은 각 원래 양식의 실제 대상을 사용했다.

**36개 모두 무저장 계획 → 같은 사본 경로 저장 → 전체 이어 읽기 → 저장 전 바이트 복구 → 최초 사본 바이트 복구를 통과**했다. 별도 Python/olefile 레코드 판독도 36개 모두 전체 문단 순서, 기존 셀 헤더(요청한 위치·문단 수만 변경), 글꼴/서식 정의·페이지 번호 원시 바이트·다른 스트림 보존을 확인했다. 원본 3개는 모두 불변이며 문서·본문·이름·해시는 전송하거나 공개 기록에 넣지 않았다. 외부 한글 프로그램의 새 배치 비교와 모든 문서의 자유 편집은 미완료다. 익명 집계와 실제 사본은 ignored `outputs/testdocs-local-edit-20261011/expanded-operations-2/`에만 보관한다.

합성 회귀에는 삽입 위치 양 끝·중간, 실제 병합 셀 거부, 삭제할 셀 내용 불일치, 마지막 행 삭제 거부, 다른 문단 서식의 병합 거부, 불투명 셀 값과 요청 밖 표 폭/셀 여백 변조 거부를 포함한다. 패키지의 실제 별도 프로세스로 행·열 추가 후 삭제와 문단 삭제·본문/셀 병합을 연속 수행하고 독립 판독했다. 내용·원시 보존 검증은 화면 배치 인증이 아니다.

## 개발·패키징

소스 실행기: [local_runner.mjs](../src/one_hwp/local_runner.mjs). 복구 가능한 저장: [local_file.mjs](../src/one_hwp/local_file.mjs). 구조 변경 검사: [local_structure.mjs](../src/one_hwp/local_structure.mjs). 직사각형 표 변경: [local_table.mjs](../src/one_hwp/local_table.mjs).

실행 패키지는 Node.js 22 이상과 로컬 파일 권한을 사용한다. 엔진 JS·WASM·압축 해제기와 고지를 포함하며 실행 시 Python·pip·npm 설치나 HWP Easy 인증을 요구하지 않는다. Codex 데스크톱의 번들 Node 경로를 사용할 수 있다. 에이전트가 내부 실행 명령을 수행하므로 사용자가 명령을 입력하는 흐름으로 안내하지 않는다.

개발자가 기존 두 npm lockfile 의존성을 준비한 뒤 실행하는 검사다:

```powershell
node --test tests/test_local_runner.mjs tests/test_local_structure.mjs
node scripts/package_local_plugin.mjs
node scripts/check-local-plugin.mjs
python scripts/check-local-structure.py
python scripts/archive_local_plugin.py
```

생성 패키지는 ignored `outputs/local-plugin-20261011/hwp-easy-local`에 있다. [스킬 소스](../plugins/hwp-easy-local/skills/edit-local-hwp/SKILL.md)는 명시적으로 선택하는 `edit-local-hwp`이며 `allow_implicit_invocation: false`를 유지한다. 개발 후보의 분리 실행 검증과 실제 디렉터리 설치·업데이트·심사는 별개의 단계다. 전역 Codex 설정/MCP 등록, 운영 Sites 배포 및 기존 심사본은 변경하지 않았다.

공식 문서는 스킬의 실행 코드·자원을 패키지에 포함하는 방식을 제공하며, 공개 제출의 로컬 MCP에는 별도 지원 경로를 안내한다. 따라서 로컬 stdio MCP가 누구나 설치하는 디렉터리에 그대로 등록되었다고 주장하지 않는다. [패키지 안내](https://developers.openai.com/plugins/build/plugins), [스킬 안내](https://developers.openai.com/plugins/build/skills).
