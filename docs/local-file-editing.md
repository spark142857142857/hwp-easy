# 로컬 HWP 직접 편집

2026년 10월 11일 구현·검증. Codex가 실행 환경에서 접근할 수 있는 **지정한 HWP 파일을 직접 읽고, 수정 후 같은 경로에 저장**하는 로컬 기능이다. 문서를 서버로 업로드하거나 브라우저·다운로드 링크를 열지 않는다. 기존 원격 플러그인 0.1.9의 심사와는 별개이며 이번 코드를 그 제출본에 반영하지 않았다.

사용자는 파일을 지정하고 바꿀 내용을 요청한다. 에이전트가 읽기, 대상 확인, 저장 전 검사, 수정과 저장 후 재열기를 수행한다.

> 이 로컬 HWP의 ‘지원 동기’ 칸을 다음 두 문단으로 바꿔줘. 같은 파일에 저장해줘.

파일 경로를 지정하면 해당 경로에 저장한다. 대화에 첨부한 사본만 접근할 수 있다면 그 사본을 편집한다. 첨부 사본이 PC 원본 경로와 자동 연결되어 있다고 판단하지 않는다. Cloud에서는 Cloud 실행 환경의 파일을 편집하며 PC 파일이 자동 동기화되지 않는다.

## 추가한 기능

- 기존 본문·표 셀의 텍스트 교체와 빈 칸 채우기. 기존 원격 엔진의 raw 보존·혼합 서식·글꼴 선택 검사를 로컬에서 재사용한다.
- 여러 줄 답변을 **실제 HWP 문단**으로 저장. 표 셀 안의 새 문단과 기존 LF 줄바꿈이 있는 대상도 검사한다.
- 본문 문단 뒤에 새 문단 추가, 직사각형 표 생성과 셀 내용 입력. 기존 문단·표의 위치가 이동해도 비대상 내용을 비교한다.
- 본문 문단 삭제, 인접 본문·셀 문단 병합, 첫 문단 다음의 셀 문단 삭제. 삭제 대상에 숨은 제어가 있으면 저장 전 거부하며 병합할 두 문단의 내용·서식을 확인한다.
- 직사각형 표와 기존 병합 표의 행·열 추가/삭제. 삽입 경계를 가로지르는 병합 셀은 확장하고, 삭제할 행·열을 가로지르는 병합 셀은 축소하며 그 내용을 유지한다. 완전히 삭제되는 칸과 축소되는 병합 칸의 전체 문단 내용을 확인한다. 새 칸은 인접 칸의 지원 서식을 사용하며 변경 축 방향의 표 크기가 늘거나 줄어든다.
- 기존 병합 셀을 원래 격자로 나누기, 완전히 선택한 직사각형 셀 범위 병합. 첫 셀의 문단을 보존하고 다른 셀의 비어 있지 않은 문단을 이어 붙인다. 다른 셀의 빈 문단은 병합 과정에서 제거한다. 나눌 때 전체 폭·높이의 정수 나머지도 유지한다.
- 선택 글자 범위의 글꼴 이름·크기·색·굵게·기울임·밑줄·취소선 변경, 문단 정렬·줄 간격·여백·들여쓰기·문단 전후 간격 변경. 글꼴은 7개 언어별 ID와 필요한 새 이름 정의를 확인하며 기존 정의를 보존한다. 글꼴 파일을 설치하거나 포함하지 않는다.
- 본문·최상위 표 셀의 일반 문단에 여러 로컬 PNG/JPEG 삽입, 그림 번호로 고른 개체의 교체·크기·위치·네 방향 자르기·각도 회전과 제거. 셀 그림은 셀 문단에 인라인으로 저장한다. 교체는 틀 크기·위치·회전을 유지하고 새 이미지 전체를 사용한다. 선택하지 않은 그림과 다른 문단·셀을 보존한다.
- 검증된 페이지 번호 제어의 원시 바이트를 그대로 보존하면서 다른 지원 대상의 구조 변경을 허용한다. 페이지 번호 자체를 읽거나 바꾸는 기능은 아니다.
- 같은 파일 저장과 저장 전 이전 버전 보관. 요청한 경우에만 Save As를 사용한다. 현재 해시와 다른 파일에는 저장하지 않는다.
- 원본 바이트 복구, 버전에 고정된 이어 읽기, 기본 SVG 미리보기.

구조 변경은 균일 글자 서식의 지원 대상에 대해 한 작업씩 수행한다. 병합 표 행·열 변경은 겹침 없는 완전한 격자와 일반 셀 문단을 요구하고, 최대 512행·128열·4,096격자 위치를 검사한다. 새 칸의 서식은 균일해야 한다. 삽입 행 높이·열 폭은 인접 축의 저장 크기를 사용하고, 표시 높이가 더 큰 표의 비율도 유지한다. 확장된 병합 칸에 걸린 삽입 슬롯의 `texts`는 빈 문자열이어야 한다. 셀 나누기·병합은 숨은 개체가 없는 검증 가능한 직사각형을 요구한다. 첫 셀 문단 삭제, 서로 다른 서식의 문단 병합, 임의 혼합 서식 재구성, 그림을 포함한 셀의 표 구조 변경, 그룹 그림·캡션, 필드·중첩 표·일반 쪽 배치 변경은 아직 지원하지 않는다. 그림은 단일 구역·일반 본문/셀 문단당 최대 32개, 삽입·교체는 1 MiB 이하 PNG 또는 8비트 기본/점진 JPEG로 제한한다. 이미지 한 변은 8,192픽셀 이하, 전체는 1,600만 픽셀 이하이며 JPEG는 1개 또는 3개 성분을 지원한다. 그림 제거·교체 후에도 사용하지 않는 이전 이미지 바이트와 복구 사본은 남으므로 민감정보 영구 삭제로 안내하지 않는다. 입력·출력 4 MiB, 일반 모델 2,000,000 UTF-16 단위, 작업 프로세스 60초의 한도를 적용한다. 원격의 400,000 단위 한도는 로컬 실행에 적용하지 않는다.

여러 그림이 있는 문단에서는 현재 읽기에 나온 문단별 `picture_index`와 전체 `expected_properties`로 개체를 선택한다. 추가·삭제 후 번호를 다시 읽는다. 자르기 양은 표시 틀이 아닌 원래 이미지의 크기를 기준으로 하며, 원본 1픽셀당 75 HWP 단위다. 양쪽 합이 원본 크기 이상인 요청은 저장 전에 거부한다. 회전은 -359~359도의 정수이며 외곽 틀·중심·변환 행렬을 함께 저장한다. 각도를 바꾸면 중심을 유지하도록 틀 크기와 위치가 조정된다. PNG/JPEG의 파일 구조 검사는 전체 픽셀 디코더를 대체하지 않는다.

## 저장과 검증

읽기·미리보기·계획은 파일을 저장하지 않는다. 편집은 현재 파일 해시, 대상 ID와 기존 전체 텍스트를 확인하고, 메모리에서 수정·직렬화·재열기·내용 및 raw 레코드 검사를 거쳐 게시한다. 구조 변경에서는 기존 블록의 위치 이동, 요청한 새 문단/표의 내용, 셀 문단 수와 끝 플래그, 기존 글자/문단 정의 및 다른 스트림을 확인한다.

이전 파일은 같은 폴더의 `.hwp-easy-backups`에 문서별로 연결해 보관한다. 복구할 때도 현재 버전을 새로 보관한다. 이 폴더는 개인 문서를 포함할 수 있어 공유·업로드하지 않는다. 스크립트 간 잠금과 파일 해시 확인을 사용하지만 다른 프로그램 전체를 묶는 OS 트랜잭션은 아니며 Windows ACL·전원 장애 복구와 외부 뷰어의 모든 배치를 인증하지 않았다.

최초 검증은 개인정보 없는 실제 합성 HWP로 수행했다. 한국어·공백 경로의 같은 파일 저장, 무저장 계획, 여러 문단 셀 답변, 새 본문 문단·표 생성, 재열기·기본 SVG·이전 바이트 복구를 **node_modules가 없는 분리 폴더의 실제 패키지 프로세스**에서 통과했다. 별도 Python `olefile`/레코드 판독으로 새 셀 문단·본문·표 텍스트와 기존 글꼴·문단 정의 및 다른 스트림 보존을 확인했다. 이 합성 검사에는 사용자 문서를 사용하지 않았다.

### 사용자 제공 문서의 로컬 복사본 검사

같은 날 사용자가 `testdocs/`의 실문서로 편집 검증을 요청한 뒤 최상위 HWP **3개를 로컬 복사본으로만** 검사했다. 이전 10월 3·5·7일 보고서는 `testdocs/`의 HWP 3개에 대한 읽기·구조 검사였으며 실제 편집·저장 성공 기록이 아니었다. 첫 복사본 검사에서 한 양식의 구조 편집에 `CELL_PRESERVATION_MISMATCH`가 발생했다. pinned writer가 기존 셀 LIST_HEADER의 불투명한 zero word를 `0x0400`으로 바꾸는 현상이 새 구조 경로에서도 발생한 것이다.

기존 헤더 순서·이동된 호스트·전체 셀 문단 수와 나머지 헤더 바이트를 먼저 대조하고 **그 정확한 두 바이트 전이만 원본 값으로 복구**했다. 새 표의 헤더는 바꾸지 않으며 재열기 모델 일치와 전체 raw 보존 검사를 유지한다. 합성 회귀에 셀 여러 문단·본문 문단 추가·표 생성의 zero word 보존과 다른 전이 거부를 추가했다.

첫 단계는 12개 작업 중 9개가 통과하고 첫 문서의 구조 변경 3개가 거부됐다. 후속 조사에서 해당 문서의 미지원 요소는 페이지 번호 제어임을 확인했다. 기존의 엄격한 페이지 번호 원시 바이트 보존 프로필을 구조 편집에도 적용했으며, 읽기 결과는 여전히 부분 지원으로 표시한다. 또한 빈 문단의 표 생성 시 엔진이 현재 문단을 재사용하는 동작을 보완해 선택 문단 **뒤**에 표를 넣도록 했다.

로컬 후보 **0.2.1**로 각 문서에 12개씩, 총 **36개 편집 사례**를 다시 검사했다.

| 익명 문서 | 기존 텍스트·여러 문단 | 새 본문 문단·표 | 본문/셀 문단 삭제·병합 | 직사각형 표 행·열 추가·삭제 |
| --- | --- | --- | --- | --- |
| 1 | 기존 셀에서 통과 | 통과 | 통과 | 통과 |
| 2 | 기존 셀에서 통과 | 통과 | 통과 | 통과 |
| 3 | 기존 본문에서 통과 | 통과 | 통과 | 통과 |

문단 삭제·병합은 실문서에 추가한 시험 문단으로 검증했고, 행·열 네 작업은 실문서에 만든 2×2 시험 표에서 수행했다. 표가 없는 세 번째 문서의 셀 삭제·병합도 새 시험 표에서 확인했다. 원래 병합 표의 행·열 편집으로 확대하지 않는다. 기존 셀/본문 텍스트 치환은 각 원래 양식의 실제 대상을 사용했다.

**36개 모두 무저장 계획 → 같은 사본 경로 저장 → 전체 이어 읽기 → 저장 전 바이트 복구 → 최초 사본 바이트 복구를 통과**했다. 별도 Python/olefile 레코드 판독도 36개 모두 전체 문단 순서, 기존 셀 헤더(요청한 위치·문단 수만 변경), 글꼴/서식 정의·페이지 번호 원시 바이트·다른 스트림 보존을 확인했다. 원본 3개는 모두 불변이며 문서·본문·이름·해시는 전송하거나 공개 기록에 넣지 않았다. 외부 한글 프로그램의 새 배치 비교와 모든 문서의 자유 편집은 미완료다. 익명 집계와 실제 사본은 ignored `outputs/testdocs-local-edit-20261011/expanded-operations-2/`에만 보관한다.

합성 회귀에는 삽입 위치 양 끝·중간, 실제 병합 셀 거부, 삭제할 셀 내용 불일치, 마지막 행 삭제 거부, 다른 문단 서식의 병합 거부, 불투명 셀 값과 요청 밖 표 폭/셀 여백 변조 거부를 포함한다. 패키지의 실제 별도 프로세스로 행·열 추가 후 삭제와 문단 삭제·본문/셀 병합을 연속 수행하고 독립 판독했다. 내용·원시 보존 검증은 화면 배치 인증이 아니다.

### 병합 셀·서식·그림의 후속 검사

후속 후보 **0.2.2**에서 실제 패키지로 세 복사본의 새 사례 **19개**를 검사했다. 각 사례는 무저장 계획, 같은 경로 저장, 저장 해시에 고정한 전체 이어 읽기, 이전 바이트의 정확한 복구를 수행했다. 독립 Python/olefile 판독도 19개 모두 통과했고 원본 세 파일은 바이트 불변이다. 기록과 사본은 ignored `outputs/advanced-edit-20261011/real-copy-cases/`에만 보관한다.

| 검사 | 실제 사본 사례 | 결과 |
| --- | --- | --- |
| 글자 크기·색·굵기·기울임·밑줄·취소선 | 기존 지원 대상 3개 | 3/3 |
| 문단 정렬·줄 간격·여백·들여쓰기·전후 간격 | 기존 지원 대상 3개 | 3/3 |
| 원래 병합 셀 나누기 → 같은 범위 병합 | 원래 표가 있는 양식 두 개, 가로 18칸·세로 6칸 | 4/4 |
| 본문 그림 삽입·크기/위치 변경·제거 | 각 실문서 사본에 합성 PNG 삽입 | 9/9 |

원래 문서에는 그림이 없으므로 기존 개인 이미지의 호환성을 인증하지 않는다. 셀 나누기에서 정수 나눗셈으로 소실되던 전체 폭·높이의 나머지를 마지막 칸에 반영했고, 셀 크기 setter의 요청 밖 전체 표 크기 재계산을 피했다. 병합에서도 선택한 셀의 실제 경계 크기 합을 유지하며, 기존 셀 헤더의 요청 밖 값과 페이지 번호를 대조한다. 문단 서식은 기존 54바이트 정의를 보존하고 필요한 새 정의의 58바이트 zero tail만 확인한다. 글자 서식은 코드 포인트 범위와 raw UTF-16 run을 독립적으로 대조한다.

합성 로컬 회귀 **76개**는 기존 55개와 새 21개를 합한 검사다. 새 검사는 이모지·기존 혼합 run의 서식 변경/해제, 셀 텍스트 보존과 병합 경계, 폭의 나머지·불투명 zero word, 그림이 있는 문서의 다른 칸 편집, 잘못된 PNG CRC·이미지 해시·파일 링크, 요청 밖 서식·셀 여백·그림 효과 변조 거부를 포함한다. 분리 폴더 패키지의 연속 편집과 독립 raw 검사도 통과했다. 이 결과는 내용·원시 데이터 보존 검사이며 외부 한글의 화면 배치 검증은 남아 있다.

### 병합 표 행·열, 글꼴 이름과 셀 그림·교체

로컬 후보 **0.2.3**은 `testdocs/`의 세 복사본에서 새 **31개 사례**를 통과했다. 원래 병합 표가 있는 두 문서의 행·열 추가/삭제 8개, 기존 지원 대상의 글꼴 변경 3개, 본문 그림 삽입·교체·크기 변경·제거 12개, 표 셀 그림의 같은 네 작업 8개다. 모든 사례는 실제 패키지의 무저장 계획 → 같은 경로 저장 → 전체 이어 읽기 → 정확한 이전 바이트 복구를 수행했다. 독립 Python/olefile 원시 판독도 **31/31**을 통과했다. 원본 3개는 불변이며 내용·이름·해시는 전송하거나 공개하지 않았다.

병합 표 삭제에서 저장 순서가 행·열 순서와 다른 양식도 실제 좌표로 헤더를 대응했다. 요청 밖 셀의 내용·서식·불투명 헤더 값은 그대로 대조하며, 엔진이 잘못 재계산하는 표 외곽 크기와 병합 셀 크기를 명시한 변경 범위로 보완했다. 글꼴 변경은 실제 언어별 ID와 이름 기록, 기존 혼합 run의 나머지 속성을 확인한다. 셀 그림은 엔진의 표 밖 floating 삽입 결과를 선택 셀 문단의 실제 인라인 개체로 옮겨 저장하며, 크기 변경으로 표의 다른 칸 높이가 바뀌지 않게 한다.

실문서에는 원래 그림이 없어 그림 검사는 합성 PNG를 넣고 **다른 크기의 PNG로 교체**한 범위다. 임의의 기존 개인 이미지, 한 문단의 여러 그림, 외부 한글 화면 배치 인증으로 확대하지 않는다. ignored `outputs/advanced-edit-20261011/extended-copy-cases/`에 검증 사본과 익명 집계를 보관한다. 로컬 회귀 97개, 분리 폴더 패키지의 연속 편집과 원래 파일 복구, 독립 합성 원시 검사 18개도 통과했다. 회귀에는 병합 경계 삽입/삭제, 확장된 병합 칸에 요청 텍스트를 숨기려는 입력의 거부, 기존 병합 내용 확인, 빈 셀과 이모지 위치의 그림 저장·교체를 포함한다. 운영 사이트와 심사 중인 원격 패키지는 이 변경에 포함되지 않는다.

### 여러 그림·JPEG·자르기·회전

로컬 후보 **0.2.4**는 `testdocs/` 세 복사본에서 새 **50개 사례**를 통과했다. 본문 세 곳과 표 셀 두 곳에 PNG·기본 JPEG·점진 JPEG를 함께 넣고, 가운데 그림만 자르기·해제·90도/34도/0도 회전·교체·삭제했다. 각 작업은 실제 패키지의 무저장 계획 → 같은 경로 저장 → 전체 이어 읽기를 수행했고, 각 연속 작업 끝에 원래 바이트로 복구했다. 독립 Python `olefile`/원시 레코드 판독도 **50/50**을 통과했다. 세 원본은 그대로이며 개인 문서·내용·이름·해시는 전송하거나 공개하지 않았다. 원래 이미지가 없는 양식에 합성 PNG/JPEG를 넣은 범위다.

원래 BodyText를 재사용해 선택한 그림과 앵커만 바꾸며 다른 그림·본문·셀 헤더·기존 이미지 스트림을 그대로 비교한다. 실제 셀의 34도 회전이 작은 스트림 저장 공간 경계에서 거부되는 문제를 재현하고, 한 개의 미니 섹터와 필요한 루트/miniFAT 섹터를 각각 최대 하나만 늘리는 로컬 보완을 추가했다. 기존 FAT 용량·다른 스트림의 바이트와 위치는 유지하며 더 큰 할당 변경은 저장 전에 거부한다. 짧아진 압축 BodyText는 허용된 zero tail로 기존 공간을 유지한다. 운영 경로의 구조 보완은 기존 검사를 그대로 사용한다.

로컬 회귀 **105개**, CFB v3/v4의 공간 경계·잘못된 할당 거부 검사 5개, 공통 엔진 34개·가드 회귀, Python 284개(4개 제외)가 통과했다. node_modules 없는 분리 패키지의 합성 그림 연속 작업 **20건**, 기존 연속 편집·복구, 독립 기존 그림/서식 18건과 구조 검사도 통과했다. 이번 그림 20건과 실문서 사본 50건은 Python/Pillow로 합성 raster 디코딩과 크기까지 별도 확인했다. 회귀는 빈 셀·이모지·음수/임의 각도, 회전 후 크기 변경·교체, 다른 그림 보존, 오래된 속성·번호 누락·범위 초과 자르기와 손상 JPEG의 저장 전 거부를 포함한다. 외부 한글 프로그램의 그림 배치 확인은 남아 있다.

교체는 자르기 범위와 저장된 원본 이미지 크기를 모두 새 raster 크기로 갱신하며 틀·회전·선택하지 않은 그림을 보존한다. 검증 사본과 익명 집계는 ignored `outputs/picture-edit-20261011/real-copy-cases-4/`에 보관한다. 원시 변환 행렬은 [고정 RHWP serializer](https://github.com/edwardkim/rhwp/blob/e8800c8def63449808a4092798442652ed460552/src/serializer/control.rs)의 형식을 따르며, JPEG framing은 [ITU-T T.81](https://www.w3.org/Graphics/JPEG/itu-t81.pdf)을 참고했다. 그룹 개체·캡션·그림을 포함한 셀의 구조 변경을 일반 지원으로 확대하지 않는다.

### 한글 2020 화면 확인과 셀 그림 크기 보완

로컬 후보 **0.2.5**는 한글 2020의 실제 화면 비교에서 발견한 셀 그림 크기 오류를 수정했다. 셀에 인라인 그림을 저장할 때 공통 헤더 속성을 `1`로 설정해 절대 폭·높이 기준이 사라졌고, 한글은 크기를 종이 비율로 해석해 그림을 납작하게 표시했다. 인라인 비트와 절대 크기 기준을 함께 유지하는 `0x000a0001`로 보완했다. 이 값은 [한컴 HWP 5.0 형식 revision 1.3](https://cdn.hancom.com/link/docs/%ED%95%9C%EA%B8%80%EB%AC%B8%EC%84%9C%ED%8C%8C%EC%9D%BC%ED%98%95%EC%8B%9D_5.0_revision1.3.pdf)의 공통 개체 속성 표 70에 따른다. 본문·셀 그림의 폭/높이 기준을 회귀와 독립 Python 판독에서 함께 검사한다.

수정한 실제 분리 패키지로 세 `testdocs/` 복사본의 **50/50**, 독립 Python/Pillow **50/50**, 합성 그림 **20/20**과 로컬 회귀 **105/105**를 다시 통과했다. 기존 분리 패키지의 연속 편집·29개 복구 사본·독립 구조 및 고급 편집 검사도 통과했다. 수정 코드 `e538bc7`의 [Linux·Windows CI 네 작업](https://github.com/spark142857142857/hwp-easy/actions/runs/38110386470)은 모두 성공했다.

한글 2020의 **100% 배율**에서 수정 패키지가 저장한 다음 **13개 화면**을 직접 비교했다. 본문 그림은 같은 로컬 패키지의 위치 변경으로 서로 떨어뜨린 비교 사본을 사용했고, 셀 그림은 인라인 배치 그대로 확인했다. 문서 번호는 개인 파일 이름을 대신한 익명 식별자다.

| 문서·대상 | 직접 확인한 화면 | 결과 |
| --- | --- | --- |
| 문서 01 본문 | 여러 그림 중 가운데 JPEG의 34도 회전 | 1/1 |
| 문서 01 넓은 표 셀 | 여러 그림의 나란한 배치와 가운데 JPEG의 34도 회전 | 1/1 |
| 문서 02 본문 | 여러 그림 중 가운데 JPEG의 34도 회전 | 1/1 |
| 문서 02 좁은 표 셀 | 기준 배치, 네 방향 자르기·해제, 90도/34도/0도 회전 | 6/6 |
| 문서 03 본문 | 기준 배치, 네 방향 자르기, 90도/34도 회전 | 4/4 |

선택한 JPEG만 잘리거나 회전했고 나머지 PNG·점진 JPEG의 틀과 방향이 유지됐다. 자르기는 표시 틀을 유지했고 해제하면 전체 패턴이 다시 보였다. 90도와 34도 회전은 중심과 전체 모서리를 확인했으며 0도로 되돌리면 수평 틀이 복원됐다. 본문 그림은 서로 겹치지 않았고, 넓은 셀은 나란히, 좁은 셀은 여러 줄로 표시됐다. 좁은 셀은 그림을 수용하며 행 높이가 늘고 한 문서는 1쪽에서 2쪽으로 재배치됐다. 보이는 인접 칸 경계는 정렬을 유지했다.

그림·화면·개인 문서는 공개하거나 업로드하지 않았다. 화면 비교 중 한글에서 파일을 저장하지 않았고, 검사 후 세 원본과 비교 파일의 바이트를 다시 확인했다. 양식 두 개의 원래 버전 헤더에 대한 한글 2020 상위 버전 안내는 별도 관측이며 헤더를 바꿔 숨기지 않았다. 13건은 지정한 그림 영역의 관찰이고, 모든 50개 작업의 화면 검사나 전체 페이지·글꼴·인쇄·임의의 기존 이미지 배치 인증이 아니다. 그룹 그림·캡션·그림을 포함한 셀의 표 구조 변경은 후속 범위다.

**PNG 색상 추가 비교 2건:** 기존 1×1 회색·알파 PNG는 한글에서 원래 검정 픽셀과 다른 회색 그라데이션으로 표시됐다. 앞의 13건에서 이 PNG의 틀·배치는 관찰했지만 픽셀 표시 성공으로 집계하지 않는다. 별도 64×40 RGB PNG를 실제 패키지로 본문과 표 셀의 첫 그림에 교체한 두 사본에서는 빨강·초록·파랑·노랑 영역과 흰 십자, 기존 틀 크기와 두 JPEG의 보존을 확인했다. 일반 RGB PNG의 두 화면은 통과했으며, 1×1 회색·알파 PNG의 표시 차이 원인은 미해결로 남긴다. 입력 이미지와 저장된 이미지 바이트는 독립 판독에서 같다.

검증 사본은 ignored `outputs/picture-edit-20261011/real-copy-cases-5/`, 추가 비교 사본·로컬 화면·관찰 기록은 `outputs/picture-viewer-20261011/`에 보관한다. 개인 문서 자료를 제외한 로컬 실행 패키지는 `hwp-easy-local-0.2.5.zip`으로 준비했다. 운영 Sites·전역 설치·심사 중인 원격 0.1.9에는 반영하지 않았다.

## 개발·패키징

소스 실행기: [local_runner.mjs](../src/one_hwp/local_runner.mjs). 복구 가능한 저장: [local_file.mjs](../src/one_hwp/local_file.mjs). 구조 변경 검사: [local_structure.mjs](../src/one_hwp/local_structure.mjs). 직사각형 표 변경: [local_table.mjs](../src/one_hwp/local_table.mjs). 병합 셀: [local_merged_table.mjs](../src/one_hwp/local_merged_table.mjs). 병합 표 행·열: [local_merged_axis.mjs](../src/one_hwp/local_merged_axis.mjs). 서식: [local_format.mjs](../src/one_hwp/local_format.mjs). 그림: [local_picture.mjs](../src/one_hwp/local_picture.mjs), [셀 그림 저장](../src/one_hwp/local_cell_picture.mjs).

실행 패키지는 Node.js 22 이상과 로컬 파일 권한을 사용한다. 엔진 JS·WASM·압축 해제기와 고지를 포함하며 실행 시 Python·pip·npm 설치나 HWP Easy 인증을 요구하지 않는다. Codex 데스크톱의 번들 Node 경로를 사용할 수 있다. 에이전트가 내부 실행 명령을 수행하므로 사용자가 명령을 입력하는 흐름으로 안내하지 않는다.

```powershell
node --test tests/test_local_runner.mjs tests/test_local_structure.mjs tests/test_local_advanced.mjs tests/test_local_extended.mjs tests/test_local_pictures.mjs
node scripts/package_local_plugin.mjs
node scripts/check-local-plugin.mjs
python scripts/check-local-structure.py
python scripts/check-local-advanced.py
node scripts/check-local-pictures.mjs
python scripts/check-local-pictures.py
python scripts/archive_local_plugin.py
```

생성 패키지는 ignored `outputs/local-plugin-20261011/hwp-easy-local`에 있다. [스킬 소스](../plugins/hwp-easy-local/skills/edit-local-hwp/SKILL.md)는 명시적으로 선택하는 `edit-local-hwp`이며 `allow_implicit_invocation: false`를 유지한다. 개발 후보의 분리 실행 검증과 실제 디렉터리 설치·업데이트·심사는 별개의 단계다. 전역 Codex 설정/MCP 등록, 운영 Sites 배포 및 기존 심사본은 변경하지 않았다.

공식 문서는 스킬의 실행 코드·자원을 패키지에 포함하는 방식을 제공하며, 공개 제출의 로컬 MCP에는 별도 지원 경로를 안내한다. 따라서 로컬 stdio MCP가 누구나 설치하는 디렉터리에 그대로 등록되었다고 주장하지 않는다. [패키지 안내](https://developers.openai.com/plugins/build/plugins), [스킬 안내](https://developers.openai.com/plugins/build/skills).
