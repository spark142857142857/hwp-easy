# HWP Easy 제품 요구사항 초안

상태: v0.4 검토용 초안 · 비공개 MVP 이후 공개 플러그인 출시 준비 · 갱신일: 2026년 10월 10일

현재 운영 버전 53에서 공개 URL의 익명·위조 신원 요청 거부와 포털의 도메인 소유 확인을 완료했다. 추가 유료 서버 없이 기존 Sites를 유지하는 방향으로, 공개 출시 초안 0.1.8에 실제 Sites client ID와 명시적인 `tokenEndpointAuthMethod=none`을 넣고 사용자가 승인한 현재 계정의 실제 OAuth·콜백·13개 도구 검색을 완료했다. 포털은 Authorized / Configured와 최신 MCP 검사 No findings를 표시했다. 원래 초안은 같은 선언으로 갱신해도 client ID 필요 오류가 남아 있어 새 패키지 식별자 `hwp-easy-public`의 출시 초안으로 연결을 완료했다. 이 결과는 공개 심사·게시, 실제 두 계정 격리나 자동 갱신 해결이 아니다. 호스팅은 현재 공개 베타의 적격 ChatGPT 플랜에 포함되지만 플랜별 사용 한도와 향후 조건 변경 가능성이 있다. 독립 서버 전환은 채택하지 않았다. [현재 출시 근거와 남은 항목](public-plugin-release.md)을 따른다.

10월 6일 CPU 실패 후속 구현은 운영 버전 45에 반영했다. 원격 문서 처리에 본문·표 셀 전체의 **400,000 UTF-16 단위** 사전 한도를 추가했다. 기존 4 MiB 전송·2,000,000 단위 raw 검사와 구분하며 로컬 엔진의 한도를 바꾸지 않는다. 120만 자 처리를 성공시키는 성능 개선이 아니라, 확인된 큰 입력이 WASM·저장에 들어가기 전에 명확히 거부되는 보완이다. 실제 소유자 연결에서 합성 399,999단위 가져오기·400,001단위 거부와 정확한 400,000단위 수정·회수·재열기·복구를 확인했다. 이후 관측된 파일 전달 호스트의 DNS·HTTPS 확인과 사용자 승인 후 정확한 origin 하나를 설정에 추가하고 기존 버전 45를 재배포해, 같은 400,000단위 합성 파일의 직접 가져오기·저장 해시 일치도 확인했다. [검증 범위](performance-check.md#파일-전달-호스트-설정-후-직접-가져오기)를 따른다. 32,000ms는 실패 로그의 관측 CPU 사용량이며 실제 설정 한도는 미확인이다. 새 한도도 모든 허용 문서의 처리 성공을 보장하지 않는다.

HWP Easy의 목표는 **에이전트가 한글 설치 없이 기존 HWP 문서를 이해하고, 필요한 부분을 편집하고, 검증된 HWP로 저장하는 것**이다. 에이전트가 사용할 문서 처리 기능을 중심으로 하되, 사용자가 한글 설치 없이 원본과 편집 결과를 확인할 수 있는 기본 미리보기를 제공한다. 세부 서식과 최종 제출 상태는 사용자가 가진 외부 HWP 뷰어에서도 확인하도록 안내한다. 일반 사용자는 설치 명령이나 파일 내부 구조를 알 필요가 없어야 한다.

현재 저장소에는 기존 Windows COM 프로토타입과 별도로 **한글 없는 WASM 엔진 어댑터와 로컬 stdio MCP의 1차 구현**이 있다. 비공개 Sites에는 제한된 원격 문서 도구와 저장을 구현했고, 사용자의 요청으로 소유자만 접근하는 파일 가져오기 시험을 열었다. 지원 범위가 좁으며 일반 사용자용 배포와 운영 서비스 검증은 끝나지 않았다. 이번 방향 전환은 설치 방식만 다듬는 작업이 아니라 **한글에 의존하지 않는 문서 처리 경로를 만드는 작업**이다. 이 문서는 제품 전체의 구현 완료를 선언하는 명세가 아니라, 사용자가 읽고 방향을 수정할 기준이다.

클라우드 지원은 **새 Codex Cloud 작업에서 HWP 입력부터 결과 회수까지 원활하게 동작한다**는 뜻이다. 한글과 GUI가 없는 Linux에서의 엔진 실행은 필요 조건일 뿐 완료 조건은 아니다. 실제 Codex Cloud 작업의 파일 전달·도구 연결·읽기·수정·저장·결과 회수와 Sites 서버의 실행을 각각 검증한다. Sites 채택, 공개 서비스 운영과 Claude 호환이 이미 확정되거나 구현된 뜻은 아니다. 로컬에서도 한글이 필수여서는 안 된다.

Codex Cloud는 게시한 환경의 저장소·도구·파일을 사용하며, PC의 로컬 파일이나 브라우저 로그인 상태가 자동으로 넘어가지 않는다. 따라서 `testdocs`나 PC의 원본을 자동 공유하거나 원격 편집 결과가 PC 원본에 즉시 저장된다고 가정하지 않는다. 실제 저장소 Codex Cloud 작업에서 고정 합성 파일의 native 입력·읽기·문단/셀 편집·저장·버전 고정 조각 회수·독립 바이트 검사·재열기·복구를 통과했다. 응답의 보호된 편집 버전 링크로 PC 다운로드와 해시 일치도 확인했다. Cloud 결과 첨부 UI, 일반 사용자 문서와 외부 뷰어·시각 배치는 아직 미검증이다. 기존 ChatGPT Work Cloud 채팅의 고정 합성 진단과 별도 실증이며 한 사용자·고정 합성 파일의 성공을 전체 지원으로 확대하지 않는다. [Codex 실행 환경](https://learn.chatgpt.com/docs/environments/modes), [Codex Cloud 환경](https://learn.chatgpt.com/docs/environments/cloud-environments)

### 현재 구현과 검증 범위

1차 로컬 구현은 본문·최상위 표 셀의 조회와 검색, 버전이 고정된 이어 읽기, 수정 계획 검사, 균일 스타일 대상 편집, 같은 파일 저장, 요청한 별도 사본 저장, 이전 버전 복구 및 직접 SVG 미리보기를 제공한다. 읽기와 계획 검사에서는 파일을 변경하지 않는다. 개인정보 없는 합성 HWP 20종과 별도 10개 국소 편집 사례, 실제 stdio MCP 흐름을 Windows와 한글·GUI 없는 Linux에서 검증했다. 이는 임의 양식·시각 배치의 보존 인증이 아니다. [새 엔진 안내](native-engine.md)

원격에는 D1 메타데이터·R2 HWP 바이트 저장, 조건부 저장·복구·재시도와 인증한 사용자별 개발용 문서 도구를 구현했다. 로컬 actual workerd의 신원·네트워크 모의 검사와 비공개 Sites의 실제 사용자 검증을 구분한다. 현재 소유자 전용 배포에서는 `hwp_import`의 업로드 설정과 검증한 정확한 전달 origin 목록을 켰다. Codex Desktop에서 합성 HWP의 실제 로컬 파일 인수 → 가져오기 → 지원 내용 전체 읽기 → 문단·셀 편집 → 같은 원격 문서 저장 → 재열기를 확인했다. 가져오기와 편집의 정확한 재시도는 같은 문서·버전을 반환했고 이전 버전과 비대상 내용은 유지됐다. 이는 일반 가져오기 도구의 실증이며 개인 문서·다른 클라이언트·실제 두 OAuth 사용자 검증은 아니다. 앞선 별도 고정 합성 전달 진단의 embedded HWP 회수와 시험용 합성 호스트 설정 제거 이력은 별도로 유지한다. [저장 계약](durable-storage.md), [파일 전달 계약](remote-documents.md)

일반 업로드와 분리한 고정 합성 전달 진단은 서버 지문과 별도 호스트 설정을 요구한다. 개발 모드의 도구 새로 고침 뒤 새 로컬 대화에서 13개 native 도구를 확인했다. 실제 합성 입력·조회·국소 편집·같은 원격 문서 저장·재열기·복구·시험 문서 정리와 embedded HWP 바이트의 로컬 회수를 통과했다. 회수 바이트는 별도 로컬 실행에서 같은 편집을 재현한 결과와 완전히 일치했다. 추가로 로그인한 Chrome에서 고정 합성 다운로드 버튼을 눌러 받은 HWP가 그 결과와 바이트 전체 일치함을 확인했다. 이 별도 진단은 요청 때 고정 결과만 생성하며, 저장된 사용자 문서의 다운로드·에이전트 앱의 파일 UI·시각 배치·일반 개인 문서 지원을 인증하지 않는다. 반복 재인증 오류의 원인도 미확정이다. 실제 두 OAuth 사용자 격리·운영 로그/삭제·Cloud 결과 첨부 UI·다른 클라이언트 연결과 일반 사용자용 간편 배포는 남아 있다. Dots는 MVP 완료 조건에서 제외한 추후 확장 항목이다. [클라이언트 검증 기준과 연결 상태](codex-cloud.md)

추가로 로그인한 Chrome에서 고정 합성 HWP 한 개를 D1/R2에 보관하고, 같은 사용자의 Codex Desktop native MCP가 해당 문단·셀을 수정해 새 버전으로 저장했다. 저장 버전 화면에서 새 SVG를 표시하고 이전·현재 HWP를 실제 내려받아 저장 해시·재열기 내용·로컬 재현 바이트 일치를 확인했다. 이 제한된 실증은 앞선 저장소 없는 고정 다운로드 진단 및 이후 일반 가져오기 시험과 별개다. 시험 문서와 이전 버전은 직접 삭제할 때까지 보관한다.

모의 두 사용자의 같은 이메일·요청 ID 분리, 문서 도구 8종과 보기·SVG·HWP 경로의 타인 접근 차단 및 거부 뒤 저장 불변을 실제 로컬 workerd/D1/R2에서 검사했다. 삭제와 R2 읽기·저장이 겹치는 시점도 주입해 저장층 반환 전 삭제 상태 재확인, 불가능한 저장의 조기 거부와 삭제 뒤 문서 부활 차단을 확인했다. 이미 전달된 데이터의 회수와 모든 운영 임시 바이트 정리까지 인증한 것은 아니다. 공개 오류는 등록한 고정 코드로 제한한다. 기능 조회는 연결 성공, 업로드 설정과 운영 검증 완료를 별도 상태로 알린다. 비공개 파일 가져오기를 열어도 모의 격리 검사를 실제 두 OAuth 계정 검증으로 집계하지 않으며 `production_ready`는 거짓이다.

이름 있는 필드, 중첩 표, 머리말·꼬리말, 이미지 편집과 일반 혼합 글자 스타일의 수정은 미지원이다. 운영 버전 46에는 기존 한 서식 구간 안에서 글자 수와 각 위치의 UTF-16 길이를 유지하는 제한된 혼합 서식 치환을 제공한다. 합성 본문·셀·병합 셀의 실제 native 저장·회수·복구와 독립 바이트 보존을 확인했다. 로컬 Python/stdio는 혼합 문단의 기존 읽기 전용 범위를 유지한다. [제한과 검증](remote-documents.md#혼합-글자-서식의-제한된-치환)을 따른다. 안전한 조회·보존을 확인하지 못한 레코드와 보안·선택 기능 플래그는 제한하거나 거부한다. 원격 운영 서비스나 제품 전체의 구현 완료로 표시하지 않는다. 개인 문서 검사 결과와 개별 배포 이력은 ignored 로컬 기록으로 분리한다.

원격 문서 계약은 확인된 단일 구역의 쪽 번호 위치 제어(`pgnp`)를 보존 전용으로 허용한다. 고정 길이·루트 문단의 연결 슬롯·모델의 제어 수와 위치가 일치해야 하며 해당 문단은 수정하지 않는다. 다른 지원 문단·셀을 편집해도 제어의 모든 원래 바이트·레코드 순서·연결 슬롯을 독립 검사하고 불일치하면 저장하지 않는다. 합성 네 가지 형태의 편집·재열기, 손실·변조 거부와 actual workerd/D1/R2의 저장·회수를 검사했다. `edit_profile_supported`는 편집 계약이고 `all_content_supported`·`content_complete`는 전체 이해 범위이므로 서로 구분한다. 로컬 stdio의 보수적 차단은 유지하며 다중 구역·다른 제어·임의 실제 문서 저장·서식 정확성까지 인증한 예외는 아니다. [보존 전용 계약](remote-documents.md#쪽-번호-보존-전용-편집)

원격 수정 계획은 실제 편집과 같은 메모리 내 HWP 생성·재열기·독립 레코드 보존 검사까지 수행하되 저장하지 않는다. 대상·기존 값 검사만 통과하고 실제 생성에서 메타데이터가 달라지는 사례를 합성 문서로 재현해 계획 단계에서도 거부하도록 했다. 저장소·현재 버전과 시각 배치는 별도 검사다. `edit_profile_supported`와 계획 성공을 모든 실제 문서의 저장 지원으로 해석하지 않으며, Python 로컬 stdio의 빠른 계획 계약과 구분한다. [사전 검사 계약](remote-documents.md#수정-계획의-저장-전-검사)

고정 writer가 표 셀 목록의 0 word를 기본값으로 바꾸는 동작에 대해서는, 정확히 일치하는 셀 헤더·모델 좌표·문단 수를 검증하고 후보 CFB의 확보된 공간 안에서 원래 두 바이트를 보존하는 제한된 어댑터를 추가했다. 보완 뒤에도 전체 내용·모델·raw 보존 검사를 수행하고 다른 손실과 아래 범위 밖의 할당 변화는 거부한다. 새 일반 HWP writer나 모든 양식 지원을 선언한 것은 아니며 Python 로컬 경로는 그대로다. [셀 목록 보존 계약](remote-documents.md#셀-목록의-0-값-보존)

보완한 동일 raw 바이트의 기본 압축이 후보의 기존 저장 공간 조건과 맞지 않을 때에는 대체 압축 설정을 한 번 시도한다. 한 본문에 64바이트 mini-sector 한 개만 더 필요하면 이미 확보된 mini-stream의 빈 꼬리 공간과 FREE miniFAT 항목을 정확히 검증한 뒤 연결할 수 있다. 파일 길이·일반 FAT·root chain·다른 스트림과 내용 검사는 유지한다. 할당 감소·저장 종류 전환·추가 파일 공간·여러 mini 증가는 지원하지 않으며 경계를 벗어나면 저장하지 않는다. 고정 합성 경계 사례의 무저장 검사·같은 문서 저장·다운로드·재열기를 시험한다.

검증된 후보의 할당 조건 불일치는 고정 오류 코드와 함께 한국어 제한 설명·안전한 숫자 진단을 에이전트에 전달한다. 재인증·디스크 부족과 구분하고, 같은 실패 요청의 무조건 재시도나 요청하지 않은 변경·자동 일부 저장을 권하지 않는다. 개인정보나 임의 오류 속성은 진단에 넣지 않으며 기존 할당 제한 자체를 해결한 기능으로 표현하지 않는다. [실패 피드백 계약](remote-documents.md#할당-조건-실패의-에이전트-피드백)

원격 조회는 보이지 않는 별도 글자 서식이나 검증되지 않은 텍스트 레코드 구조 등 현재 편집 계약에 맞지 않는 대상을 읽기 전용으로 표시하고 한국어 제한 사유를 제공한다. 기존 셀의 검증된 빈 문단은 텍스트 레코드 한 개의 정확한 추가를 독립 검사한 뒤 채울 수 있다. 검증된 일반 텍스트 셀은 해당 텍스트 레코드만 정확히 제거해 원래 문단·셀·서식을 유지한 빈칸으로 만들 수 있다. 새 문단·셀 생성과 서식 변경은 포함하지 않는다. 다른 대상의 읽기와 편집 계약은 유지하지만 실제 저장 전 생성·재열기·raw 검사와 할당 조건은 계속 확인한다. 여러 대상의 실패 요청을 임의로 쪼개 일부만 저장하지 않는다. [대상별 제한](remote-documents.md#조회-단계의-대상별-편집-제한), [빈 셀 채우기](remote-documents.md#기존-빈-셀의-텍스트-채우기), [셀 비우기](remote-documents.md#기존-셀의-텍스트-비우기)

원격 성능·한도 검증에서 압축된 작은 파일의 과도한 본문을 WASM 파싱 전에 거부하도록 보강했다. 모든 BodyText 텍스트 레코드의 보이는 UTF-16 길이 합계를 2,000,000 code units로 제한하며 제어 슬롯과 문단 끝 문자는 제외한다. 기존 모델 검사·4 MiB 입력·보존 검사도 유지한다. 실제 호스팅의 전체 메모리·비용 한도를 인증한 것은 아니다. [성능 측정 범위](performance-check.md)

## 해결할 문제

비공개 MVP 이후 문서 목록 식별 편의를 개선한다. 사용자가 보기 화면에서 직접 입력한 80자 이내 표시 이름을 문서의 소유자별 메타데이터로 보관하며, 원래 파일명이나 HWP 내용을 자동 추출하지 않는다. 빈 이름은 문서 번호 표시로 돌아간다. 이름 변경은 HWP 바이트·현재 버전·저장 이력을 바꾸지 않고, 독립된 이름 변경 번호로 오래된 화면의 덮어쓰기와 중복 재시도를 검사한다. 현재 소유자 전용 접근과 문서 보관·삭제 계약을 유지한다.

실제 저장소 Codex Cloud 검증을 위해 작은 고정 합성 문서의 native 파일 입력·편집·불변 버전 조각 회수·복구·결과 제공 절차와 합성 전용 client 회수 도구를 준비했다. 회수 도구는 전체 해시·실제 엔진 재열기·고정 합성 바이트의 독립 재현 뒤 새 파일로만 게시하며 일반 개인 문서는 받지 않는다. Desktop와 실제 Codex Cloud 작업에서 이 회수 경로를 확인했다. Cloud 결과 첨부 UI와 일반 개인 문서의 호환성은 별도 미검증이다. [Cloud 검증 절차](cloud-client-check.md)

원격 결과 회수는 기존 보호된 브라우저 링크 외에, 명시적인 `delivery: embedded` 요청으로 256 KiB 이하 저장 버전의 전체 HWP 바이트를 MCP resource로 받는 개발 경로를 추가했다. 더 큰 지원 파일에는 `delivery: chunk`로 같은 문서·버전·해시의 바이트를 최대 64 KiB씩 회수하는 경로와 검증 재조립 라이브러리를 제공한다. 총 4 MiB 한도 안에서 누락 없이 합친 뒤 전체 해시·HWP 재열기를 확인해야 완성본이다. 조각은 HWP가 아니며 PC 파일을 자동 저장하지 않는다. 문서·버전·해시와 삭제 상태를 확인하고 읽기로 저장소나 PC 파일을 바꾸지 않는다. 기존 링크도 유지한다. 이 서버 반환 경로와 합성 로컬 재열기 검증을 앱의 파일 UI·PC 원본 자동 저장·Cloud/Dots 지원 완료로 해석하지 않는다. [결과 반환 계약](remote-documents.md#저장된-hwp의-직접-결과-반환)

사용자가 지원서나 과제의 HWP 양식을 에이전트에 주면, 에이전트가 글은 작성해도 원본 양식에 내용을 넣거나 다시 편집 가능한 HWP로 돌려주기 어려울 수 있다. 사용자가 다른 형식으로 변환하거나 한글에 직접 붙여넣는 단계를 줄이는 것이 이 제품의 목적이다. 이 문제와 우선 사용 사례는 이번 대화에서 출발한 가설이며, 시장 전체의 수요를 검증한 결과는 아니다.

에이전트가 실행 환경과 사용자가 부여한 권한 범위 안에서 HWP 파일을 자유롭게 읽고 생성·수정·저장할 수 있도록 한다. 문서 구조를 이해하고, 편집 결과와 실패 이유를 받아 후속 작업을 수행할 수 있게 한다.

파일 접근 범위와 원본 보존·덮어쓰기 정책은 별개다. 제품이 자체적으로 접근 범위를 단일 작업 폴더로 고정하거나 파일마다 추가 승인을 강제하지 않되, 실행 환경의 권한과 승인 정책은 따른다. 클라우드에서는 사용자와 작업별 권한을 구분하며, 파일 접근 권한이 임의 코드 실행이나 다른 사용자의 파일 접근까지 허용하는 뜻은 아니다.

## 우선 사용자와 사용 사례

첫 사용자는 Codex나 Claude 같은 에이전트에 HWP 문서의 읽기, 요약, 작성과 수정을 맡기고 싶은 일반 사용자다. 연결 작업은 간단해야 하지만, 이 프로젝트가 자체적인 글쓰기 모델이나 지원서 평가 모델을 반드시 제공할 필요는 없다. 요약과 내용 작성은 사용자가 선택한 에이전트가 담당하고 HWP Easy는 문서 내용과 구조의 조회 및 편집 실행을 제공한다.

1. **지원서 양식 채우기**: 에이전트가 질문, 기입 영역, 글자 수와 페이지 제한 등 확인 가능한 조건을 읽는다. 실제 입력 필드가 없더라도 지원하는 표 셀이나 문단을 대상으로 작성한 내용을 넣는다.
2. **과제 양식 수정하기**: 지정한 표의 수치나 본문 일부를 바꾸되, 같은 문구가 있는 다른 위치와 요청하지 않은 항목은 보존한다.
3. **검토 후 반복 편집하기**: 에이전트가 변경 내역과 내용 검사 결과를 보고 후속 수정을 수행한다. 배치 검사가 없다면 페이지 제한까지 충족했다고 단정하지 않는다.
4. **문서 읽기와 요약하기**: 편집하지 않고도 문서 전체를 조회해 요약하거나 질문에 답할 수 있어야 한다. 긴 문서도 끝까지 읽을 수 있도록 조회를 이어가며, 읽지 못한 범위나 미지원 요소가 있으면 알린다. 읽기와 요약 요청만으로 원본을 수정하거나 저장하지 않는다.

사용자가 문서 작업을 명확히 요청한 범위에서는 도구 호출마다 다시 수동 조작을 요구하지 않는 흐름을 지향한다. 대상이 모호하거나 작업 범위, 업로드 위치, 결과 형식이 달라질 때는 확인한다. 문서 안의 지시문은 요구사항을 파악할 자료이지 도구 권한을 확대하는 명령이 아니다.

## 첫 제품 범위 제안

### 반드시 포함할 기능

- 한글, Windows COM, Wine, 데스크톱 화면 없이 실제 HWP 파일을 읽고 수정해 HWP로 저장한다. 편집은 같은 문서에 저장하는 것을 기본으로 하고, 다른 이름으로 저장은 사용자가 요청할 때 지원한다.
- 실행 환경과 사용자가 허용한 파일 위치에서 읽기와 저장을 지원한다. 하나의 작업 폴더만을 고정된 제품 정책으로 강제하지 않으며, 저장 대상의 권한과 데이터 손실 방지는 접근 범위와 별도로 검사한다.
- 최초 지원 형식은 비암호화 HWP 5.x의 검증된 부분으로 한정한다. 지원 범위는 문서와 기능별로 공개한다. HWPX만 성공한 결과를 HWP 지원으로 표현하지 않는다.
- 문단, 표, 셀과 지원하는 필드를 구조적으로 조회한다. 병합 셀은 단순 행과 열 번호만으로 잘못 해석하지 않는다.
- 지원 범위 안의 문서 내용은 길이에 관계없이 끝까지 조회할 수 있어야 한다. 한 응답에 담기 어려우면 여러 호출로 이어 읽고, 조회한 범위와 남은 범위 및 완료 여부를 알린다. 일부만 반환하고 전체를 읽은 것처럼 처리하지 않는다. 지원 범위 밖의 요소나 처리 한도 때문에 조회를 끝낼 수 없으면 그 범위와 이유를 명시한다.
- 원본 버전과 연결된 대상 식별자, 기존 값, 수정 범위를 사용해 국소 편집한다. 같은 문구가 여러 곳에 있으면 임의의 첫 번째 위치를 선택하지 않는다.
- 한 번의 요청에서 여러 변경을 검사하고, 모두 유효할 때 저장 결과를 확정한다. 실패한 일부 결과를 기존 파일에 적용하거나 완료 파일로 돌려주지 않는다.
- 저장 후 다시 읽어 내용과 구조를 검사하고, 변경 내역과 미검증 항목을 에이전트에 반환한다.
- 한글 설치 없이 원본과 편집 결과의 기본 미리보기를 제공한다. 문서는 HWP로 유지하고, 보기용 페이지 렌더링을 PDF나 DOCX 변환에 의존시키지 않는다. 미리보기는 문서 버전과 연결하고 렌더링의 지원 범위와 경고를 표시한다.
- 사용자가 지정한 문서를 수정해 달라고 요청하면 별도의 저장 요청 없이 검증된 결과를 같은 문서에 저장한다. 저장하지 말라는 요청은 따른다. 갱신 전 버전은 복구할 수 있게 보관하고, 검증 실패나 버전 충돌이면 기존 파일을 바꾸지 않는다. 무관한 기존 파일은 임의로 덮어쓰지 않는다.
- PDF와 DOCX는 기본 실행 경로의 입력, 중간 파일, 출력으로 생성하지 않는다.
- MCP로 문서 기능을 제공하고, 클라이언트에 맞는 간편 연결 경로를 마련한다. 일반 사용자가 Python이나 pip 명령과 설정 파일 편집을 해야 하는 흐름을 정상 사용 경험으로 요구하지 않는다.

### 후순위 기능

Dots 연결은 사용자의 결정으로 MVP에서 제외한다. 추후 확장할 때 기존 원격 MCP 재사용과 실제 Dot의 인증·파일 입력·편집·HWP 회수를 별도 검증한다. MVP 작업 중 Dot 생성·연결·검증을 진행하지 않는다.

표 행 추가, 문단 삽입과 삭제, 스타일 수정, 이미지 교체, 새 문서 생성은 다음 범위 후보이다. 에이전트가 텍스트 치환만 할 수 있는 제품으로 영구 고정하지는 않되, 첫 범위에 모두 포함하지도 않는다. 필요한 기능을 실제 사용자 작업과 엔진 지원 범위로 결정한다.

### 첫 범위에서 제외할 기능

HWPX·PDF·DOCX 변환과 내보내기는 선택 기능이나 후속 개발 항목으로 남기지 않고 제품 범위에서 제외한다. 필요할 때는 사용자가 가진 한글이나 별도 변환 도구를 이용하는 흐름으로 둔다. 기본 미리보기는 제공하지만, 사람이 직접 조작하는 전체 편집 UI나 일반 워드프로세서의 메뉴와 편집 화면을 만드는 일은 제품 목표로 두지 않는다. 편집 내용과 검증 결과의 보고는 이 제외 범위와 별개로 유지한다.

HWP 97, 암호화와 DRM 해제, 편집 제한 우회, 임의 매크로 실행, 전체 한글 기능의 재구현, 자동 포털 제출, 모든 문서의 픽셀 단위 동일성 보장은 제외한다. 미지원 문서는 안전한 거부와 이유를 제공하며, 다른 형식으로 몰래 바꾸거나 한글 설치를 요구하는 경로로 자동 전환하지 않는다.

## 배포와 에이전트 연결

첫 배포 후보는 **Sites에 호스팅하는 원격 MCP와 이를 연결하는 플러그인**이다. 별도 전체 편집 앱이나 Windows 설치형 프로그램을 먼저 완성하는 순서는 우선하지 않는다. MCP는 에이전트가 문서 기능을 호출하는 공통 연결 규격이고, 플러그인이나 확장 패키지는 사용자가 그 연결을 쉽게 설치하는 배포 수단이다. 실제 HWP 처리는 별도의 문서 엔진이 담당한다.

2026년 10월 1일의 공개 발표는 ChatGPT Sites에서 MCP 서버를 만들고 배포한 뒤 플러그인으로 연결하는 흐름과 접근 대상 제한·공개 공유를 설명한다. 이것은 배포 후보를 검토할 근거이지, HWP 엔진의 실행이나 Claude 연결을 입증하는 근거는 아니다. [Tibo의 발표](https://x.com/thsottiaux/status/2105519215092584786), [인용된 Max Stoiber의 발표](https://x.com/mxstbr/status/2105428405571428785)

### 첫 사용 흐름

비공개 사이트에는 로그인 후 HWP를 직접 선택하는 `/documents/upload` 화면을 구현한다. 기존 업로드 설정과 소유자 검사를 유지하고, 명시적인 버튼 전송 후 저장된 버전의 보기·다운로드로 연결한다. 파일 선택만으로 업로드하지 않으며 PC 원본은 변경하지 않는다. 응답 확인 실패의 같은 화면 재시도는 동일 파일·요청 ID를 유지한다. 이 UI가 일반 파일 호환성·운영 서비스 검증을 대신하지 않는다.

사용자는 연결을 설치하고 인증한 뒤, HWP를 업로드하거나 허용된 저장소의 문서를 선택해 읽기, 요약 또는 수정을 요청한다. 에이전트는 MCP로 필요한 내용과 구조를 조회한다. 읽기와 요약은 파일을 변경하지 않는다. 수정 요청에서는 편집과 검증 후 현재 문서에 저장하는 것이 기본이며, 사용자가 요청할 때만 별도 이름이나 경로로 저장한다. 사용자는 기본 미리보기와 검사 결과를 확인하고 저장된 HWP를 내려받을 수 있다. 편집마다 저장 방식을 선택하는 수동 절차를 요구하지 않는다.

클라이언트에 첨부한 파일이 MCP 서버에 자동 전달된다고 가정하지 않는다. 업로드와 결과 다운로드의 경로, 파일의 소유자와 문서 버전을 확인할 수 있어야 한다. 원격 MCP가 사용자 PC의 원본까지 직접 덮어쓰는 흐름은 첫 원격 검증에 포함하지 않는다. PC 파일의 직접 저장은 추후 명시적으로 연결한 로컬 MCP 등 별도 경로로 제공하며, 제품의 같은 파일 저장 요구사항을 없애지 않는다.

### 채택 전에 확인할 조건

- Sites의 실제 배포 환경에서 엔진과 필요한 글꼴을 실행해 HWP 읽기, 국소 편집, 저장과 재열기를 검증한다. MCP 초기화나 모의 도구 호출 성공만으로 문서 편집이 된다고 판단하지 않는다. 지원 가능한 파일 크기와 처리 시간·메모리 한도도 확인한다.
- 플러그인을 연결하고 문서 접근을 허용한 사용자는 그 범위에서 자기 문서를 읽고 수정·저장할 수 있어야 한다. 제품 자체가 파일마다 추가 승인을 반복해서 요구하지 않되, 실행 환경의 권한과 승인 정책은 따른다. 원격 연결만으로 PC의 모든 파일에 접근할 수 있는 것은 아니며, 원격에서는 업로드한 문서나 접근을 허용한 저장소의 문서를 사용한다. 다른 사용자의 문서에는 접근할 수 없어야 한다.
- 접근 권한 철회와 연결 해제, 사용자 간 격리, 저장 전 버전의 복구, 원문을 남기지 않는 로그 및 파일 보관·삭제 정책을 시험한다. 공개 연결은 다른 사람도 도구를 연결할 수 있다는 뜻이지, 개인 문서를 공개한다는 뜻이 아니다.
- ChatGPT, 로컬 Codex, Codex Cloud에서 설치·인증·도구 호출 및 파일 전달을 각각 직접 시험한다. Codex Cloud의 실제 작업에서 합성 HWP를 입력하고 전체 읽기·요약·수정·기본 저장·재열기·HWP 결과 회수를 완료해야 클라우드 클라이언트를 지원한다고 표시한다. Linux CI나 Sites 도구 호출 성공으로 이 검증을 대체하지 않는다. Claude Desktop과 Claude Code의 연결과 인증도 각각 검증한다. 한 클라이언트의 플러그인이 다른 실행 환경에 자동 전달된다고 약속하지 않는다.
- 미리보기 UI가 없는 클라이언트에서도 편집과 HWP 결과 반환을 사용할 수 있어야 한다. 필요한 보기 화면은 선택적인 연결 UI나 브라우저 화면으로 제공하며, 전체 워드프로세서를 만들지는 않는다.

Sites가 문서 처리나 필수 클라이언트 연결 조건을 충족하지 못하면 해당 조건을 완화하거나 인증을 제거하지 않는다. 다른 호스팅 또는 로컬 연결을 평가하고 변경할 배포 방향을 사용자와 확인한다. 공통 HWP 엔진과 표준 MCP 계약은 특정 호스팅의 인증·저장소·UI 코드와 분리해 재사용한다. 현재 비공개 Sites와 같은 계정의 Codex Desktop·Codex Cloud에서 고정 합성 HWP의 입력·편집·저장·결과 회수를 확인했다. 일반 사용자 문서의 원격 편집·저장과 추가 클라이언트 연결, 인증 자동 갱신의 연속 동작은 미검증이다. [클라이언트별 확인 범위](codex-cloud.md)를 적용한다. 로컬 설정을 자동 변경하거나 서비스 접근 자격을 사용자 신원으로 해석하지 않는다.

## 편집 후 저장하는 방식

기본 동작은 **현재 문서에 저장**이다. 사용자가 특정 HWP를 수정해 달라고 요청하면, 에이전트는 요청 범위의 변경을 검증하고 같은 문서에 저장한다. 사용자가 매번 저장을 따로 요청하거나 저장 방식을 선택할 필요는 없다. 읽기와 요약만 요청했거나 저장하지 말라고 한 경우에는 원본을 변경하지 않는다.

**다른 이름으로 저장**은 기능으로 제공하되, 원본을 유지한 별도 사본이나 다른 경로를 사용자가 요청할 때만 수행한다. 별도 대상이 이미 존재하면 그 파일을 교체할 의도가 확인돼야 한다. 현재 문서의 편집·저장 요청을 무관한 기존 파일의 덮어쓰기 권한으로 해석하지 않는다.

저장 대상은 실행 환경에서 접근 권한을 가진 문서다. 로컬에서는 사용자가 선택한 파일을 갱신하고, 클라우드에서는 해당 사용자의 작업 영역에 있는 현재 문서를 새 버전으로 갱신한다. 업로드한 문서를 편집했다고 사용자 PC에 있는 원본까지 자동으로 바뀌는 것은 아니다. PC 파일을 갱신하려면 별도로 승인된 로컬 연결이 필요하다.

지정한 문서를 편집하는 작업 범위 안에서는 저장마다 제품 자체의 추가 승인을 반복해서 요구하지 않는다. 실행 환경의 권한과 승인 정책은 따른다. 편집 대상이나 요청 범위가 모호하면 먼저 확인하고, 다른 문서로 저장 대상을 임의 변경하지 않는다.

내부적으로는 편집 결과를 임시 산출물에 작성하고 내용과 구조를 검증한 뒤, 변경 전 버전을 복구할 수 있는지와 대상의 현재 버전을 확인한다. 그 다음 실행 환경에 맞는 안전한 교체 방식으로 저장한다. 검증·복구 준비·교체에 실패하거나 다른 작업의 변경 또는 파일 잠금이 발견되면 기존 파일을 훼손하지 않고 원인을 보고한다. 안전하게 교체할 수 없는 환경에서는 실패를 알리며, 저장 경로나 방식을 몰래 바꾸지 않는다.

저장 전 버전의 보관 위치와 기간, 디스크 사용량, 클라우드의 삭제 정책은 일반 사용자 배포 전에 정한다. 복구용 사본도 원문과 같은 권한 보호를 받고, 별도 승인 없이 외부 서비스에 업로드하지 않는다. 1차 로컬 구현은 지정한 백업 폴더에 이전 버전과 복구 메타데이터를 보관하며 자동 삭제 정책은 없다. 안전한 실패·충돌·복구 검사는 있지만 프로세스 강제 종료, 모든 저장소와 Windows ACL 보존을 인증한 것은 아니다. 기존 COM 프로토타입은 여전히 새 출력만 지원한다.

## 사용자가 문서를 확인하는 방식

기본 미리보기에서 사용자는 원본과 편집 결과의 페이지를 선택해 내용을 확인할 수 있어야 한다. 보기용 페이지는 HWP에서 직접 렌더링한 SVG나 PNG 등의 표시 자원을 사용하며, 최종 편집 산출물은 HWP로 유지한다. 버전·페이지와 연결된 SVG와 저장된 버전의 브라우저 보기 화면을 구현했다. 화면은 사용자 소유권·선택 버전을 확인하고 HWP 다운로드, 수동 SVG 이미지, 페이지 이동과 이전 버전 링크를 제공한다. 앱 안의 파일·미리보기 UI는 미구현이다. 실제 한 사용자의 Chrome 합성 문서 저장, Codex Desktop native MCP 문단·셀 편집, 새 저장본의 SVG 표시와 이전·현재 HWP 다운로드·해시·재열기를 실증했다. 일반 개인 문서·두 OAuth 사용자 격리·시각 배치 보존은 별도 미검증이며, 모의 신원의 실제 workerd 검사와 구분한다. Codex Cloud는 고정 합성 HWP의 편집·회수·보호된 링크 다운로드를 확인한 범위로 한정한다. 결과 첨부 UI와 일반 문서 사용은 별도 미검증이고 Dots는 현재 MVP에서 제외한 추후 확장 항목이다.

연결된 에이전트 앱의 표시 기능을 사용할 수 있으면 앱 안에서 보여주고, 해당 기능이 없으면 브라우저의 보기 화면 등 대체 경로를 제공한다. 미리보기 화면을 지원하지 않는 클라이언트에서도 에이전트의 읽기와 편집 도구는 사용할 수 있어야 한다.

편집 전 버전과 저장된 HWP를 내려받아 사용자가 가진 외부 뷰어에서 확인하는 경로도 제공한다. 세부 글꼴, 복잡한 표와 수식, 정확한 줄바꿈과 쪽 나눔, 최종 제출 상태는 외부 HWP 뷰어에서도 확인하도록 안내한다. 외부 뷰어의 재현 수준도 다를 수 있으므로, 특정 제출 환경과의 일치를 보장하지 않는다. 외부 뷰어 설치를 기본 사용의 전제나 서버 편집 엔진의 의존성으로 삼지 않는다.

미리보기를 생성하거나 사용자가 열었다는 사실만으로 서식 검증 완료라고 표시하지 않는다. 글꼴 대체, 렌더링하지 못한 요소, 내용 검사와 배치 검사의 상태를 구분해서 알린다. 미리보기 실패 시 원본이나 편집 결과 파일의 검사 상태와 별도로 보고하고, 확인하지 못한 배치를 정확하다고 설명하지 않는다.

## 에이전트가 사용할 기능 계약 제안

아래는 제품의 개념적 계약이며, 구현 범위를 전부 달성했다는 뜻은 아니다. 1차 로컬 MCP의 7개 도구와 실제 입력·결과 계약은 [개발자 안내](native-engine.md#에이전트-도구)에 별도로 기록한다. 원격 계약과 이름·분리는 배포 검증 후 조정할 수 있다.

| 기능 | 에이전트가 받거나 지정할 정보 | 필요한 조건 |
| --- | --- | --- |
| 기능 확인 | 엔진 버전, 지원 형식과 편집 기능, 실행 한도 | 한글 실행이나 설정 변경 없이 조회한다. |
| 문서 내용과 구조 조회 | 문서 버전과 해시, 본문과 표 셀의 내용 및 식별자, 필드, 지원 상태, 조회 범위와 이어 읽는 방법 | 지원하는 전체 내용을 빠짐없이 조회할 수 있어야 한다. 여러 호출로 나눌 때도 같은 버전을 끝까지 읽고 완료 여부를 확인한다. 미지원 요소나 조회 실패는 누락 범위와 함께 알린다. |
| 대상 검색과 조회 | 검색 결과의 문맥, 표 위치, 실제 기존 값 | 중복 대상은 구분하고 식별자를 원본 버전에 묶는다. |
| 수정 계획 검사 | 변경할 대상과 기존 값, 예상 변경, 지원 여부 | 파일을 쓰지 않는 검사와 실제 적용을 구분한다. |
| 수정 적용과 저장 | 허용된 작업 묶음, 원본 해시, 저장 대상과 기대 버전, 요청된 경우의 다른 이름 저장 정보 | 편집한 현재 문서에 검증 후 저장하는 것이 기본이다. 다른 이름으로 저장은 사용자 요청이 있을 때만 수행한다. 오래된 버전이나 조건 불일치면 적용하지 않으며, 같은 파일 갱신은 복구할 이전 버전을 확보한다. |
| 미리보기 조회 | 문서 버전과 페이지, 보기용 자원, 렌더링 경고 | 편집과 분리된 읽기 기능이다. 기본 미리보기 제공을 서식 정확성 보증으로 표현하지 않는다. |
| 결과 검증과 반환 | 저장된 HWP의 경로와 버전, 저장 방식, 변경 내역, 검사 근거, 복구 정보와 경고 | 내용, 구조, 배치 검사 상태를 별도로 표시한다. |

전체 조회는 한 번의 도구 응답이나 모델 문맥에 문서 전체를 반드시 넣는다는 뜻이 아니다. 긴 문서는 버전이 고정된 내용을 여러 번 이어 읽으며, 다음 조회 위치와 완료 여부를 제공한다. 도중에 버전이 바뀌면 서로 다른 버전의 내용을 섞지 않고 다시 조회해야 함을 알린다. 에이전트가 전체 문서 요약을 요청받았을 때는 조회를 끝까지 수행하고 그 내용을 바탕으로 요약한다. 조회 실패나 미지원 요소가 남으면 요약이 어느 범위를 다뤘는지 알리고 전체를 읽었다고 보고하지 않는다.

내부 라이브러리와 구조화된 도구 계약을 중심에 두고 MCP로 에이전트에 연결한다. 제품용 CLI는 계획에 포함하지 않으며, 일반 사용자는 플러그인이나 MCP 연결을 통해 문서 작업을 요청한다. Codex나 Sites 전용 구현에 문서 엔진을 묶지 않으며, 원격 MCP에는 인증과 사용자별 저장 영역을 설계한다. 배포와 클라이언트 연결은 앞의 채택 조건을 따른다.

같은 쓰기 요청을 재시도해 산출물이 중복 생성되거나 같은 변경이 반복 적용되지 않도록 요청 식별과 결과 조회 방식을 정한다. 동시 수정이나 버전 충돌은 현재 문서를 읽은 뒤 계획을 다시 만드는 방식으로 처리한다. 스킬의 명시 호출 설정은 MCP의 인증이나 문서별 권한 검사 대신이 아니다.

Dots는 추후 확장 후보이며 현재 MVP의 지원 대상과 검증 일정에서 제외한다. 확장 착수 시 같은 원격 MCP와 플러그인의 재사용 가능성, 파일·로그인·로컬 연결 권한을 다시 확인한다. 자동 작업·이벤트 구독·상시 문서 감시를 MVP 요구사항으로 추가하지 않는다. [확장 시 참고할 Dots 연결 안내](https://learn.chatgpt.com/docs/dots/computers-and-apps)

## 문서 보존과 검증 기준

파일을 저장할 수 있다는 사실과 내용을 보존했다는 사실은 다르다. 자기 엔진으로 재열기만 성공한 결과를 한글과의 호환성이나 배치 정확성까지 입증한 결과로 보고하지 않는다.

| 검사 | 확인할 내용 | 확인하지 못하는 것 |
| --- | --- | --- |
| 파일과 저장 | 실제 HWP 구조, 저장 대상과 기대 버전, 저장 전 버전의 복구 가능 여부. 다른 이름으로 저장할 때는 원본 해시 불변도 확인한다. | 문서 전체의 내용과 배치 |
| 편집 내용 | 대상의 최종 값, 비대상 본문과 필드의 보존 | 글의 품질이나 문항 적합성 |
| 문서 구조 | 표와 병합 관계, 스타일 참조, 비대상 이미지와 첨부 데이터 | 원본과 같은 조판 결과 |
| 독립 호환성 | 다른 reader 또는 별도 검증 환경에서의 열기와 내용 비교 | 모든 한글 버전의 호환성 |
| 배치 | 검증된 렌더러에서의 넘침, 줄바꿈과 페이지 변화 | 렌더러가 지원하지 않는 요소 |

변경하지 않은 데이터의 보존 기준을 엔진별로 정의한다. 이미지 payload와 보존 대상의 해시, 문서 구조의 의미 비교를 사용할 수 있다. 전체 출력 파일의 바이트 동일성만 요구하지는 않는다. 해석하지 못한 레코드를 안전하게 유지할 수 없다면 그 문서의 편집을 거부한다.

글의 길이가 바뀌면 정상적으로 줄바꿈과 페이지 수가 달라질 수 있다. 이를 모두 오류로 취급하거나 자동 축약과 글꼴 축소로 숨기지 않는다. 고정 페이지 제한이 중요한 작업은 실제 배치 검사가 필요하고, 검사하지 못했다면 그 제한은 미검증으로 남긴다.

## 클라우드 실행과 개인정보

문서 엔진의 첫 기술 검증은 Linux 컨테이너에서 수행하는 안을 제안하고, 원격 MCP 배포는 Sites 환경에서 별도로 검증한다. 문서 작업에 한글, Windows 라이선스, COM 등록, 화면이나 클릭이 없어야 한다. 엔진 자체는 외부 네트워크를 끈 실행에서도 동작을 확인하되, 원격 MCP의 인증과 파일 전달까지 오프라인이어야 한다는 뜻은 아니다. 언어와 런타임 의존성까지 없앤다는 뜻도 아니다.

파일 접근은 실행 환경과 사용자·작업별 권한에 따라 구성한다. 로컬에서 사용자가 허용한 여러 파일 위치를 지원하고, 클라우드에서는 해당 사용자의 업로드나 허용된 저장 영역을 사용한다. 현재 프로토타입의 단일 workspace 제한을 새 제품의 고정 원칙으로 가져오지 않는다.

작업 실행의 시간과 메모리 및 압축 해제 한도, 실패한 산출물의 정리를 설계한다. 문서 스크립트나 외부 링크를 실행하지 않는다. 문서의 손상이나 미지원 기능이 서버 전체 장애로 번지지 않도록 격리된 작업 실행을 검증한다.

클라우드 제공 시 사용자별 권한과 파일을 분리한다. 에이전트 서비스, 문서 처리 서비스, 저장소 중 어디에 원문이 전달되는지 알리고, 업로드와 보관 기간은 사용자가 확인할 수 있어야 한다. 실제 개인 지원서를 동의 없이 테스트 코퍼스로 수집하거나 로그에 원문을 남기지 않는다.

기존 COM 프로토타입은 신규 출력만 하드링크로 게시한다. 새 로컬 경로는 이전 버전을 보관하고 같은 파일을 교체하며, 신규 사본 생성에는 무덮어쓰기 하드링크를 쓴다. 모든 마운트·객체 저장소에서 지원되는 방식은 아니다. 마지막 해시 확인과 교체 사이의 비협조적 외부 쓰기까지 원자적으로 차단하지는 못한다. 원격 서비스의 저장소별 버전 조건과 격리는 별도 설계·검증해야 한다.

## 기술 검증과 진행 단계 제안

### 소유자용 비공개 MVP의 완료 범위

이 MVP는 한 계정이 기존 연결과 브라우저에서 HWP를 가져와 지원 내용을 끝까지 읽고, 검증된 본문·최상위 표 셀을 수정하고, 같은 원격 문서 저장·이전 버전 복구·기본 미리보기·HWP 다운로드를 사용하는 제한된 단계다. 기존 단일 스타일 텍스트와 검증된 빈 셀 채우기·비우기를 포함하며 각 문서와 수정 요청의 대상 제한 및 저장 전 생성·보존 검사를 유지한다. 합성 45셀·46셀 문단·52블록의 실제 가져오기·이어 읽기·세 대상 편집·회수·원본 복구, 독립 Python/olefile의 본문 UTF-16 및 비대상 레코드 비교, 두 미리보기 페이지를 추가로 확인했다.

현재 계정의 비공개 사용 준비와 일반 양식·공개 서비스 인증을 구분한다. 임의 개인 양식의 호환성, 정확한 글꼴·줄바꿈·페이지 제한, 독립 HWP 프로그램의 시각 비교, 실제 두 OAuth 사용자 격리·철회, 운영 GC·재해 복구·비용 인증과 추가 클라이언트 검증은 완료로 표시하지 않는다. 기본 미리보기는 조판 인증을 제공하지 않는다. 중요한 결과는 HWP로 내려받아 별도 보관하고 최종 제출 상태를 확인한다. 이 결정은 개인 시험 파일의 업로드·수정을 허용하지 않는다. 완료 근거와 후속 확장은 [MVP 진행 상태](mvp-status.md)에 기록한다.

일정을 고정하기 전에 실제 파일로 다음 기준을 확인한다. 숫자는 초안의 검증 규모이며, 구현 결과나 확정된 서비스 수준이 아니다.

1. **엔진 후보 평가**: 엔진, 종속 라이브러리, 글꼴과 형식 자료의 이용·배포 조건 및 유지보수 조건을 확인하고, 비개인 합성 HWP 5.x 문서 최소 20개를 준비한다. 한글 본문, 여러 구역, 스타일 run, 일반 표와 병합 셀, 필드, 이미지 사례와 미지원 사례를 구분한다. 같은 코퍼스로 후보의 reader와 writer를 평가한다.
2. **전체 조회 검증**: 짧은 문서와 여러 호출이 필요한 긴 문서에서 지원하는 내용의 누락과 중복 없이 끝까지 조회되는지 확인한다. 마지막 문단과 표까지 도달하는지, 버전 변경과 중도 실패를 식별하는지, 미지원 요소와 조회 범위가 표시되는지 검사한다. 읽기·요약 요청에서는 원본 해시가 바뀌지 않아야 한다. 에이전트의 요약 검증에는 문서 앞·중간·끝의 내용을 확인해야 하는 사례를 포함하고, 일부만 읽은 결과를 전체 요약으로 보고하지 않는지 확인한다.
3. **무수정 저장 검증**: 선언한 지원 문서는 모두 읽기와 저장 후 재열기에 성공해야 한다. 본문, 표 관계, 스타일과 이미지 보존을 비교한다. 독립 reader 또는 별도 한글 검증 환경에서도 확인한다. 미지원 파일을 제외해 놓고 전체 코퍼스 성공률로 보고하지 않는다.
4. **국소 편집 검증**: 최소 10개 수정 사례에서 길이가 다른 한글, 스타일 run 경계, 반복 문구, 표 셀과 필드를 시험한다. 대상만 변경됐는지와 오래된 해시 및 이전 값 불일치 시 출력이 없는지 확인한다.
5. **한글 없는 실행 검증**: Windows, Wine, 한글과 GUI가 없는 Linux 컨테이너에서 실제 HWP의 조회, 수정, 저장, 재읽기와 MCP 호출을 통과시킨다. 기본 경로에 PDF와 DOCX가 생기지 않아야 한다. 처리 시간과 메모리 측정 후 성능 목표를 정한다.
6. **저장과 복구 검증**: 수정 요청의 기본 저장, 요청한 경우에만 수행되는 다른 이름으로 저장, 의도한 기존 대상 교체와 반복 저장을 시험한다. 저장하지 말라는 요청에서는 원본이 바뀌지 않아야 한다. 검증 실패, 버전 충돌, 파일 잠금, 백업 실패, 디스크 부족과 저장 중 종료에서는 직전 정상본을 보호하고 복구할 수 있어야 한다. 권한 밖 접근 거부와 클라우드 사용자 간 격리도 확인한다. 손상·암호화·과도한 압축·미지원 파일, 시간 초과, 동시 저장과 저장소 제약에서는 실패한 결과를 완료로 게시하지 않는다.
7. **제품 흐름 검증**: 같은 지원서와 과제 작업에서 에이전트의 대상 선택 정확도, 도구 호출 수, 수동 조작 수, 실패 복구와 결과 설명을 비교한다. 전체 읽기와 요약이 편집 없이 가능한지, 편집마다 별도의 저장 요청이나 저장 방식 선택을 요구하지 않는지도 확인한다. 외부 뷰어 없이 원본과 새 결과의 미리보기를 확인할 수 있는지, 문서 버전이 맞는지, 렌더링 경고와 HWP 다운로드 안내가 있는지도 검사한다.
8. **원격 MCP와 연결 검증**: Sites에 제한된 접근 대상으로 배포해 비개인 합성 HWP의 업로드, 전체 내용 조회, 요약, 국소 편집, 기본 저장, 재열기, 미리보기와 다운로드를 끝까지 시험한다. 실제 배포 환경의 엔진 실행과 자원 한도, 인증 및 사용자 간 격리, 권한 철회와 보관·삭제 정책을 확인한다. ChatGPT·로컬 Codex·실제 Codex Cloud 작업·Claude Desktop·Claude Code의 연결·인증·파일 전달을 각각 기록한다. Dots는 MVP에서 제외하며 추후 확장 시 따로 검증한다. 한 클라이언트나 서버의 성공을 전체 지원으로 표현하지 않는다. 통과한 지원 범위와 운영 비용·사용 한도·소스 이동 가능성을 검토한 뒤 호스팅과 일반 사용자용 연결 패키지를 확정한다.
9. **사용자 안내 마무리**: 핵심 문서 흐름 검증 후 HWP Easy 앱 설명을 일반 사용자에게 친절하게 다듬는다. 무엇을 할 수 있는지, 연결 후 어떻게 요청하는지, 지원 범위와 개인정보 전달 경로를 짧게 설명한다. 현재 시험용 연결을 완성된 편집 서비스로 소개하지 않는다.

각 단계의 결과는 통과, 제한적 통과, 실패로 기록하고 지원 범위와 근거를 남긴다. 첫 지원 문서의 필수 검사에서 조용한 내용 손실은 허용하지 않는다. 엔진이 기준을 충족하지 못하면 범위를 사용자와 조정하거나 다른 엔진을 평가한다. 한글 필수, HWPX 전용, PDF 결과로 요구사항을 조용히 바꾸지 않는다.

독립 제품보다 기존 프로젝트의 연결 도구나 기여로 해결하는 편이 낫다면 그 방향도 피벗 후보로 둔다. 기존 엔진을 재사용하는 것이 기본 검토 순서이며, 처음부터 새 HWP 엔진을 작성하는 결정을 내린 상태가 아니다.

## 다음 검토에서 정할 사항

- 첫 완료 경험을 지원서 표 채우기에 좁힐지, 일반 보고서의 문단 편집까지 포함할지.
- 사용자가 말하는 자유로운 편집에 표 행 추가, 스타일 수정과 새 문서 생성이 얼마나 중요한지.
- Sites 검증 결과에 따라 채택할 호스팅, ChatGPT·Codex·Claude의 연결 패키지와 인증 방식, 로컬 파일 직접 저장의 후속 연결 범위.
- 기본 미리보기와 별도로, 자동 배치 검사와 페이지 제한 검증을 첫 범위에서 어디까지 제공할지.
- 원격 문서의 명시적 삭제와 복구 UX, 미게시 바이트 정리 및 저장소별 안전한 교체 방식. 기본 보관 기간은 사용자가 직접 삭제할 때까지로 정했다.
- 기존 엔진의 기능에 비해 실제로 남는 제품 가치가 있는지. 없다면 독립 엔진 대신 어댑터나 기존 프로젝트 기여로 갈지.

사용자 피드백으로 우선 사용 사례와 제안 범위를 먼저 수정하고, 그 변경이 요구사항과 검증 기준에도 반영되도록 한다. PRD와 구현이 다르면 구현 상태를 사실로 기록하고, 새 기능 구현 전에 변경된 방향을 확인한다.
