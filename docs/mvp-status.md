# HWP Easy MVP 진행 상태

갱신일: 2026년 10월 9일. 사용자 결정에 따라 **현재 계정용 소유자 전용 비공개 MVP의 핵심 흐름 준비를 완료**했다. 아래의 완료 표시는 명시한 문서·사용자·실행 범위에만 적용한다. 일반 문서 호환성과 공개 서비스 준비를 뜻하지 않는다.

## 비공개 MVP의 제공 범위와 완료 근거

첫 제공 범위는 현재 계정의 Codex Desktop 연결과 같은 계정 브라우저다. Codex Cloud는 앞서 확인한 고정 합성 파일 흐름만 검증 범위로 명시한다. 본문·최상위 표 셀의 검증된 단일 스타일 텍스트 치환, 기존 빈 셀 채우기·비우기와 제한된 혼합 서식 치환을 제공하며, 파일마다 조회·대상 제한과 실제 저장 전 생성·보존 검사를 통과해야 한다. 중요한 결과는 HWP로 내려받아 별도 보관한다.

- [x] 일반 사용자에게 Python·CLI 설치를 요구하지 않는 기존 앱 연결과 브라우저 업로드·보기·내 문서 흐름.
- [x] 지원 내용을 끝까지 이어 읽고 미지원 범위를 구분하는 조회, 좌표로 구분한 대상 선택과 저장 전 검사.
- [x] 같은 원격 문서 저장, 이전 버전 유지·복구, 정확한 재시도와 충돌·128개 한도 안내.
- [x] 대표 45셀 합성 HWP의 실제 가져오기·6회 이어 읽기·52블록 전체 확인·3개 셀 작업·바이트 회수·원본 복구. 요청한 세 곳 외 내용이 일치하고 최초·편집·복구의 3개 버전을 보존했다.
- [x] 독립 Python/olefile의 모든 52문단 UTF-16 및 비대상 레코드 비교, 실제 로그인 브라우저의 두 기본 미리보기 페이지 로드.
- [x] 공개 빈 양식 한 파일의 실제 Codex Desktop 가져오기·187블록 전체 읽기·빈 셀 한 곳 계획/저장·정확 재시도·바이트 회수·원본 복구. 독립 Python/olefile의 187문단과 비대상 레코드 비교, 한글 2020의 원본/회수본 3쪽 유지와 화면상 선택 칸·주변 표 배치를 확인했다. 추가 확대 비교와 일반 조판 인증은 미완료다. [검사 범위](first-form-check.md#공개-빈-양식의-실제-연결-검사)
- [x] 4 MiB·128버전 제한, 직접 삭제까지 보관, AI 앱으로의 조회 내용 전달, PC 원본 미갱신과 조판·운영 미검증 경계를 [사용 안내](quick-start.md)에 명시.

이 판정은 소유자용 제한된 MVP의 사용 준비다. 위의 특정 문서 시각 확인을 임의 문서의 조판 인증으로 확대하지 않으며, 실사용 양식 전체의 호환성, 운영 GC·재해 복구·비용 인증을 완료한 뜻은 아니다. 다른 사용자 접근을 열기 전 실제 두 OAuth 계정 검증이 필요하다. 별도 일반 사용자용 설치 패키지와 추가 클라이언트는 현재 비공개 MVP의 완료 조건으로 요구하지 않는다.

앱 연결의 인증 갱신 중 재연결 요구가 반복 발생했다. 기존 계정·권한으로 재연결하는 절차를 사용 안내에 남겼으며 원인은 아직 확인하지 못했다. 인증 갱신의 연속 동작을 검증 완료로 표시하지 않는다. 인증 오류와 문서 보존 검사 실패는 구분하며, 저장 결과가 불확실한 경우 기존 요청과 버전 기록을 다시 확인한다.

문서 목록 식별 개선으로 보기 화면에서 직접 표시 이름을 설정하고 지울 수 있다. 원래 파일명은 자동 수집하지 않으며 이름 변경은 HWP와 저장 버전을 바꾸지 않는다. 브라우저 다운로드 파일 이름에는 문서·버전 번호를 포함한다. 합성 문서의 조건부 이름 변경·동시 충돌·정확 재시도·재시작 유지·기존 스키마 갱신과 버전 기록·바이트 불변을 실제 로컬 D1/R2에서 검사했다. 모의 owner 검사와 실제 OAuth 검증은 구분한다.

10월 6일 후속 소스에는 읽기 응답과 보기 화면의 **편집 가능 범위 안내**를 추가했다. 선택 버전 전체의 본문·표 셀 문단을 한 번씩 집계하고 기존 제한의 읽기 전용 이유를 고정 한국어로 설명한다. 후보 수가 직렬화·저장 성공을 뜻하지 않으며 편집 허용 범위는 유지한다. 합성 문서에서 이어 읽기·응답 변경 격리·혼합 서식 거부와 인접 지원 문단 저장·미지원 구조·페이지 번호·기존 원본 제한을 검사했다. 실제 로컬 compiled Worker에서 MCP와 보기 집계 일치, 조회 뒤 저장 불변 및 사용자 격리를 확인했다. 운영 버전 45 반영은 성공했고 새 화면의 실제 브라우저 검증은 미완료다.

**기존 혼합 글자 서식의 제한된 치환**을 10월 7일 운영 버전 **46**에 반영했다. 기존 한 서식 구간에서 글자 수와 각 글자의 UTF-16 길이를 유지하는 변경만 허용하며 서식 자체를 바꾸지 않는다. 합성 본문·일반 셀·병합 셀의 로컬 Worker 검사와 Windows·Ubuntu CI를 통과했다. 사용자 재연결 뒤 실제 native 기능 조회·가져오기·계획·저장·정확 재시도·embedded 회수·원본 복구를 확인했다. 세 문서에서 길이 변경·삭제·서식 경계 변경·UTF-16 폭 변경의 계획과 편집을 모두 거부했고, 함께 요청한 정상 수정도 일부 저장하지 않았으며 현재 버전·이력이 유지됐다. 실제 회수 바이트는 독립 로컬 재현과 전체 일치했고, Python/olefile의 원본/편집본 6개·스트림 54개·서식 레코드 22개 비교도 통과했다. 사용자 요청에 따라 이번 시험 문서 3개와 기록된 버전 9개를 삭제했고 삭제 후 조회·이력 접근 거부도 확인했다. 로컬 Python/stdio의 혼합 문단은 여전히 읽기 전용이다. 새 화면의 실제 브라우저 조작과 독립 프로그램의 시각 배치는 미검증이다. [지원 계약](remote-documents.md#혼합-글자-서식의-제한된-치환)

내 문서에서 직접 설정한 이름과 문서 번호의 일부로 검색할 수 있다. 검색어를 유지한 페이지 이동·검색 지우기·결과 없음 안내를 제공하며 본문을 열지 않는다. 합성 22개 문서의 한글·ASCII 대소문자·일반 문자로서의 `%`·`_` 검색, 페이지 누락 없음과 모의 두 owner·삭제 상태 필터 및 저장 불변을 실제 로컬 workerd/D1/R2에서 확인했다. 실제 브라우저의 합성 metadata 미리보기에서 검색과 페이지 이동도 확인했다. 기존 소유자 계정으로 로그인된 실제 배포에서도 합성 45셀 문서의 한글 이름·대문자 문서 번호 검색, 본문 문구의 검색 결과 없음과 수정 후 현재 저장본 링크를 확인했다. 실제 계정의 20개 초과 페이지 이동과 두 OAuth 사용자 격리는 이 검사 범위에 없다. 실제 OAuth 연결의 연속 동작과 일반 양식 호환성은 이 검사로 인증하지 않는다.

**10월 9일 긴 입력 후속 소스:** 공개 빈 양식의 7개 로컬 성공 사례와 6개 예상 거부를 확인했다. 각 성공 결과의 9개 스트림·187개 raw 문단을 별도 Python으로 비교했다. 기본 엔진에서 원본 3쪽이 긴 입력으로 4·5·13쪽까지 늘어나는 사례를 확인해 계획·저장 응답에 페이지 수 안내를 추가했다. 요청 문구 전체를 보존하며 엔진 열기를 추가하지 않는다. 페이지 수와 글꼴·줄바꿈·제출 분량의 검증은 구분하고 자동으로 문구를 줄이거나 일부만 저장하지 않는다. Worker Node 460개·공통 엔진 34개·Python 271개(11개 건너뛰기)와 compiled Worker 회귀를 통과했으며 **운영 배포는 하지 않았다**. [상세 범위](first-form-check.md#같은-공개-양식의-긴-입력과-거부-검사)

**반복 문구·병합 셀 선택 후속 소스:** 읽기 응답에 0부터 시작하는 좌표 계약과 병합 셀의 격자 시작·범위, 저장 순서 셀 번호의 구분을 추가했다. 반환한 대상 ID와 전체 기존 값을 사용하도록 도구 설명도 보완했다. 합성 3열 병합 표에서 반복 문구 한 칸만 저장한 결과·비대상 보존·이전 대상 ID 거부와 이어 읽기·검사 캐시 응답 격리를 확인했다. Node 462개와 실제 로컬 compiled Worker의 계약 전달·계획·저장·회수·복구 검사가 통과했다. 운영 배포는 하지 않았으며 개인 양식의 대상 선택 인증으로 확대하지 않는다. [좌표 계약](remote-documents.md#반복-문구와-빈-칸의-대상-좌표)

**언어별 글꼴 비교 보완:** 인천대 공개 빈 양식의 글꼴 대표값 비교로 인한 불필요한 거부를 합성 사례로 재현했다. 원격 후속 소스에서 첫 글자의 언어에 따른 대표값을 정확히 비교하고 전체 7개 언어의 글꼴 설정·다른 서식·raw 보존을 유지했다. 두 로컬 결과의 44문단·9스트림 독립 비교와 합성 본문/셀의 실제 로컬 D1/R2 저장·회수·복구를 확인했다. 상명대 공개 양식은 미지원 그림/도형을 알리는 부분 조회로 남았으며 편집하지 않았다. 운영 배포와 새 두 양식의 외부 HWP 프로그램 시각 비교는 미완료다. ## 확인한 흐름

- [x] 지원 본문·최상위 표 셀의 이어 읽기, 대상별 편집 제한, 저장 전 생성·보존 검사.
- [x] 같은 원격 문서 저장, 버전 충돌·정확한 재시도 처리, 이전 버전 유지와 복구. 삭제 계약과 실패 주입 검사는 모의 신원의 실제 로컬 저장소에서 확인.
- [x] 실제 Codex Desktop와 저장소 Codex Cloud에서 한 사용자·고정 합성 HWP의 입력·편집·저장·바이트 회수·재열기. Cloud의 보호된 링크로 PC 다운로드 확인.
- [x] 실제 로그인 브라우저의 합성 HWP 선택·업로드·기본 미리보기·다운로드 및 같은 계정 MCP 조회.
- [x] 내 문서 목록과 저장본 다시 열기, 이전/현재 버전 구분, 한국어 앱 소개와 사용 안내. 기능 변경은 Node·공통 엔진·실제 로컬 Worker 검사 및 Windows·Ubuntu CI로 확인한다. 최신 성능 변경의 방법과 한계는 [검사 기록](performance-check.md)에 남긴다.
- [x] 기존 개인 HWP의 로컬 읽기 전용 구조·편집 후보 분류. 원본은 보존하고 원격 전송하지 않았다. 대표 45셀 합성 양식과 페이지 번호 사례의 국소 편집 검사를 추가했다. 실제 양식 저장과 독립 프로그램 비교는 남아 있다. [첫 양식 검사](first-form-check.md)
- [x] 실제 Codex 연결을 동일 계정·권한으로 재인증한 뒤 현재·이전 합성 저장본의 끝까지 읽기와 버전 기록 불변을 확인했다. 별도 고정 합성 문서에서 6페이지·10블록 이어 읽기, 중복 셀의 좌표 선택, 같은 셀 두 번 수정, 정확한 재시도·오래된 버전 차단, 원본 해시·본문으로 복구를 확인했다. 최초·수정 2회·복구의 4개 버전을 보존했다. 정확한 OS 클립보드 붙여넣기와 일반 양식 사용은 별도 미검증이다.
- [x] 10월 6일 실제 소유자 브라우저 검색→저장본 전달 요청의 링크·ID 확인→Codex Desktop의 3회 이어 읽기→반복 문구 43곳 중 좌표로 선택한 셀 1곳 수정→같은 문서 저장→브라우저 HWP 다운로드를 확인했다. 이전 3개 버전을 유지했으며 52블록 중 나머지 51개는 그대로였다. 다운로드 해시 일치·재열기와 독립 Python/olefile의 비대상 레코드 비교를 통과했다. 복사 버튼의 성공 표시는 확인했지만 실제 OS 클립보드 붙여넣기, ChatGPT 웹 대화 호출과 외부 HWP 프로그램 조판은 미검증이다. 이 검사 전에도 재인증이 필요했으므로 자동 인증 갱신 해결의 근거가 아니다.

Worker는 생성 주석을 제외하면 main 빌드와 같고 WASM 바이트도 일치한다. 경로를 옮긴 소스의 관련 단위 20개와 compiled Worker 혼합 서식 검사를 통과했다. 소유자 전용 접근, 기존 D1/R2 바인딩·마이그레이션과 runtime revision 7은 유지했다. 실제 기능 조회에서 혼합 서식 기능과 400,000단위 한도를 확인했으며 위의 세 합성 문서 왕복을 통과했다. 신규 포장 helper는 배포 진입점을 `dist/server/index.js`에 두고 승인된 manifest·마이그레이션·런타임 파일만 포함한다. helper의 거부/보존 검사 3개와 실제 배포 archive의 파일 15개 경로·바이트 일치를 확인했다. 소스 push와 운영 배포는 별도 단계다. 아래 버전 45 기록은 이전 한도·경계 검증의 근거로 유지한다.

**10월 9일 로컬 후속 검증:** 개발 소스 `ee08a60`과 `origin/main`의 일치를 확인하고 재배포 없이 운영 브라우저에서 혼합 서식·병합 셀 합성 HWP의 업로드, 제한된 치환 후보 1곳·읽기 전용 3곳 표시, 기본 미리보기 로딩과 다운로드를 확인했다. 회수 바이트가 원본과 일치했고 10블록 재열기도 통과했다. 기존 45셀 저장본의 52블록 전체 조회·해시 일치와 한글 2020 열기를 확인했으며, 별도 고정 합성 원본/수정본은 한글에서 두 페이지 수와 표 배치·비대상 문구·지정한 치환을 비교했다. 상세 범위는 [첫 양식 검사](first-form-check.md)에 기록했다. 개인 문서는 업로드하거나 수정하지 않았다.

큰 기존 저장본의 다운로드·이력 유지, 읽기 전달/미리보기 생략과 권한·손상·삭제 차단은 최신 빌드의 로컬 workerd/D1/R2 합성 검사 11개가 통과했다. 실제 브라우저의 로컬 합성 제한 화면은 `net::ERR_BLOCKED_BY_CLIENT`로 접근하지 못했으므로 운영 브라우저 성공으로 집계하지 않는다. 운영 복사 버튼의 성공 안내와 정확한 버전·수정 금지 직접 복사 요청을 확인했다. 이후 같은 계정 Chrome의 합성 저장본에서 복사 버튼을 누르고 한글 2020의 저장하지 않은 새 빈 문서에 실제 `Ctrl+V`로 붙여넣었다. 다른 합성 기준 문구의 네이티브 복사·붙여넣기로 먼저 PC 클립보드 경로를 확인했으며, 사이트 요청의 350 UTF-16 단위·5줄 전체가 접근성 본문과 SHA-256까지 일치했다. 보기 링크·문서 ID·불변 버전 ID·수정 및 저장 금지 문구를 모두 보존했다. 브라우저 가상 클립보드 조회를 성공 근거로 사용하지 않았으며, 이 결과는 해당 Chrome→PC 편집기 전달 1건에 한정한다. ChatGPT 웹 대화 호출·Cloud 첨부 UI·인증 자동 갱신은 이 검사 범위에 없다. 문서 저장·재인증·인증 설정·접근 범위·운영 코드 변경 없이 기존 현재 버전과 한 개의 이력 표시를 유지했다.

같은 날 운영 자료와 분리한 복구 사전 검사와 합성 복구 시험을 추가했다. 원래 로컬 workerd runtime을 닫고 별도 새 D1/R2에 문서 2개·버전 4개·완료된 삭제 영수증 1개를 복사한 뒤 다시 시작해 전체 해시·HWP 재열기·이력·이름·기존 요청 재시도와 삭제 접근 차단을 확인했다. 나중에 삭제된 문서가 남은 복구 지점, 누락된 과거 생성 영수증, 진행 중 삭제와 손상 자료는 거부한다. Node 단위 검사와 실제 로컬 Worker 복구 검사를 CI에 등록했다. 운영 백업 내보내기·플랫폼 복원·최신 삭제 원장 확보·실제 OAuth·미게시 바이트 GC는 여전히 미검증이며 운영 데이터·배포·접근 설정은 변경하지 않았다. [독립 합성 복구 검사](durable-storage.md#독립-로컬-저장소의-합성-복구-시험)

이후 실제 Sites 설정·DB 화면과 연결 도구의 운영 백업 조회 범위를 확인했다. 테이블 조회는 가능했지만 확인한 화면에는 D1/R2 통합 내보내기·복원 기능이 보이지 않았으며 플랫폼 기능 부재로 단정하지 않는다. 기존 합성 45셀 문서의 현재·이전 버전 네 개를 같은 계정 브라우저에서 각각 내려받아 표시 해시·크기와 대조하고 모든 파일의 52블록 전체 읽기·재열기를 통과했다. 최초·복구본은 바이트가 같고 현재본은 복구본 대비 지정된 셀 문단 한 곳만 달랐으며 나머지 51블록과 기존 네 버전 이력을 유지했다. HWP 사본 보관의 확인이며 원격 메타데이터·권한·삭제 기록 전체 복원이나 별도 장애 영역의 백업을 인증하지 않는다. [운영 조회와 사본 보관의 경계](durable-storage.md#실제-sites-조회와-hwp-사본-보관)

후속 읽기 전용 저장소 점검은 실제 로컬 합성 R2의 세 페이지에서 기록된 파일 4개와 미게시 파일 1개를 구분하고, 모든 DB 기록·파일 5개의 키·크기·해시 불변을 확인했다. 목록 누락·중복·크기 불일치·페이지 진행 실패와 처리 예산 초과는 성공으로 표시하지 않는다. 결과는 수량만 반환하며 객체 삭제·운영 GC·원자적인 운영 백업의 증명은 제공하지 않는다. 배포 Worker·MCP에는 추가하지 않았다. 이후 재인증 없이 실행한 실제 `hwp_capabilities` 한 번은 `UNAUTHORIZED`와 `oauth_token_invalid_grant`로 거부됐다. 앞선 브라우저 성공과 MCP 연결의 인증은 별개이며 자동 갱신은 계속 미해결이다. 해당 검사에서는 재인증·같은 호출 반복·운영 문서 변경을 하지 않았다.

사용자가 기존 계정의 재연결을 승인한 뒤 ChatGPT 웹의 설치된 HWP Easy 관리 화면에서 다시 연결을 시작했다. 비밀번호·추가 인증은 사용자가 직접 완료했다. 이후 Codex Desktop의 읽기 전용 기능 조회가 성공했고, 기존 합성 45셀 문서의 현재·이전 네 버전을 각각 끝까지 읽었다. 각 버전의 52블록 전체 ID·종류·텍스트와 SHA-256이 로컬 사본을 새로 연 결과와 일치했다. 현재 버전의 embedded 회수 13,312바이트도 기존 사본과 같았고 HWP 재열기를 통과했다. 조회 전후 현재 버전·revision·네 버전 이력이 같았으며 원격 저장·복구·삭제·운영 배포는 하지 않았다. [사용 안내](quick-start.md)에 확인한 재연결 절차를 추가했다. 재연결 직후의 성공이며 자동 refresh 실행·장시간 유지·영구 해결의 증거로 집계하지 않는다.

10월 6일 Cloud 후속 작업은 운영 버전 **45**에 반영했다. 기준 커밋 `4541b26317bddfc2016519f0b44d735671aca0c5`까지 동기화하고 독립 검사에 필요한 `olefile`을 준비했다. 원격 처리에 400,000 UTF-16 단위의 본문·표 셀 합산 사전 거부와 수정 결과 길이 검사를 추가했다. 120만 자 지원 성공이나 설정 CPU 한도 확인으로 집계하지 않는다. 32초는 앞선 실패 로그의 관측값이며 인증 자동 갱신은 별도 미해결이다. 검증 범위와 측정 결과는 [성능 기록](performance-check.md#cloud-후속-원격-작업량-사전-검사)을 따른다.

PR 보강 검사에서 399,999·400,000·400,001단위의 입력·수정 계획 경계, 여러 문단·셀 합산과 결합 이모지를 확인했다. 로컬 compiled Worker의 초과 업로드·수정·복구 거부 후 기존 문서·현재 버전·이력·요청 기록·바이트가 유지됐고 브라우저 재시도가 차단됐다. 현재 버전이 커도 선택한 복구 원본이 한도 이내면 복구할 수 있다. 새 검사는 CI에 등록했다. 이후 실제 소유자 연결에서는 고정 writer 합성 HWP의 399,999단위 가져오기·7회 전체 조회, 400,001단위 가져오기 거부와 수정 계획·수정 거부 후 현재 버전·이력·해시 불변을 확인했다. 본문 +😀와 표 셀 −1단위의 합산 수정은 정확히 400,000으로 저장됐고, 7조각 회수·독립 바이트 재현·재열기·Python/olefile 비대상 레코드 보존을 통과했다. 399,999·400,000단위의 각 원본으로 복구해 네 버전을 확인한 뒤 명시적 요청으로 시험 문서와 그 버전만 삭제했다. [실제 경계 검사와 제한](performance-check.md#운영-버전-45의-합성-경계-검사)

400,000단위 파일의 첫 직접 가져오기는 파일 전달 호스트가 허용 목록 밖으로 배정돼 바이트 수신 전에 차단됐다. 이후 관측된 정확한 origin의 공개 DNS·HTTPS와 네 주소 설정의 허용/거부 경계를 확인하고, 사용자 승인으로 origin 하나만 추가해 환경 revision 7의 기존 버전 45를 비공개 재배포했다. 같은 합성 파일의 직접 가져오기·저장 해시 일치·첫 읽기 조각이 성공했고 400,001단위 거부와 기존 시험 버전·해시 유지도 확인했다. 시험 문서와 한 버전은 명시적 요청으로 삭제했다. 소스·저장소 바인딩·스키마와 소유자 전용 접근은 유지했다. 모든 미래 파일 호스트 지원이나 추가한 특정 호스트의 실제 바이트 전송 인증으로 확대하지 않는다. [설정 적용 뒤 직접 가져오기](performance-check.md#파일-전달-호스트-설정-후-직접-가져오기)

다음 연결 검증에는 미관측 파일 전달 호스트의 명확한 거부 안내와 새 화면의 실제 로그인 브라우저 조작이 남아 있다. 실제 서버의 초과 이전 버전 복구 거부는 미검증이며 로컬 검사와 구분한다. 정확한 조판·일반 양식 지원과 자동 인증 갱신도 별도로 해결해야 한다.

사용자 결정으로 이후 검증된 소스는 PR 생성 없이 `main`에 직접 push한다. Cloud·로컬 세션 모두 작업 시작과 push 전에 최신 `origin/main`을 확인해 동시 변경을 보존한다. 코드 push와 운영 Sites 배포는 별개이며, 배포는 요청받은 뒤 진행한다. 기존 검토 완료된 CPU 한도 보완도 main 소스에 포함한다. 지원팀은 영상과 진단 자료 수신을 확인했고 같은 녹화·실험이나 자료 재전송을 요구하지 않았다. 연결 후 refresh 과정의 원인·수정 일정은 아직 미확정이며 자동 갱신 문제는 미해결이다. 이번 Cloud 세션에는 재인증 실행 도구가 없으며 사용자가 재연결한 뒤 읽기 전용 `hwp_capabilities` 호출은 성공했다. 이후 운영 버전 45 검증 전 기능 조회에서 재연결 오류가 재발했다. 사용자가 다시 연결한 뒤 새 한도 조회와 고정 합성 문서 왕복은 통과했으나 자동 갱신 해결로 집계하지 않는다.

후속 소스에서 새 처리 한도에 걸린 기존 저장본도 보기 화면의 다운로드·버전 이력을 사용할 수 있도록 보완했다. 내용 조회·미리보기·편집 후보와 실패할 읽기 요청 복사는 제공하지 않는다. 소유자·해시·삭제 상태를 다시 검사하고 엔진 재시도나 저장은 하지 않는다. 관련 단위 검사와 합성 compiled Worker/D1/R2의 큰 이전·현재 저장본, 작은 저장본 흐름, 반복 조회 뒤 전체 저장 행·블롭 불변 및 권한·손상·누락·삭제 거부를 확인했다. 실제 로컬 D1/R2에서 첫 읽기와 안내용 재읽기 중 삭제 완료·정리 대기 경합도 차단했다. 운영 버전 45 반영은 성공했고 새 화면의 실제 브라우저 검증은 미완료다. [보기 제한 계약](remote-documents.md#cpu-실패-후속-보완)

합성 성능 후속 작업으로 큰 문서의 이어 읽기에서 문단 전체 배열·복사를 없애고, 바이트가 그대로인 경우 이미 재열기 검증한 모델을 재사용했다. 35만 자 전체 읽기는 로컬 측정에서 약 152ms→4ms로 줄었으며 120만 자의 한 번의 편집 흐름도 별도 진단에서 완료했다. 큰 문서 편집은 약 31초로 여전히 느리고, 실제 서버의 전체 메모리·지연·동시 요청은 미검증이다. [측정 방법과 한계](performance-check.md)

추가 계측 뒤 짧은 삽입 범위의 글자 스타일이 전부 원래 값과 같을 때 불필요한 재지정을 생략했다. 120만 자 문서의 짧은 마지막 문단 편집은 단일 로컬 비교에서 29.32초→17.80초로 줄었다. 복원이 필요한 대상과 긴 삽입 범위는 기존 경로를 유지하며 내용·스타일·raw 보존 검사를 생략하지 않는다. 남은 큰 비용은 원문과 저장 결과의 엔진 재열기다.

저장·수정 전 검사 요청의 중복 원본 열기도 제거했다. 새 원본 세션에서 raw 대상·요청을 검사하고 편집하며, 저장 결과와 복원본은 계속 독립 재열기 검증한다. 살아 있는 엔진을 캐시하지 않는다. 원본 열기를 포함한 120만 자 요청의 단일 로컬 비교는 편집 25.54→17.96초, 수정 전 검사 31.33→16.93초이며 이전 문단의 측정과 시작점이 다르다. 엔진 생성·쪽 조판 자체의 비용과 실제 서버 메모리·지연 검증은 남아 있다.

별도 이어 읽기 요청은 사용자·문서·불변 버전·해시별로 검사 모델만 제한적으로 재사용한다. 저장소 권한·바이트·삭제 상태와 raw 매핑은 매 호출 확인하며, 편집은 새 세션을 사용한다. 120만 자 고정 합성 문서에서 첫 호출은 약 8.1초, 다음 두 호출은 각각 약 28ms였고 151개 응답의 전체 내용이 새 검사 결과와 일치했다. 실제 서버 지연·전체 RAM을 측정한 것은 아니다. 캐시의 기한·크기·삭제 경합과 측정 한계는 [검사 기록](performance-check.md)에 명시한다. 인증 자동 갱신 문제는 여전히 별도 미해결이다.

아래 순서는 후속 작업 제안이다. 사용자가 선택한 현재 계정용 비공개 MVP와 구분하며, 미검증 항목을 완료로 집계하지 않는다. 새로운 클라이언트나 다른 사용자에게 제공할 때 해당 조건을 별도로 충족한다.

10월 6일 실제 소유자 배포에서 35만 자 합성 문서의 6회 전체 이어 읽기·짧은 마지막 문단 수정·같은 문서 저장·원본 복구·브라우저 다운로드를 확인했다. 3개 버전과 비대상 본문·원시 레코드가 보존됐다. 120만 자 입력은 실제 가져오기에서 CPU 한도 초과로 실패했으며 해당 도구 호출 구간의 Worker 로그는 CPU 32초 사용을 기록했다. 실제 서버 CPU·처리 시간은 확인했지만 전체 RAM·동시 처리·큰 문서 일반 지원은 계속 미검증이다. 이후 버전 45의 사전 거부와 위의 특정 합성 경계는 확인했으며, 큰 문서 지원을 넓히려면 엔진·호스팅 비용과 일반 양식 범위를 추가 검증해야 한다. 이전 버전 복구와 HWP 로컬 별도 보관의 성공을 플랫폼 D1/R2 백업 복구로 집계하지 않는다. 첫 양식 범위의 확인은 임의 양식의 지원 약속이 아니다. 이름 있는 필드, 중첩 표, 머리말·꼬리말, 이미지 편집, 일반 혼합 글자 스타일 수정, 새 문단·셀·표 구조 생성은 지원 완료로 표시하지 않는다. 위의 제한된 혼합 서식 치환도 소스 검증 범위와 운영 제공 범위를 구분한다. 필요한 양식이 현재 계약을 벗어나면 기능 확대와 첫 범위 축소 중 어느 쪽을 택할지 검토한다.

실제 사용자 격리와 공개 운영 준비를 끝낼 때까지 현재 소유자 전용 비공개 배포 범위를 유지한다. 소유자용 파일럿의 기능 확인만으로 다중 사용자 서비스를 완료 처리하지 않는다. 정확한 글꼴·줄바꿈·페이지 배치는 별도 검증이며, 현재 기본 미리보기의 완료 조건을 임의로 전체 조판 인증으로 확대하지 않는다.

성능 후속 작업으로 고정 합성 5종의 로컬 반복 처리, 4 MiB 전송 경계, 실제 로컬 Worker의 양식 저장·다운로드·복구 6회를 측정했다. 큰 문서의 느린 처리 사례는 제한적 결과로 남기고, 과도한 압축 본문은 WASM 실행 전에 UTF-16 길이를 검사하도록 보강했다. 실제 호스팅 전체 메모리·동시 처리·운영 비용은 여전히 미검증이다. [성능·한도 검사](performance-check.md)

## 현재 범위 밖

- Dots는 사용자 결정으로 MVP에서 제외한 추후 확장 항목이다.
- HWPX·PDF·DOCX 변환과 내보내기는 새 제품 범위에 없다.
- 기존 Windows COM용 EXE·GUI 배포안은 참고 자료이며 새 제품의 우선 개발 순서가 아니다.
- PC 원본 직접 저장은 별도로 허용된 로컬 연결이 필요하다. 현재 원격 저장과 다운로드를 PC 원본 자동 갱신으로 설명하지 않는다.
